Convolution

GBGPeriodicFields.Convolution — Module
Convolution

Periodic (circular) convolution of a field with a kernel, computed in spectral representation. This is the kernel-multiplier role of the package's measure structure — a grid→grid multiplier that filters a field against a fixed kernel — the spectral sibling of the differential operators and the same-base counterpart of Interpolation. The reductions, this module, and the grid↔point transfer realize one integration structure in three roles. On the torus the only convolution is the periodic one, and by the convolution theorem it is exactly a coefficientwise product of the transforms, so the operation lives in spectral representation. A scalar kernel multiplies every fiber component, so one operation serves scalar, vector, and tensor fields. The operation is named convolve (allocating infix ⋆) rather than *, because the coefficientwise product would read as a pointwise multiplication, which it is not.

A kernel is not a field. The two hold identical coefficients, so nothing but a type can say which role is meant, and the roles differ: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it (inv, defined for all four classes), while the same operation on a field is one the package does not define. Every kernel subtypes SpectralKernel, and the four classes reach every kernel-taking entry point interchangeably — StoredKernel holds one coefficient per mode, and the three compressed classes hold the parameters of a closed-form multiplier and evaluate it per mode. All four agree bit for bit, so the choice is one of memory and speed rather than of result.

Physics stays consumer-side: an LES filter, a viscous integrating factor, or a de-aliasing mask is a multiplier the consumer supplies — through radial_kernel when it depends on the mode only through $|k|^2$, or as coefficients built from FieldSpectralMultipliers and wrapped in StoredKernel. The package supplies the operation, not the physical meaning.

Convolution operations:

  • convolve / convolve! — convolve a field with a kernel; the in-place form adds $\alpha$/$\beta$ accumulation, and convolve(g₁, g₂) composes two kernels into one.
  • exponential_convolve! / exponential_convolve — convolve with the exponential radial kernel, computed from the wavenumber arrays on the fly instead of stored as a field; the two-operand form filters a weighted combination in the same pass.
  • The kernel-composed combine! method — the weighted combination of two fields convolved with a kernel, in one fused pass.

Kernel storage classes:

  • StoredKernel — one coefficient per mode, the $O(N^3)$ storage every other class exists to avoid. It wraps a ScalarFieldSpectral, which is how a consumer declares that those coefficients are playing the kernel role rather than being a field.
  • SeparableKernel — a kernel that factors over the axes, held as its three per-axis factors, so it costs kilobytes rather than a field; the class translation_kernel and assignment_window return.
  • RadialKernel — a kernel depending on the mode only through $|k|^2$, held as the function $\sigma$ computing it (a closure, evaluated per mode), so it stores no coefficients at all; the class spectral_cutoff, spectral_band and radial_kernel return.
  • ProductKernel — a radial and a separable factor held unmultiplied, which is what composing across the two families gives; it applies in a single pass like either factor alone.
  • materialize_kernel — expand a compressed kernel into a StoredKernel, for a consumer that wants to inspect or modify the coefficients.

Kernel builders:

  • radial_kernel — build a RadialKernel from any real function $\sigma$ of the squared wavenumber, which is the route for a multiplier this module does not name (a smooth filter, a hyperviscosity, an integrating factor).
  • spectral_cutoff / spectral_band — build the isotropic sharp low-pass kernel and its annular band-pass generalization, both radial kernels.
  • assignment_window — the linear (cloud-in-cell) mass-assignment window, a separable kernel, for deconvolving a gridded point density.
  • translation_kernel / translation_kernel! — the separable kernel that translates a field by a physical displacement, the shift theorem's phase.

GBGPeriodicFields.Convolution.convolve! — Function
convolve!(destination, field, kernel::SpectralKernel)
convolve!(destination, field, kernel::SpectralKernel, α, β)

Convolve field with the kernel whose transfer function is kernel, writing the result into destination in place and returning destination; both field and destination are in spectral representation.

Use this in-place form when destination is already allocated; the allocating convolve returns a fresh result instead.

Two kernels compose through the allocating form, which allocates nothing

This operation applies a kernel to a field. Composing two kernels into one is convolve(g₁, g₂), and there is deliberately no in-place spelling, because there is nothing for one to save: composition never builds a field of coefficients in any storage class. Two separable kernels compose into their per-axis products, and two radial ones into a single closure when both are built over canonical multipliers of the same concrete type (RadialKernel gives the condition); every other pair — two stored kernels, a cross-family pair, or radial operands failing that test — becomes a ProductKernel holding both factors unmultiplied and evaluating them in a single pass. Composing two stored kernels allocates zero bytes, against the $O(N^3)$ a materialized product would cost, and applying the composite is bitwise-identical to applying the two in sequence. Use materialize_kernel if the coefficients themselves are wanted.

The arguments are:

  • field — the field to filter, in spectral representation.
  • kernel — the kernel's transfer function $\hat g$, in any storage class of a SpectralKernel: a StoredKernel holding one coefficient per mode, or one of the compressed classes evaluated per mode (radial, separable, or their product), which costs $O(N)$ or a closure rather than $O(N^3)$. One scalar kernel serves scalar, vector, and tensor fields, and every storage class gives bitwise-identical results.
  • destination — the field written with the result; it may alias field or kernel, since the product is coefficientwise.
  • α, β — real accumulation weights, converted to the field's scalar type; the three-argument form overwrites ($\alpha = 1$, $\beta = 0$), the five-argument form computes $\alpha (f \star g) + \beta \texttt{destination}$.

As a real physical object the periodic convolution is the kernel-weighted local average of the field $f$ about each point $x$ — a low-pass filter when the kernel $g$ is a smoothing bump:

\[(f \star g)(x) = \int_\Omega f(y) g(x - y)\,\mathrm{d}y ,\]

with $\Omega$ the periodic box and the displacement $x - y$ reduced onto the torus. On the grid the operation computes the circular sum $(f \star g)[n] = \sum_m f[m] g[n - m]$ (indices modulo the grid size) — the integral's Riemann sum without the cell volume $|\Omega|/N$, the dimensionless convention that makes a kernel act as a per-mode transfer function ($\hat g \equiv 1$ is the identity; a sharp cutoff is a projection); the continuum integral above is $|\Omega|/N$ times it. By the convolution theorem (the forward transform unnormalized) the circular sum is exactly the coefficientwise product of the transforms, which is what this operation computes — $\hat g$ = kernel, broadcast over every fiber component of $\hat f$, with the $\alpha$/$\beta$ accumulate:

\[\widehat{\texttt{destination}}(k) = \alpha \hat f(k) \hat g(k) + \beta \widehat{\texttt{destination}}(k).\]

A real field needs a Hermitian kernel

The stored half-spectrum holds only the modes with a non-negative wavenumber along the folded axis (the layout's fft_dims[1], not necessarily the first physical axis); the rest are implied by the reality of the field, $\hat f(-k) = \overline{\hat f(k)}$. A kernel returns a field that is still real exactly when its own transfer function carries that symmetry, $\hat g(-k) = \overline{\hat g(k)}$ — equivalently, when the physical-space kernel $g$ is real. Every kernel the package builds satisfies it: the real, even ones (spectral_cutoff, spectral_band, assignment_window) trivially, and the complex translation_kernel by construction. A consumer-built kernel that breaks the symmetry yields coefficients that are those of no real field, and the inverse transform then silently keeps only their Hermitian part.

Spectral representation only: on the torus convolution is the coefficientwise spectral product.

GBGPeriodicFields.Convolution.exponential_convolve! — Function
exponential_convolve!(destination, field, multipliers, coefficient::Real)
exponential_convolve!(destination, field, multipliers, coefficient::Real, α, β)

                      offset_scale::Real, offset::ScalarFieldSpectral)
exponential_convolve!(destination, field, multipliers, coefficient::Real,
                      offset_scale::Real, offset::ScalarFieldSpectral, α, β)
exponential_convolve!(destination, α::Real, a, β::Real, b, multipliers,
                      coefficient::Real)
exponential_convolve!(destination, α::Real, a, β::Real, b, multipliers,
                      coefficient::Real, offset_scale::Real,
                      offset::ScalarFieldSpectral)

Convolve a field with the exponential radial kernel $\exp(c |k|^2 + s \hat w)$, where $c$ is a real coefficient on the squared wavenumber $|k|^2$, and the optional term adds a per-mode real field $\hat w$ supplied by the consumer under a real scale $s$. The kernel is evaluated from the wavenumber arrays on the fly — never built or stored as a field — and the result is written into destination in place, which is returned.

Use this in-place form when destination is already allocated; the allocating exponential_convolve returns a fresh result instead.

For a coefficient $c \le 0$ this is, as a real physical object, convolution with the periodic Gaussian (heat) kernel: the operator $e^{-c\Delta}$, which smooths the field at the length scale $\sqrt{-2c}$. In spectral representation it is the coefficientwise product with $\exp(c |k|^2)$, the true squared wavenumber kept at the Nyquist frequency (the Laplacian convention), so the kernel is real, even, and positive — a valid kernel for every real field. The optional term $s \hat w$ generalizes the exponent by whatever per-mode field the consumer supplies.

Choose between this and a stored kernel by reuse. When the exponent changes between applications — so a stored kernel would be rebuilt each time — the lazy form wins: it removes the kernel's build pass, its residency, and its per-application field read, reading three one-dimensional wavenumber arrays instead (measured $\approx 1.4\times$ over rebuild-then-convolve! on a GPU at $256^3$). When one fixed kernel is applied many times, a stored kernel with convolve! is the faster route: the per-mode exponential costs more than the field read it saves ($\approx 1.1\times$ on a GPU; $\approx 1.7\times$ on a CPU, where the exponential is expensive and is evaluated once per fiber component). The two-operand forms win on both backends — $\approx 1.5\times$ over the sequential combine!-then-convolve! pair, except the CPU two-operand exponential at $\approx 1.1\times$ — fusing away the combination's destination write and re-read as well.

On a CPU a deeply damped kernel has one further Float32 cost cliff: modes whose factor lands in the subnormal range — exponent arguments $c \lvert k\rvert^2 + s \hat w$ between about $-103$ and $-87$ — are produced through a hardware assist at roughly $16\times$ the usual per-element cost, so a kernel deep enough to cross that band pays a multiple of its whole pass. The Float64 band (arguments below about $-708$) is beyond any physical kernel, and the GPU backends flush subnormals to zero, so both are unaffected; where the band matters, use Float64 or a milder exponent.

The arguments are:

  • destination — the field written with the result; it may alias field (or a, b, offset), since the product is coefficientwise.
  • field — the field to filter, in spectral representation.
  • α, β — in the single-operand forms, where they trail the argument list, the usual accumulation weights: the result is written as $\alpha (\text{filtered } f) + \beta \texttt{destination}$.
  • α, a, β, b — in the two-operand forms, where they lead it, the real weights and fields of the combination $\alpha a + \beta b$ the kernel is applied to, exactly as combine! takes them; with b === destination the filtered accumulate runs in place. The two roles never share a signature, which is why one pair of glyphs can serve both.
  • multipliers — the wavenumber arrays for the field's grid; the kernel is evaluated from their squared-wavenumber family.
  • coefficient — the real factor $c$ on $|k|^2$ in the exponent, dimensionless as received (the consumer folds its own physical factors before the call).
  • offset_scale, offset — the real scale $s$ and the per-mode field $\hat w$ of the optional exponent term $s \hat w$; offset is a scalar field in spectral representation holding real values (as a materialized radial kernel would). The pair enters as scale times field so a changed scale costs nothing — the resident $\hat w$ is built once.
The offset must be real-valued

The exponential of a real, even multiplier keeps a real field real. A complex-valued offset breaks that Hermitian symmetry exactly as a consumer-built kernel can under convolve!, and the inverse transform then silently keeps only the Hermitian part. There is deliberately no scalar exponent offset: a constant $s_0$ in the exponent is $e^{s_0}$ times the kernel and belongs in $α$.

The single-operand accumulate form computes

\[\widehat{\texttt{destination}}(k) = \alpha \exp\bigl(c |k|^2 + s \hat w(k)\bigr) \hat f(k) + \beta \widehat{\texttt{destination}}(k),\]

Spectral representation only.

The two-operand form

Passing α, a, β, b ahead of the multipliers applies the same kernel to a weighted combination, $\exp(c |k|^2 + s \hat w) \cdot (\alpha \hat a + \beta \hat b)$, in one pass — the lazy-kernel twin of the kernel-composed combine! method, and the same fusion the kernel-composed divergence! and helmholtz_projection! arities perform. With b === destination it is the filtered accumulate, computed in place.

Kernel storage classes

A kernel is anything an operation can apply as the coefficientwise product $\hat f \cdot \hat g$, and the package holds one in whichever of four forms is cheapest for its multiplier: a ScalarFieldSpectral of coefficients wrapped in a StoredKernel when the multiplier is arbitrary, the per-axis factors when it separates, the function computing it when it depends on the wavenumber only through $\lvert k\rvert^2$, or a pair of the last two held unmultiplied when a composition crosses those two families. All four are applied identically and give bitwise-identical results, so the choice is one of storage, not of meaning.

Every operation taking a kernel dispatches on SpectralKernel, the supertype of the four classes below. It is documented with Fields, where the protocol is defined so the differential operators and the reductions can name it too (weighted_inner narrows it further, taking only a stored or radial weight).

A field in spectral representation is not a kernel. A StoredKernel and a ScalarFieldSpectral hold identical data, so only a type can say which role is meant, and the distinction is load-bearing: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it (inv), while the same operation on a field is one the package does not define. Wrap the field in a StoredKernel to declare the role.

GBGPeriodicFields.Convolution.StoredKernel — Type
StoredKernel(field::ScalarFieldSpectral)

Wrap a scalar field in spectral representation so that it plays the kernel role — one coefficient per mode, the $O(N^3)$ storage the compressed classes exist to avoid.

The wrapper is required rather than a convenience. A field and a kernel hold identical data, so nothing but a type can say which role is meant, and the two admit different operations: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it (inv), while the same operation on a field is nonlinear in that field's spectral representation and the package does not define it. So a bare ScalarFieldSpectral passed where a kernel is expected does not dispatch — wrap it here, or build the kernel with one of the builders, and the role is then carried by the type rather than inferred from the call site.

Wrapping costs nothing per application: the struct holds a reference, and the fused passes reach the coefficients through it without an extra read. Wrap once, where the kernel is built.

materialize_kernel returns this class, so a compressed kernel expanded into its coefficients arrives already in the kernel role.

The fields are

  • field — the ScalarFieldSpectral holding the coefficients, referenced rather than copied.

GBGPeriodicFields.Convolution.SeparableKernel — Type
SeparableKernel

A spectral kernel that factors over the axes, $\hat g(k) = \prod_a \sigma_a(k_a)$, stored as its three one-dimensional per-axis factors rather than as a full field. The factors are evaluated into the product one mode at a time, so the kernel never occupies a field's worth of memory: three arrays of $O(N)$ entries in place of $O(N^3)$ coefficients — kilobytes rather than the hundreds of megabytes a $256^3$ kernel would take — and applying it reads no FIELD-SIZED kernel stream: the three $O(N)$ factors are read per mode, which is the saving, not zero kernel traffic.

Build one with translation_kernel (the displacement phase, complex factors) or assignment_window (the mass-assignment window, real factors), and apply it exactly like a kernel held as a field: pass it to convolve! or as the trailing kernel of a fused operator.

Whether that is also faster depends on the base. Applying it moves two field-sized streams where a stored kernel moves three, but evaluates the product per mode, so it trails a stored kernel on a base small enough to sit in cache and overtakes it once the base is bound by memory. On a small base where the difference matters, materialize_kernel trades the memory back, and its docstring carries the measured crossover. Use inv for the reciprocal kernel $1/\hat g$, which is separable too since $1/\prod_a \sigma_a = \prod_a (1/\sigma_a)$ — the deconvolution an assignment window is built for.

The fields are

  • factor_1, factor_2, factor_3 — the per-axis factors, each shaped to broadcast along its own axis, of the stored spectral length of that axis (the folded axis is the layout's fft_dims[1]).
  • grid, layout — the base and Fourier layout the factors were built for, which a call checks the field against.
Separable, not radial

A kernel that depends only on the wavenumber magnitude is radial, not separable — a function of $k_1^2 + k_2^2 + k_3^2$ does not factor into per-axis terms. This type is for kernels that genuinely do factor, whose canonical case is a per-axis phase.

GBGPeriodicFields.Convolution.RadialKernel — Type
RadialKernel

A spectral kernel that depends only on the wavenumber magnitude, $\hat g(k) = \sigma(|k|^2)$, stored as the function $\sigma$ rather than as its values — its symbol, in the sense the differential operators use for the multiplier a coefficientwise operator applies. The function is evaluated one mode at a time from the wavenumber arrays the multipliers already hold, so the kernel occupies no field: a closure and three references, against the $O(N^3)$ coefficients a stored kernel needs — bytes rather than the 129 MiB a $256^3$ kernel would take.

Build one with spectral_cutoff or spectral_band for the sharp masks, or with radial_kernel for any other such function — a smooth filter envelope, a hyperviscous $\exp(-\nu (|k|^2)^p \tau)$, an integrating factor. Apply it exactly like a kernel held as a field: pass it to convolve!, to a fused operator's trailing kernel argument, or to weighted_inner as a reduction weight.

Why this family is closed by construction: $|k|^2$ is real and even in every component, so any real $\sigma$ of it is real and even too, hence Hermitian-symmetric — the coefficients it produces are always some real field's. It also carries the true squared wavenumber at an even axis's Nyquist — the value a magnitude-dependent multiplier wants there, unlike the derivative wavenumbers, which are zeroed at that mode — so no case analysis is needed anywhere in the family.

The fields are

  • sigma: the function $\sigma$, called with the real $|k|^2$ and returning a real value.
  • multipliers — the FieldSpectralMultipliers supplying $|k|^2$, referenced, not copied. Whether they are the grid's own wavenumbers (canonical, built by the convenience constructor from the grid) or a caller's own (supplied through the explicit constructor, which validates lengths and not values) is part of their type, and it decides whether composing two of these kernels collapses into one: two kernels over canonical multipliers of the same type hold the same coordinates by construction and merge, while a kernel over a caller's own coordinates keeps both operands as a ProductKernel, since one composite can carry only one set of coordinates.
  • grid, layout — the base and Fourier layout the kernel was built for, which a call checks the field against.
Radial, not separable

$|k|^2 = k_1^2 + k_2^2 + k_3^2$ is a function of the sum, so it does not factor into per-axis terms and cannot be stored per axis the way a SeparableKernel is. The two families are disjoint: a phase depends on direction, a magnitude-dependent multiplier does not.

GBGPeriodicFields.Convolution.ProductKernel — Type
ProductKernel

The coefficientwise product of two spectral kernels, held as the pair rather than evaluated — what convolve returns whenever composing cannot produce a single kernel more cheaply. That covers every cross-family pair, two stored kernels (merging those would mean materializing an $O(N^3)$ product), and two radial kernels whose coordinates cannot be shown to agree.

Composition inside a family usually stays in that family: two axis-factored kernels always multiply into one axis-factored kernel, and two radial symbols multiply into one radial symbol when both are evaluated against the same coordinates, which RadialKernel explains and decides by type. Radial operands that fail that test land here instead. Across families there is no collapse at all: a radial symbol times an axis-factored phase is neither radial nor separable, so the composite keeps both operands and multiplies their per-mode values. Either order composes and gives the same operator, the product being coefficientwise, and a composite composes further in either position. It still stores nothing of field size, and it applies exactly like either operand.

This is what lets a mask and a displacement — or any radial symbol and any per-axis factor — be applied in a single pass instead of two.

The fields are

  • first_kernel, second_kernel — the two operands, held unmultiplied and evaluated per mode.

Base.inv — Function
inv(kernel::ProductKernel)

The reciprocal kernel $1/\hat g$, formed by inverting each factor — the product of the reciprocals is the reciprocal of the product — so it is another ProductKernel and materializes nothing.

Each factor must have no zeros on any stored mode

The composite vanishes wherever either factor does, so both must be invertible; each factor's own inv states the condition it needs.

inv(kernel::RadialKernel)

The reciprocal kernel $1/\sigma(|k|^2)$, formed by composing the reciprocal with $\sigma$, so it is another RadialKernel and still costs no storage.

The function must have no zeros on any stored mode

A $\sigma$ that vanishes at any stored mode gives a non-finite reciprocal — a sharp mask is exactly such a function, so inverting a spectral_cutoff is not meaningful.

source
inv(kernel::SeparableKernel)

The reciprocal kernel $1/\hat g$, itself separable because $1/\prod_a \sigma_a = \prod_a (1/\sigma_a)$ — so it is formed per axis, at $O(N)$ cost, with no field materialized. Applying it deconvolves by kernel, which is what a mass-assignment window is built for (assignment_window).

The factors must have no zeros

Every per-axis factor must be non-zero at every stored mode; a zero yields a non-finite reciprocal. An assignment_window satisfies this on every stored mode, whereas a phase kernel does not in general (a displacement can drive an even axis's Nyquist factor to zero).

inv(kernel::StoredKernel)

The coefficientwise reciprocal of a kernel held as a field, which is the kernel that deconvolves by it.

A kernel with a zero coefficient annihilates that mode, so no kernel undoes it and this throws rather than returning a non-finite coefficient. The check is a full pass over the coefficients, which an explicit inversion can afford; the axis-factored SeparableKernel method checks its $O(N)$ factors instead, and the radial method documents the precondition it cannot test cheaply.

materialize_kernel(kernel::SeparableKernel)

Evaluate an axis-factored kernel into a kernel held as a field, returning the StoredKernel whose coefficients are the product of the per-axis factors. The result applies identically and gives bit-identical results — the two differ only in what they cost.

Use this to trade memory back for speed on a small base. Applying an axis-factored kernel moves two field-sized streams where a stored kernel moves three, but evaluates the product per mode; which wins depends on whether the base outgrows cache. Measured against a stored kernel on a vector field, the axis-factored form trails it below cache and overtakes it above: threaded on a CPU it runs at roughly $0.5$–$0.6$ of its speed at $64^3$, crosses one somewhere past $128^3$, and is $1.1$–$1.2$ times faster at $256^3$–$512^3$. Single-threaded the crossing never arrives in this range, and on a GPU the ratio sits near parity at $64^3$ and drifts slightly down — a device being bandwidth-bound at every size here rather than growing out of cache. The full grid is in PERFORMANCE.md's finding (o) table. So a run whose grids are small, or which applies one fixed kernel very many times with memory to spare, can materialize once and keep the field; a run at production resolution should not, and pays a field of residency for nothing if it does (129 MiB at $256^3$, against about 10 KiB for the factors).

This gives up the memory saving entirely

The returned field costs the full $O(N^3)$ the axis-factored form exists to avoid. Materialize deliberately, for a measured reason on a specific base — not by default.

Kernel builders

Each returns a kernel for a multiplier the package names, in whichever storage class that multiplier admits — and each signature says which class, since that is what determines the cost of applying it: radial_kernel, spectral_cutoff and spectral_band give a RadialKernel (a closure); translation_kernel and assignment_window give a SeparableKernel (three $O(N)$ factors). radial_kernel is the escape hatch: it builds one from any other real function of $\lvert k\rvert^2$, which is the route for a filter, a hyperviscosity, or an integrating factor the package does not name.

GBGPeriodicFields.Convolution.radial_kernel — Function
radial_kernel(sigma, reference::AbstractFieldSpectral,
              multipliers::FieldSpectralMultipliers) -> RadialKernel

Build the RadialKernel for an arbitrary real function of the squared wavenumber — its symbol, in the sense the differential operators use — the general constructor behind spectral_cutoff and spectral_band, for the multipliers the package does not name.

The arguments are:

  • sigma — a function of one real argument, the squared wavenumber $|k|^2$, returning a real value. It must be pure and GPU-safe: capture only values, never a type — a closure holding a Type is not a bitstype and a device rejects it at launch — and no mutable state or scalar indexing of device arrays; anything it captures by value, such as a viscosity or a substep, is free to vary per call because building a kernel allocates nothing of field size.
  • reference — a field in spectral representation fixing the base, layout and element type.
  • multipliers — the wavenumber arrays supplying $|k|^2$.

The physics stays with the consumer: an integrating factor is radial_kernel(k2 -> exp(-ν * k2 * Δt), …), a smooth filter its own envelope. Because the function is evaluated per mode rather than stored, a kernel whose parameters change every call costs nothing to rebuild — where a stored kernel would pay a full field write each time.

GBGPeriodicFields.Convolution.spectral_cutoff — Function
spectral_cutoff(reference::AbstractFieldSpectral,
                multipliers::FieldSpectralMultipliers, wavenumber_cutoff) -> RadialKernel

Build an isotropic sharp low-pass kernel, returned as a RadialKernel — the function itself rather than its coefficients, so it costs no field of storage. Use materialize_kernel to expand it into a StoredKernel. It is built on reference's grid and array backend: the transfer function is $1$ for $|k| \le k_c$ and $0$ above it.

Convolve a field with it for the ideal low-pass projection, the basis of spectral truncation and de-aliasing. It is idempotent ($\hat g^2 = \hat g$), hence a projection, and it is the low-pass special case of spectral_band with $k_\mathrm{lo} = 0$.

The arguments are:

  • reference — a field in spectral representation whose grid and backend the kernel matches.
  • multipliers — the wavenumber arrays for that grid, checked against reference.
  • wavenumber_cutoff — the cutoff wavenumber $k_c$; a mode is kept when $|k| \le k_c$.

\[\hat g(k) = \mathbf{1}\bigl[ |k| \le k_c \bigr].\]

The choice of cutoff, such as a $2/3$ de-aliasing rule or an LES filter scale, is the consumer's. The squared wavenumber $|k|^2$ keeps the true value at the Nyquist frequency (the Laplacian convention).

GBGPeriodicFields.Convolution.spectral_band — Function
spectral_band(reference::AbstractFieldSpectral,
              multipliers::FieldSpectralMultipliers,
              wavenumber_low, wavenumber_high) -> RadialKernel

Build an isotropic sharp spectral band-pass kernel, returned as a RadialKernel — the function itself rather than its coefficients, so it costs no field of storage. Use materialize_kernel to expand it into a StoredKernel. It is built on reference's grid and array backend: the transfer function is $1$ on the wavenumber shell and $0$ outside it.

Convolve a field with it to keep an isotropic shell of wavenumbers — a de-aliasing band, a forcing band, or any shell selector. It is idempotent ($\hat g^2 = \hat g$), hence a projection, and it is the annular generalization of spectral_cutoff, which is the low-pass case $k_\mathrm{lo} = 0$.

The arguments are:

  • reference — a field in spectral representation whose grid and backend the kernel matches.
  • multipliers — the wavenumber arrays for that grid, checked against reference.
  • wavenumber_low, wavenumber_high — the inner and outer edges $k_\mathrm{lo}$, $k_\mathrm{hi}$ of the retained shell.

\[\hat g(k) = \begin{cases} 1, & k_\mathrm{lo} \le |k| \le k_\mathrm{hi}, \\ 0, & \text{otherwise,} \end{cases}\]

with $|k|^2$ keeping the true value at the Nyquist frequency (the Laplacian convention). The band edges are the consumer's choice.

GBGPeriodicFields.Convolution.assignment_window — Function
assignment_window(reference::AbstractFieldSpectral,
                  multipliers::FieldSpectralMultipliers) -> SeparableKernel

Return the linear (cloud-in-cell) mass-assignment window — assignment in the particle-mesh sense of depositing point mass onto grid cells, unrelated to the fused elementwise write that threading_cutoff measures — as a SeparableKernel — its three per-axis factors rather than a field of coefficients — on reference's grid and array backend, for deconvolving a gridded point density.

Use it when a pair correlation is estimated from points deposited on a grid rather than counted directly. Depositing $M$ points on the grid with the positive linear assignment (LalescuSpline(0, 0) — the two-point linear "tent" transfer kernel, the $m = 0$ member of the spline family documented with Interpolation) spreads each point's mass over a tent, so the gridded density is the true density $\rho$ convolved with this window, $\rho_g = \rho \star W$. Dividing the transform by $\hat W$ — a convolve by $1/\hat W$ — undoes that smearing before you estimate the radial distribution function $g(r)$ (the pair density at separation $r$ relative to an uncorrelated uniform gas).

Here reference is a field in spectral representation whose grid and backend the window matches, and multipliers supplies the wavenumber arrays for that grid, checked against reference.

As a real physical object $W$ is the linear B-spline ("tent") cloud, the tensor product of per-axis tents:

\[W(x) = \prod_{a=1}^{3} \frac{1}{\Delta x_a} \max\Bigl(0, 1 - \frac{|x_a|}{\Delta x_a}\Bigr),\]

each a tent of half-width one cell $\Delta x_a$ along axis $a$, of unit integral and peaked at the origin (a cell-wide top-hat convolved with itself, hence the squared sinc). The function returns its transfer function $\hat W(k)$, the squared sinc

\[\begin{gathered} \hat W(k) = \prod_{a=1}^{3} \operatorname{sinc}^2\Bigl(\tfrac{k_a \Delta x_a}{2}\Bigr), \\ \operatorname{sinc}(y) = \frac{\sin y}{y}, \end{gathered}\]

computed from the per-axis wavenumber $k_a$ (kept at the Nyquist frequency) and the grid spacing $\Delta x_a$, so $\hat W(0) = 1$ and it decays toward the grid scale. Because the squared sinc does not vanish at any wavenumber the grid resolves, dividing by it is stable. The package supplies the window; the density estimate and the correlation normalization stay consumer-side.

GBGPeriodicFields.Convolution.translation_kernel — Function
translation_kernel(reference::AbstractFieldSpectral,
                   multipliers::FieldSpectralMultipliers,
                   offset::NTuple{3, Real}) -> SeparableKernel

Build the kernel that translates a field by the physical displacement $h$ = offset, returned as a SeparableKernel on reference's grid and array backend: convolving a field $f$ with it gives the displaced field $f(x - h)$, the position $x$ reduced onto the periodic box.

Use it to move a field onto a displaced grid without re-gridding — a shift-and-average filter, the relocation of a probe, or the displaced evaluation of a phase-shift de-aliasing scheme. Apply it with convolve / convolve!, which is allocation-free in place; because a scalar kernel multiplies every fiber component, one call translates a whole vector or tensor field, and because the kernel depends on nothing but the displacement, one kernel serves every field it is applied to (and it is separable, so building it costs three $O(N)$ axis passes, not a field). To sample the field at the displaced positions $x + h$ instead, pass the negated offset — the two are inverse translations. This is the package's one complex kernel: on every sub-Nyquist mode it is a pure phase of unit modulus, so it moves the field without touching any amplitude, unlike the real and even spectral_cutoff or assignment_window. At the Nyquist frequency — the highest wavenumber a grid resolves, $\pi/\Delta x_a$, which an even-length axis stores as a single self-conjugate mode — the factor is instead the real number $\cos(\pi h_a / \Delta x_a)$, which attenuates rather than translates and vanishes at a half-cell shift — the reality condition demands it, and the warning below gives the detail.

The arguments are:

  • reference — a field in spectral representation whose grid and backend the kernel matches.
  • multipliers — the wavenumber arrays for that grid, checked against reference.
  • offset — the displacement $h = (h_1, h_2, h_3)$, a physical length per axis in the units of the box rather than a count of cells; a half-cell displacement is 0.5 .* grid.grid_spacing on the Grid3D the field lives on.

As a real physical object the translation is the convolution with a Dirac delta displaced to $h$ and periodized on the box, $g = \delta(x - h)$, whose sifting property (integrating against a delta evaluates the integrand at the delta's location) gives $(f \star g)(x) = f(x - h)$ exactly. On the grid that $g$ is the band-limited (periodic-sinc) interpolation stencil centred at $h$, so the convolution re-samples the trigonometric interpolant of $f$ at the displaced nodes $x_n - h$, and collapses to a plain index shift when $h$ is a whole number of cells. Its transfer function $\hat g$ at wavenumber $k$ is the shift theorem's phase, assembled per axis from that wavenumber's component $k_a$ and the displacement $h_a$ along the axis:

\[\hat g(k) = \prod_{a=1}^{3} \bigl[ \cos(\kappa_a h_a) - \mathrm{i} \sin(\tilde\kappa_a h_a) \bigr],\]

where $\kappa_a$ is the true wavenumber and $\tilde\kappa_a$ the Nyquist-zeroed derivative one — the package's two families, and the reason this is written with two symbols rather than as the bare phase $e^{-\mathrm{i} k \cdot h}$. The two coincide on every resolved mode — so the factor there is that pure phase — and part only at an even axis's Nyquist frequency, where the warning below applies.

At the Nyquist frequency the phase becomes a real attenuation

On an even-length axis the Nyquist mode of a real field carries a single real amplitude that stands for both of the wavenumbers $\pm\pi/\Delta x_a$ (with $\Delta x_a$ the grid spacing along axis $a$), so its band-limited form is the cosine $\cos(\pi x_a/\Delta x_a)$, and displacing that cosine re-samples on the grid to $\cos(\pi h_a/\Delta x_a)$ times itself. At that one frequency the kernel therefore carries this real factor rather than a complex phase — and it has to be real: the Nyquist mode is its own conjugate partner, so a complex factor there would leave coefficients that are those of no real field at all. A displaced Nyquist mode is thus attenuated rather than moved: it vanishes for a half-cell displacement and changes sign for an odd whole-cell one. Two consequences follow, both confined to that frequency: the translation is not invertible there (displacing by $h$ and back scales the mode by $\cos^2$), and two translations compose exactly on every resolved mode but not at Nyquist. Whole-cell displacements are exact everywhere, and a field with no Nyquist content — one truncated by a de-aliasing cutoff — never meets the caveat at all.

translation_kernel!(kernel::SeparableKernel, multipliers, offset)

Rebuild kernel in place for a new displacement offset, overwriting its per-axis factors. Internal API

These symbols are not part of the public interface; they are documented for contributors — the coefficientwise convolution, combination and exponential-kernel bodies, the axis-factored pair that evaluates a separable kernel per mode, and this module's implementations of the two kernel-protocol generics.

GBGPeriodicFields.Convolution._apply_convolution! — Method
_apply_convolution!(destination_data, source_data, kernel_data, α, β)

Apply the coefficientwise spectral product that realizes the periodic convolution in spectral representation, writing $\texttt{dst} \mathrel{.=} \alpha \hat g \cdot \hat f + \beta \texttt{dst}$ ($\texttt{dst}$ the destination_data, $\hat f$ the source_data, $\hat g$ = kernel_data). The scalar kernel_data, of shape (Nx, Ny, Nz), broadcasts over the fiber components of source_data exactly as the Laplacian's $|k|^2$ does, so one body serves every tensor order. The call branches on iszero(β) to overwrite or accumulate. The product is coefficientwise, so it is aliasing-safe: destination_data may be source_data or the kernel.

GBGPeriodicFields.Convolution._apply_separable_convolution! — Method
_apply_separable_convolution!(destination_data, source_data, kernel, α, β)

Apply a SeparableKernel as one broadcast over the whole section, writing $\texttt{dst} \mathrel{.=} \alpha \hat g \cdot \hat f + \beta \texttt{dst}$. The three per-axis factors carry singleton axes, so they broadcast along the remaining mode axes and along the fiber, and one expression serves scalar, vector, and tensor fields exactly as the stored-kernel path does.

The shape is chosen for two measured reasons. Broadcasting indexes the factors cartesian, so no element pays a linear-to-cartesian conversion — an integer division, emulated on a GPU. And the launch stays flat, which keeps it coalesced: the folded axis is $N/2 + 1$ modes long — 129 at $256^3$ — so a three-dimensional launch fragments warps against a row length that is not a multiple of the warp size.

The kernel value is associated as the stored path associates it, so an axis-factored kernel and its materialized product agree bit for bit.
