Convolution

GBGPeriodicFields.Convolution — Module
Convolution

Periodic (circular) convolution of a field with a kernel. On the torus the only convolution is the periodic one, and by the convolution theorem it is exactly a coefficientwise product of the transforms, so the operation lives in spectral representation. A scalar kernel multiplies every fiber component, so one operation serves scalar, vector, and tensor fields. The operation is named convolve (allocating infix ⋆) rather than *, which would read as a pointwise multiplication.

A kernel is not a field. The two hold identical coefficients, so nothing but a type can say which role is meant, and the roles differ: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it (inv), while the same operation on a field is one the package does not define. Every kernel subtypes SpectralKernel, and the four classes below are interchangeable wherever a kernel is applied to a field, differing in cost rather than in meaning. A kernel also serves as a reduction weight in weighted_inner, which is narrower in one respect: it requires a real multiplier.

Physics stays with the calling code: an LES filter, a viscous integrating factor, or a de-aliasing mask is a multiplier the caller supplies — through radial_kernel when it depends on the mode only through $|k|^2$, or as coefficients built from FieldSpectralMultipliers and wrapped in StoredKernel.

The parts are, in three groups — what the module does, how a kernel is stored, and which kernels it builds:

Convolution operations:

  • convolve / convolve! — convolve a field with a kernel; the in-place form adds the $\alpha$/$\beta$ weights on result and destination, and convolve(g₁, g₂) composes two kernels into one.
  • exponential_convolve! / exponential_convolve — convolve with the exponential radial kernel, computed from the wavenumber arrays on the fly instead of stored as a field; the two-operand form filters a weighted combination in the same pass.
  • The kernel-composed combine! method — the weighted combination of two fields convolved with a kernel, in one fused pass.

Kernel storage classes:

  • StoredKernel — one coefficient per mode, the $O(N^3)$ storage, cubic in the points per axis, every other class exists to avoid. It wraps a ScalarFieldSpectral in the kernel role.
  • SeparableKernel — a kernel that factors over the axes, held as its three per-axis factors, so it costs kilobytes rather than a field; the class translation_kernel, tophat_window and assignment_window return.
  • RadialKernel — a kernel depending on the mode only through $|k|^2$, held as the function $\sigma$ computing it (a closure, evaluated per mode), so it stores no coefficients at all; the class spectral_cutoff, spectral_band and radial_kernel return.
  • ProductKernel — any two kernels held unmultiplied, which is what a composition that cannot be collapsed into a single kernel gives: a cross-family pair, two stored kernels, or two radial kernels whose coordinates cannot be shown to agree. It applies in one pass.
  • materialize_kernel — expand a compressed kernel into a StoredKernel, for a caller that wants to inspect or modify the coefficients, and materialize_kernel! to expand it into one that already exists.
  • inv — the reciprocal kernel, which deconvolves by the original. Each class returns its own kind and states the precondition it can afford to check, an annihilated mode having no inverse.

Kernel builders:

  • radial_kernel — build a RadialKernel from any real function $\sigma$ of the squared wavenumber, which is the route for a multiplier this module does not name (a smooth filter, a hyperviscosity, an integrating factor).
  • spectral_cutoff / spectral_band — build the isotropic sharp low-pass kernel and its annular band-pass generalization, both radial kernels.
  • tophat_window — the box average of a chosen width, a separable kernel.
  • assignment_window — the linear (cloud-in-cell) mass-assignment window, a separable kernel, for deconvolving a gridded point density.
  • translation_kernel / translation_kernel! — the separable kernel that translates a field by a physical displacement, the shift theorem's phase.

The verbs below are this module's own. Two further operations reach a kernel through a generic another module owns, and are documented there: combine! has a kernel-composed method — a weighted combination convolved with a kernel in one fused pass — on the FieldAlgebra page, and adapt moves a kernel of any class between storage families as it moves a field, on the Fields page.

GBGPeriodicFields.Convolution.convolve! — Function
convolve!(destination, field, kernel::SpectralKernel)
convolve!(destination, field, kernel::SpectralKernel, α, β)

Convolve field with the kernel whose transfer function is kernel, writing the result into destination in place and returning destination; both field and destination are in spectral representation.

Use this in-place form when destination is already allocated; the allocating convolve returns a fresh result instead.

Arguments

  • field — the field to filter, in spectral representation.
  • kernel — the kernel's transfer function $\hat g$, in any storage class of a SpectralKernel: a StoredKernel holding one coefficient per mode, or one of the compressed classes evaluated per mode (radial, separable, or their product), which costs $O(N)$ or a closure rather than $O(N^3)$. One scalar kernel serves scalar, vector, and tensor fields, and every storage class gives bitwise-identical results on the host, a complex kernel on a device agreeing to rounding instead.
  • destination — the field written with the result; it may alias field or kernel, since the product is coefficientwise.
  • α, β — real accumulation weights, converted to the field's scalar type; the three-argument form overwrites ($\alpha = 1$, $\beta = 0$), the five-argument form computes $\alpha (f \star g) + \beta \texttt{destination}$.

Physically the periodic convolution is the kernel-weighted local average of the field $f$ about each point $x$ — a low-pass filter when the kernel $g$ is a smoothing bump:

\[(f \star g)(x) = \int_\Omega f(y) g(x - y)\,\mathrm{d}y ,\]

with $\Omega$ the periodic box and the displacement $x - y$ reduced onto the torus. On the grid the operation computes the circular sum $(f \star g)[n] = \sum_m f[m] g[n - m]$ (indices modulo the grid) — the integral's Riemann sum without the cell volume $|\Omega|/\prod_i N_i$, box volume over the product of the point counts $N_i$ along the axes, the dimensionless convention that makes a kernel act as a per-mode transfer function ($\hat g \equiv 1$ is the identity; a sharp cutoff is a projection); the continuum integral above is $|\Omega|/\prod_i N_i$ times it. By the convolution theorem (the forward transform unnormalized) the circular sum is exactly the coefficientwise product of the transforms, which this operation computes — $\hat g$ = kernel, broadcast over every fiber component of $\hat f$, with the $\alpha$/$\beta$ accumulate:

\[\widehat{\texttt{destination}}(k) = \alpha \hat f(k) \hat g(k) + \beta \widehat{\texttt{destination}}(k).\]

A real field needs a Hermitian kernel

The stored half-spectrum holds only the modes with a non-negative wavenumber along the folded axis (the layout's fft_dims[1], not necessarily the first physical axis); the rest are implied by the reality of the field, $\hat f(-k) = \overline{\hat f(k)}$. A kernel returns a field that is still real exactly when its own transfer function carries that symmetry, $\hat g(-k) = \overline{\hat g(k)}$ — equivalently, when the physical-space kernel $g$ is real. Every kernel the package builds satisfies it: the real, even ones (spectral_cutoff, spectral_band, assignment_window) trivially, and the complex translation_kernel by construction. A radial_kernel — and so the exponential kernel exponential_convolve! applies — satisfies it too, and for the strongest reason: a real symbol of $\lvert k\rvert^2$ is real, and $\lvert k\rvert^2$ is even in $k$, so the multiplier is real and even whatever the caller's closure computes. A caller-built kernel that breaks the symmetry yields coefficients that are those of no real field, and the inverse transform then silently keeps only their Hermitian part.

Two kernels compose through the allocating form, which allocates nothing

This operation applies a kernel to a field. Composing two kernels into one is convolve(g₁, g₂), and there is deliberately no in-place spelling, because there is nothing for one to save: composition never builds a field of coefficients in any storage class. Two separable kernels compose into their per-axis products, and two radial ones into a single closure when both are built over canonical multipliers — the grid's own wavenumbers, built by the convenience constructor rather than supplied by the caller — of the same concrete type (RadialKernel gives the condition); every other pair — two stored kernels, a cross-family pair, or radial operands failing that test — becomes a ProductKernel holding both factors unmultiplied and evaluating them in a single pass. Composing two stored kernels allocates zero bytes, against the $O(N^3)$ a materialized product would cost, and applying the composite is bitwise-identical to applying the two in sequence. Use materialize_kernel if the coefficients themselves are wanted.

GBGPeriodicFields.Convolution.exponential_convolve! — Function
exponential_convolve!(destination, field, multipliers, coefficient::Real)
exponential_convolve!(destination, field, multipliers, coefficient::Real, α, β)
exponential_convolve!(destination, field, multipliers, coefficient::Real,
                      offset_scale::Real, offset)
exponential_convolve!(destination, field, multipliers, coefficient::Real,
                      offset_scale::Real, offset, α, β)
exponential_convolve!(destination, α::Real, a, β::Real, b, multipliers,
                      coefficient::Real)
exponential_convolve!(destination, α::Real, a, β::Real, b, multipliers,
                      coefficient::Real, offset_scale::Real, offset)

Smooth a field with the periodic heat kernel: convolve it with the exponential radial kernel, optionally times a per-mode exponent field — $\exp(c |k|^2 + s \hat w)$, radial in the $c |k|^2$ part alone — where $c$ is a real coefficient on the squared wavenumber $|k|^2$, and the optional term adds a per-mode real field $\hat w$ supplied by the caller under a real scale $s$. The kernel is evaluated on the fly, never stored as a field, and the result is written into destination in place, which is returned.

Use this in-place form when destination is already allocated; the allocating exponential_convolve returns a fresh result instead.

It acts in spectral representation only.

For a coefficient $c \le 0$ this is, physically, convolution with the periodic Gaussian (heat) kernel: the operator $e^{-c\Delta}$, which smooths the field at the length scale $\sqrt{-2c}$. In spectral representation it is the coefficientwise product with $\exp(c |k|^2)$, the true squared wavenumber kept at the Nyquist frequency (the Laplacian convention), so the kernel is real, even, and positive — a valid kernel for every real field. The optional term $s \hat w$ generalizes the exponent by whatever per-mode field the caller supplies.

Choose between this and a stored kernel by reuse and by rank. When the exponent changes between applications — so a stored kernel would be rebuilt each time — the lazy form wins outright: a rebuild writes a whole field of coefficients that this form never writes, let alone reads, and it reads three one-dimensional wavenumber arrays instead.

For one fixed kernel reused across many calls the two are close, and rank decides, because this form's cost is the exponential it evaluates per mode while a stored kernel's is the coefficient field it streams. On a vector field one exponential serves all three components, so the lazy form runs at $0.88$–$1.03$ of a stored kernel's time at $256^3$–$512^3$, on a GPU and on a threaded CPU alike. On a scalar field it pays one exponential per element and the stored kernel leads — $0.73$–$3.09$ over those sizes, and on a CPU by as much as $20\times$ at $64^3$–$128^3$, where there is too little memory traffic to hide the exponential. Serially the stored kernel leads throughout, and Float32 shifts the balance further toward it, halving its traffic while leaving the exponential unchanged. The two-operand forms fuse the combination into this same pass, removing the combination's destination write and re-read.

On a CPU a deeply damped kernel has one further Float32 cost cliff: modes whose factor lands in the subnormal range — exponent arguments $c \lvert k\rvert^2 + s \hat w$ between about $-103$ and $-87$ — are produced through a hardware assist at roughly $16\times$ the usual per-element cost, so a kernel deep enough to cross that band pays a multiple of its whole pass. The Float64 band (arguments below about $-708$) is beyond any physical kernel, and the GPU backends flush subnormals to zero, so both are unaffected; where the band matters, use Float64 or a milder exponent.

Arguments

  • destination — the field written with the result; it may alias field (or a, b, offset), since the product is coefficientwise.
  • field — the field to filter, in spectral representation.
  • α, β — in the single-operand forms, where they trail the argument list, the usual accumulation weights: the result is written as $\alpha (\text{filtered } f) + \beta \texttt{destination}$.
  • α, a, β, b — in the two-operand forms, where they lead it, the real weights and fields of the combination $\alpha a + \beta b$ the kernel is applied to, exactly as combine! takes them; with b === destination the filtered accumulate runs in place. The two roles never share a signature, which is why one pair of glyphs can serve both.
  • multipliers — the wavenumber arrays for the field's grid; the kernel is evaluated from their squared-wavenumber family.
  • coefficient — the real factor $c$ on $|k|^2$ in the exponent, dimensionless as received (the caller folds its own physical factors before the call).
  • offset_scale, offset — the real scale $s$ and the per-mode values $\hat w$ of the optional exponent term $s \hat w$. The offset is either a scalar field in spectral representation holding real values, or a RadialKernel when $\hat w$ depends on $|k|^2$ alone (a band, for instance), which is evaluated per mode where the exponent is formed and stores nothing; the two give bitwise the same result. The pair enters as scale times values so a changed scale costs nothing.

The single-operand accumulate form computes

\[\begin{aligned} \widehat{\texttt{destination}}(k) &= \alpha \exp\bigl(c |k|^2 + s \hat w(k)\bigr) \hat f(k) \\ &\quad + \beta \widehat{\texttt{destination}}(k), \end{aligned}\]

The two-operand form

Passing α, a, β, b ahead of the multipliers applies the same kernel to a weighted combination, $\exp(c |k|^2 + s \hat w) \cdot (\alpha \hat a + \beta \hat b)$, in one pass — the lazy-kernel twin of the kernel-composed combine! method, and the fusion divergence! and helmholtz_projection! perform when given a trailing kernel. With b === destination it is the filtered accumulate, computed in place.

The offset must be real-valued and even

The exponential of a real, even multiplier keeps a real field real, and both halves of that hypothesis are the caller's to meet. A complex-valued offset breaks the Hermitian symmetry — and so does a real-valued one that is not even in $k$ on the self-conjugate planes, where both members of a $\pm k$ pair are stored and nothing forces them equal. Either way the inverse transform then silently keeps only the Hermitian part, exactly as a caller-built kernel can under convolve!. There is deliberately no scalar exponent offset: a constant $s_0$ in the exponent is $e^{s_0}$ times the kernel and belongs in $α$.

Kernel storage classes

The package holds a kernel in whichever of four forms is cheapest for its multiplier: wrapped in a StoredKernel when the multiplier is arbitrary, as per-axis factors when it separates, as the function computing it when it depends on the wavenumber only through $\lvert k\rvert^2$, or as any two kernels held unmultiplied when a composition cannot be collapsed into one. All four apply identically and agree bitwise on the host; on a device a complex-valued kernel is the one exception, agreeing there to rounding.

They part company in one place. Inversion is a mathematical partial operation — a kernel that annihilates a mode has no inverse there — and a class that cannot afford to test that precondition reports a violation differently from one that can, so inv is where the choice of class shows. It matters most for a sharp cutoff, since spectral_cutoff returns the class that cannot.

The supertype every kernel-taking operation dispatches on is SpectralKernel, documented with Fields.

GBGPeriodicFields.Convolution.StoredKernel — Type
StoredKernel(field::ScalarFieldSpectral)

Wrap a scalar field in spectral representation so that it plays the kernel role — one coefficient per mode, the $O(N^3)$ storage the compressed classes exist to avoid.

The wrapper is required rather than a convenience. A field and a kernel hold identical data, so nothing but a type can say which role is meant, and the two admit different operations: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it (inv), while the same operation on a field is nonlinear in that field's spectral representation and the package does not define it. So a bare ScalarFieldSpectral passed where a kernel is expected does not dispatch — wrap it here, or build the kernel with one of the builders, and the role is then carried by the type rather than inferred from the call site.

Wrapping costs nothing per application: the struct holds a reference, and the fused passes reach the coefficients through it without an extra read. Wrap once, where the kernel is built.

The expansion materialize_kernel returns is this class, so a compressed kernel expanded into its coefficients arrives already in the kernel role.

Fields

  • field — the ScalarFieldSpectral holding the coefficients, referenced rather than copied.

GBGPeriodicFields.Convolution.SeparableKernel — Type
SeparableKernel

A spectral kernel that factors over the axes, $\hat g(k) = \prod_a g_a(k_a)$, stored as its three one-dimensional per-axis factors rather than as a full field. The factors are evaluated into the product one mode at a time, so the kernel never occupies a field's worth of memory: three arrays of $O(N)$ entries in place of $O(N^3)$ coefficients — kilobytes rather than the 129 MiB a $256^3$ kernel would take — and applying it reads no field-sized kernel stream: the three $O(N)$ factors are read per mode, which is the saving, not zero kernel traffic.

There is no public constructor, which is why no signature is shown above: a kernel of this class is always obtained from a builder, so that its per-axis factors match the grid they will be applied on. Build one with translation_kernel (the displacement phase, complex factors) or assignment_window (the mass-assignment window, real factors), and apply it exactly like a kernel held as a field: pass it to convolve! or as the trailing kernel of divergence! or helmholtz_projection!.

Whether that is also faster depends on the grid. Applying it moves two field-sized streams where a stored kernel moves three, but evaluates the product per mode, so it trails a stored kernel on a grid small enough to sit in cache and overtakes it once the pass is bound by memory. On a small grid where the difference matters, materialize_kernel trades the memory back, and its docstring carries the measured crossover. Use inv for the reciprocal kernel $1/\hat g$, which is separable too since $1/\prod_a g_a = \prod_a (1/g_a)$ — the deconvolution an assignment window is built for.

Separable, not radial

A kernel that depends only on the wavenumber magnitude is usually radial, not separable — a general function of $k_1^2 + k_2^2 + k_3^2$ does not factor into per-axis terms, the exponential being the notable exception ($\exp(c|k|^2)$ factors, and has its own operation). This type is for kernels that genuinely do factor, the typical case being a per-axis phase.

Fields

  • factor_1, factor_2, factor_3 — the per-axis factors, each shaped to broadcast along its own axis, of the stored spectral length of that axis (the folded axis is the layout's fft_dims[1]).
  • grid, layout — the base and Fourier layout the factors were built for, which a call checks the field against.

GBGPeriodicFields.Convolution.RadialKernel — Type
RadialKernel

A spectral kernel that depends only on the wavenumber magnitude, $\hat g(k) = \sigma(|k|^2)$, stored as the function $\sigma$ rather than as its values — its symbol, in the sense the differential operators use for the multiplier a coefficientwise operator applies. The function is evaluated one mode at a time from the wavenumber arrays the multipliers already hold, so the kernel occupies no field: a closure and three references, against the $O(N^3)$ coefficients a stored kernel needs — bytes rather than the 129 MiB a $256^3$ kernel would take.

There is no public constructor, which is why no signature is shown above: a kernel of this class is always obtained from a builder, so that the multipliers it evaluates against are the ones its grid owns. Build one with spectral_cutoff or spectral_band for the sharp masks, or with radial_kernel for any other such function — a smooth envelope, a hyperviscous $\exp(-\nu (|k|^2)^p \tau)$ of viscosity, power and time step. Apply it like any kernel: pass it to convolve!, as the trailing kernel of divergence! or helmholtz_projection!, or to weighted_inner as a reduction weight.

Why this family is closed by construction: $|k|^2$ is real and even in every component, so any real $\sigma$ of it is real and even too, hence Hermitian-symmetric — the coefficients it produces are always some real field's. It also carries the true squared wavenumber at an even axis's Nyquist — the value a magnitude-dependent multiplier wants there, unlike the derivative wavenumbers, which are zeroed at that mode — so no case analysis is needed anywhere in the family.

Storing no coefficients is not the same as costing nothing

The symbol is evaluated per mode, and against a field of tensor order $R \ge 1$ it is broadcast over the field's components, so it is evaluated once per component rather than once per mode; at $R = 0$ there is no fiber to extrude over and nothing extra to pay. Whether that recompute or the kernel-array traffic it saves dominates depends on the base and on the element type.

At $64^3$ and $R = 1$ the radial route costs $1.1$–$2.1\times$ a materialized StoredKernel across the CPU thread counts measured; by $256^3$–$512^3$ the saved traffic has overtaken the recompute on most of them, at $0.70$–$0.97$. A device is not exempt: in Float64 it runs at $0.85$–$1.10$, but in Float32, where halving the stored kernel's traffic leaves the symbol's cost untouched, the radial route is slower at every size on one of the two GPUs, by as much as $2.6\times$ at $128^3$. Hoisting the evaluation was prototyped and measured, and was declined because it lost at the sizes that matter; materialize_kernel is the escape wherever the recompute wins.

Radial, not separable

$|k|^2 = k_1^2 + k_2^2 + k_3^2$ is a function of the sum, so a general real symbol of it does not factor into per-axis terms and cannot be stored per axis the way a SeparableKernel is. The two families overlap rather than partition: the exponential is in both, since $\exp(c|k|^2) = \prod_a \exp(ck_a^2)$, which is why exponential_convolve! exists as its own fused operation. What this class buys is the general case, where no such factorization is available.

Fields

  • sigma — the function $\sigma$, called with the real $|k|^2$ and returning a real value.
  • multipliers — the FieldSpectralMultipliers supplying $|k|^2$, referenced, not copied. Whether they are the grid's own wavenumbers (canonical, built by the convenience constructor from the grid) or a caller's own (supplied through the explicit constructor, which validates lengths and not values) is part of their type, and it decides whether composing two of these kernels collapses into one: two kernels over canonical multipliers of the same type hold the same coordinates by construction and merge, while a kernel over a caller's own coordinates keeps both operands as a ProductKernel, since one composite can carry only one set of coordinates.
  • grid, layout — the base and Fourier layout the kernel was built for, which a call checks the field against.

GBGPeriodicFields.Convolution.ProductKernel — Type
ProductKernel

The coefficientwise product of two spectral kernels, held as the pair rather than evaluated — what convolve returns whenever composing cannot produce a single kernel more cheaply. There is no public constructor, which is why no signature is shown above: one arises only from that composition. That covers every cross-family pair, two stored kernels (merging those would mean materializing an $O(N^3)$ product), and two radial kernels whose coordinates cannot be shown to agree.

Composition inside a family usually stays in that family: two axis-factored kernels always multiply into one axis-factored kernel, and two radial symbols multiply into one radial symbol when both are evaluated against the same coordinates, which RadialKernel explains and decides by type. Radial operands that fail that test land here instead. Across families there is no collapse at all: a radial symbol times an axis-factored phase is neither radial nor separable, so the composite keeps both operands and multiplies their per-mode values. Either order composes and gives the same operator, the product being coefficientwise, and a composite composes further in either position. It still stores nothing of field size, and it applies exactly like either operand.

This is what lets a mask and a displacement — or any radial symbol and any per-axis factor — be applied in a single pass instead of two.

Fields

  • first_kernel, second_kernel — the two operands, held unmultiplied and evaluated per mode.

inv(kernel::RadialKernel)

The reciprocal kernel $1/\sigma(|k|^2)$, formed by composing the reciprocal with $\sigma$, so it is another RadialKernel and still costs no storage.

inv(kernel::SeparableKernel)

The reciprocal kernel $1/\hat g$, itself separable because $1/\prod_a g_a = \prod_a (1/g_a)$ — so it is formed per axis, at $O(N)$ cost, with no field materialized. Applying it deconvolves by kernel, which is what a mass-assignment window is built for (assignment_window).

The factors must have no zeros, and this method checks

Every per-axis factor must be non-zero at every stored mode. Unlike the radial method, this one can afford to verify it — the factors are $O(N)$ — so a zero throws rather than returning a non-finite reciprocal. An assignment_window satisfies the condition on every stored mode, whereas a phase kernel does not in general (a displacement can drive an even axis's Nyquist factor to zero).

inv(kernel::StoredKernel)

The coefficientwise reciprocal of a kernel held as a field, which is the kernel that deconvolves by it.

A kernel with a zero coefficient annihilates that mode, so no kernel undoes it and this throws rather than returning a non-finite coefficient. The check is a full pass over the coefficients, which an explicit inversion can afford; the axis-factored SeparableKernel method checks its $O(N)$ factors instead, and the radial method documents the precondition it cannot test cheaply.

GBGPeriodicFields.Convolution.materialize_kernel! — Function
materialize_kernel!(destination::StoredKernel,
                    kernel::SpectralKernel) -> destination

Evaluate a kernel into storage that already exists: every coefficient of destination is overwritten with the kernel's value $\hat g(k)$ at that mode, and destination is returned.

Use this in-place form when destination is already allocated; the allocating materialize_kernel returns a fresh result instead. The destination is a StoredKernel sharing the grid, Fourier layout, element type and storage family of kernel, which may be of any of the four storage classes of a SpectralKernel; a mismatch is refused. The evaluation allocates nothing, so a field-sized kernel is written without a second field-sized temporary. A caller holding a field it means to fill wraps it once as StoredKernel(field), which references the field rather than copying it.

The cost is one pass over the modes, the same as the allocating form's without the allocation, and the warning on materialize_kernel about giving up a compressed kernel's memory saving applies to whatever the destination is then used for.

materialize_kernel(kernel::SeparableKernel)

Evaluate an axis-factored kernel into a kernel held as a field, returning the StoredKernel whose coefficients are the product of the per-axis factors. The result applies identically and, for real factors, gives bit-identical results — the two differ only in what they cost. Complex factors agree bitwise on the host and to rounding on a device.

Use this to trade memory back for speed on a small grid. Applying an axis-factored kernel moves two field-sized streams where a stored kernel moves three, but evaluates the product per mode; which wins depends on the grid. Measured against a stored kernel on a vector field: threaded on a CPU the axis-factored form costs $1.75$–$2.45\times$ a stored kernel at $64^3$, is mixed at $128^3$ ($0.83$–$2.11$, Float32 still behind), and overtakes by $256^3$–$512^3$ at $0.72$–$0.95$. Single-threaded it never overtakes in this range. On a device the answer depends on the card: of the two measured, one crosses ($1.37$ at $64^3$ falling to $0.88$ at $256^3$ in Float64) while the other does not, staying $1.20$–$2.53\times$ at every size and element type measured. So a run whose grids are small, or which applies one fixed kernel very many times with memory to spare, can materialize once and keep the field; a threaded run at production resolution should not, and pays a field of residency for nothing if it does (129 MiB at $256^3$, against about 10 KiB for the factors).

This gives up the memory saving entirely

The returned field costs the full $O(N^3)$ the axis-factored form exists to avoid. Materialize deliberately, for a measured reason on a specific grid — not by default.

Kernel builders

Each returns a kernel for a multiplier the package names, in whichever storage class that multiplier admits — and each signature says which class, since that is what determines the cost of applying it: radial_kernel, spectral_cutoff and spectral_band give a RadialKernel (a closure); tophat_window, assignment_window and translation_kernel give a SeparableKernel (three $O(N)$ factors). The escape hatch is radial_kernel, taking any other real function of $\lvert k\rvert^2$.

GBGPeriodicFields.Convolution.radial_kernel — Function
radial_kernel(sigma, multipliers::FieldSpectralMultipliers) -> RadialKernel

Build the RadialKernel for an arbitrary real function of the squared wavenumber — its symbol, in the sense the differential operators use — the general constructor behind spectral_cutoff and spectral_band, for the multipliers the package does not name.

Here sigma is a function of one real argument — the squared wavenumber $|k|^2$ — returning a real value, and it must be pure and GPU-safe: it may capture only values, never a type, since a closure holding a Type is not a bitstype and a device rejects it at launch, and it may hold no mutable state and do no scalar indexing of device arrays. Anything it does capture by value, such as a viscosity or a substep, is free to vary per call, because building a kernel allocates nothing of field size. The multipliers are the FieldSpectralMultipliers supplying $|k|^2$, and whose grid, Fourier layout, element type and storage family the kernel takes as its own.

The physics stays with the caller: an integrating factor is radial_kernel(k2 -> exp(-ν * k2 * Δt), …), a smooth filter its own envelope. Because the function is evaluated per mode rather than stored, a kernel whose parameters change every call costs nothing to rebuild, where a stored kernel pays a full field write. That evaluation is per mode, so on a CPU at a small grid a field of order $R \ge 1$ pays it once per fiber component; RadialKernel carries the measured trade-off against a materialized kernel.

GBGPeriodicFields.Convolution.spectral_cutoff — Function
spectral_cutoff(multipliers::FieldSpectralMultipliers,
                wavenumber_cutoff::Real) -> RadialKernel

Build an isotropic sharp low-pass kernel, returned as a RadialKernel — the function itself rather than its coefficients, so it costs no field of storage. The evaluation is per mode, so on a CPU at a small grid an $R \ge 1$ field pays it once per fiber component — see RadialKernel for the measured trade-off against a materialized kernel. Use materialize_kernel to expand it into a StoredKernel. It is built on the multipliers' grid and storage family: the transfer function is $1$ for $|k| \le k_c$ and $0$ above it.

Convolve a field with it for the ideal low-pass projection, the basis of spectral truncation and de-aliasing. It is idempotent ($\hat g^2 = \hat g$), hence a projection, and it is the low-pass special case of spectral_band with $k_\mathrm{lo} = 0$.

Here multipliers is the FieldSpectralMultipliers whose grid, Fourier layout, element type and storage family the kernel takes as its own, and wavenumber_cutoff is the cutoff wavenumber $k_c$ — a mode is kept when $|k| \le k_c$.

\[\hat g(k) = \mathbf{1}\bigl[ |k| \le k_c \bigr].\]

The choice of cutoff, such as a $2/3$ de-aliasing rule or an LES filter scale, is the caller's. The squared wavenumber $|k|^2$ keeps the true value at the Nyquist frequency (the Laplacian convention).

GBGPeriodicFields.Convolution.tophat_window — Function
tophat_window(multipliers::FieldSpectralMultipliers, width::Real) -> SeparableKernel
tophat_window(multipliers::FieldSpectralMultipliers,
              width::NTuple{3, Real}) -> SeparableKernel

Return the top-hat (box-average) window of a given width as a SeparableKernel, its three per-axis factors on the multipliers' grid and storage family: convolving a field with it replaces the field at each point by its mean over the box of that width centred there.

Use it to average a field over sub-boxes smaller than the domain — the scale-resolved statistics that remove a sub-box mean, such as the kinetic energy held in scales below a given size, or a box filter of chosen width. The returned w is the window's transfer function $\hat W$; the weights those statistics need are its square, convolve(w, w), which composes per axis at no extra cost.

Here multipliers is the FieldSpectralMultipliers whose grid, Fourier layout, element type and storage family the window takes as its own, and width is the edge of the box in the units of the domain: one number for a cube, or one per axis for a rectangular box. Each edge must be finite and non-negative, and a zero edge leaves that axis unfiltered.

As a real physical object the window is the normalized indicator of the box, the tensor product of per-axis top-hats, and the returned transfer function is its product of per-axis sincs:

\[\begin{gathered} W(x) = \prod_{a=1}^{3} \frac{1}{l_a} \mathbf{1}\bigl[|x_a| \le \tfrac{l_a}{2}\bigr], \\ \hat W(k) = \prod_{a=1}^{3} \operatorname{sinc}\Bigl(\tfrac{k_a l_a}{2}\Bigr), \\ \operatorname{sinc}(y) = \frac{\sin y}{y}, \end{gathered}\]

with $l_a$ the box edge along axis $a$, $x_a$ the displacement along it reduced onto the periodic domain, and $k_a$ the true wavenumber component, kept at the Nyquist frequency so a real field stays real. On a periodic domain the width may be any non-negative number: at $l_a$ equal to the domain's extent every nonzero wavenumber along that axis is cancelled to rounding, so a box the size of the domain keeps the mean alone, and as $l_a \to 0$ that axis's factor tends to one. The assignment_window is this window at the grid spacing, squared.

It averages the band-limited field, not the grid values

The sinc is the transform of the continuum box, so the result is the exact box mean of the band-limited field the grid values represent, even for an edge of a whole number of cells: it is not the mean of the nodes inside the box. That field can itself exceed the range of its grid values, and so can its box mean, where a mean of grid values could not.

GBGPeriodicFields.Convolution.assignment_window — Function
assignment_window(multipliers::FieldSpectralMultipliers) -> SeparableKernel

Return the linear (cloud-in-cell) mass-assignment window — assignment in the particle-mesh sense of depositing a point's mass onto the grid cells around it, not the sense of writing a value into an array — as a SeparableKernel — its three per-axis factors rather than a field of coefficients — on the multipliers' grid and storage family, for deconvolving a gridded point density.

Use it when a pair correlation is estimated from points deposited on a grid rather than counted directly. Depositing $M$ points on the grid with the positive linear assignment (LalescuSpline(0, 0) — the two-point linear "tent" transfer kernel, the smoothness $m = 0$ member of the Interpolation spline family) spreads each point's mass over a tent, so the gridded density is the true density $\rho$ convolved with this window, $\rho_g = \rho \star W$. Dividing the transform by $\hat W$ — a convolve by $1/\hat W$ — undoes that smearing before you estimate the radial distribution function $g(r)$ (the pair density at separation $r$ relative to an uncorrelated uniform gas).

Here multipliers is the FieldSpectralMultipliers whose grid, Fourier layout, element type and storage family the window takes as its own.

As a real physical object $W$ is the linear B-spline ("tent") cloud, the tensor product of per-axis tents:

\[W(x) = \prod_{a=1}^{3} \frac{1}{\Delta x_a} \max\Bigl(0, 1 - \frac{|x_a|}{\Delta x_a}\Bigr),\]

each a tent of half-width one cell $\Delta x_a$ along axis $a$, of unit integral — the tophat_window at the grid spacing convolved with itself, hence the squared sinc. It returns its transfer function $\hat W(k)$, the squared sinc

\[\begin{gathered} \hat W(k) = \prod_{a=1}^{3} \operatorname{sinc}^2\Bigl(\tfrac{k_a \Delta x_a}{2}\Bigr), \\ \operatorname{sinc}(y) = \frac{\sin y}{y}, \end{gathered}\]

computed from the per-axis wavenumber $k_a$ (kept at the Nyquist frequency) and the grid spacing $\Delta x_a$, so $\hat W(0) = 1$ and it decays toward the grid scale. Because the squared sinc does not vanish at any wavenumber the grid resolves, dividing by it is stable. Stable is not exact: $\hat W$ is the transform of the continuum tent, while a grid deposit applies that transform plus the aliasing sum over the periodic images of $k$, so the division undoes the smearing only up to that aliasing — trust the band well below the Nyquist frequency. The package supplies the window; the density estimate and the correlation normalization stay with the caller.

References

  • R. W. Hockney, J. W. Eastwood, Computer Simulation Using Particles, Adam Hilger, Bristol, 1988 (deposition / charge assignment; the NGP and CIC windows).

GBGPeriodicFields.Convolution.translation_kernel — Function
translation_kernel(multipliers::FieldSpectralMultipliers,
                   offset::NTuple{3, Real}) -> SeparableKernel

Build the kernel that translates a field by the physical displacement $h$ = offset, returned as a SeparableKernel on the multipliers' grid and storage family: convolving a field $f$ with it gives the displaced field $f(x - h)$, the position $x$ reduced onto the periodic box.

Use it to move a field onto a displaced grid without re-gridding — a shift-and-average filter, the relocation of a probe, or the displaced evaluation of a phase-shift de-aliasing scheme. Apply it with convolve / convolve!, which is allocation-free in place; because a scalar kernel multiplies every fiber component, one call translates a whole vector or tensor field, and because the kernel depends on nothing but the displacement, one kernel serves every field it is applied to (and it is separable, so building it costs three $O(N)$ axis passes, not a field). To sample the field at the displaced positions $x + h$ instead, pass the negated offset — the two are inverse translations. This is the package's one complex kernel: on every sub-Nyquist mode it is a pure phase of unit modulus, so it moves the field without touching any amplitude, unlike the real and even spectral_cutoff or assignment_window. At the Nyquist frequency — the highest wavenumber a grid stores, $\pi/\Delta x_a$, which an even-length axis stores as a single self-conjugate mode — the factor is instead the real number $\cos(\pi h_a / \Delta x_a)$, which attenuates rather than translates and vanishes at a half-cell shift — the reality condition demands it, and the warning below gives the detail.

Here multipliers is the FieldSpectralMultipliers whose grid, Fourier layout, element type and storage family the kernel takes as its own, and offset is the displacement $h = (h_1, h_2, h_3)$ — a physical length per axis in the units of the box rather than a count of cells, so a half-cell displacement is 0.5 .* grid.grid_spacing on the Grid3D the field lives on.

As a real physical object the translation is the convolution with a Dirac delta displaced to $h$ and periodized on the box, $g = \delta(x - h)$, whose sifting property (integrating against a delta evaluates the integrand at the delta's location) gives $(f \star g)(x) = f(x - h)$ exactly. On the grid that $g$ is the band-limited (periodic-sinc) interpolation stencil centred at $h$, so the convolution re-samples the trigonometric interpolant of $f$ at the displaced nodes $x - h$, and collapses to a plain index shift when $h$ is a whole number of cells. Its transfer function $\hat g$ at wavenumber $k$ is the shift theorem's phase, assembled per axis from that wavenumber's component $k_a$ and the displacement $h_a$ along the axis:

\[\hat g(k) = \prod_{a=1}^{3} \bigl[ \cos(k_a h_a) - \mathrm{i} \sin(a_a h_a) \bigr],\]

where $k_a$ is the true wavenumber and $a_a$ the Nyquist-zeroed derivative one — the package's two families, and the reason this is written with two symbols rather than as the bare phase $e^{-\mathrm{i} k \cdot h}$. The two coincide on every resolved mode — so the factor there is that pure phase — and part only at an even axis's Nyquist frequency, where the warning below applies.

At the Nyquist frequency the phase becomes a real attenuation

On an even-length axis the Nyquist mode of a real field carries a single real amplitude that stands for both of the wavenumbers $\pm\pi/\Delta x_a$ (with $\Delta x_a$ the grid spacing along axis $a$), so its band-limited form is the cosine $\cos(\pi x_a/\Delta x_a)$, and displacing that cosine re-samples on the grid to $\cos(\pi h_a/\Delta x_a)$ times itself. At that one frequency the kernel therefore carries this real factor rather than a complex phase — and it has to be real: the Nyquist mode is its own conjugate partner, so a complex factor there would leave coefficients that are those of no real field at all. A displaced Nyquist mode is thus attenuated rather than moved: it vanishes for a half-cell displacement and changes sign for an odd whole-cell one. Two consequences follow, both confined to that frequency: the translation is not invertible there (displacing by $h$ and back scales the mode by $\cos^2$), and two translations compose exactly on every resolved mode but not at Nyquist. Whole-cell displacements are exact everywhere, and a field with no Nyquist content — one truncated by a de-aliasing cutoff — never meets the caveat at all.

GBGPeriodicFields.Convolution._apply_separable_convolution! — Method
_apply_separable_convolution!(destination_data, source_data, kernel, α, β)

Apply a SeparableKernel as one broadcast over the whole section, writing $\texttt{dst} \mathrel{.=} \alpha \hat g \cdot \hat f + \beta \texttt{dst}$. The three per-axis factors carry singleton axes, so they broadcast along the remaining mode axes and along the fiber, and one expression serves scalar, vector, and tensor fields exactly as the stored-kernel path does.

The shape is chosen for two measured reasons. Broadcasting indexes the factors cartesian, so no element pays a linear-to-cartesian conversion — an integer division, emulated on a GPU. And the launch stays flat, which keeps it coalesced — neighbouring threads reading neighbouring addresses, which a GPU serves as one wide transaction. The folded axis is $N/2 + 1$ modes long, half its point count plus one (129 at $256^3$), so a three-dimensional launch would cut each row against a length that is not a multiple of the warp — the group of threads a GPU issues in lockstep, 32 on NVIDIA and 64 on AMD — leaving every row's last transaction partly idle.

The kernel value, the axis factors in order, is associated as the stored path does, $\alpha((\sigma_1\sigma_2)\sigma_3)\hat f$, so a real-factored kernel and its materialized product agree bitwise. A complex-factored one can differ by an ulp on a device: the compiler contracts the $ac - bd$ of a complex multiply into a fused multiply-add, differently when the product is inlined here than when a stored kernel rounds it to memory first.
