GBGPeriodicFields.Fields — Module
Fields

Field representation and transform core for scalar, vector, and second-order tensor fields on three-dimensional rectangular periodic domains, for CPU and GPU array backends. A field is a physical object, and the physical-space and spectral types (for example ScalarFieldPhysical and ScalarFieldSpectral) are two representations of the same field.

The parts are:

  • Grid and layout — Grid3D describes the periodic domain geometry, and RealFourierLayout describes the real-to-complex transform layout.
  • Field types — the scalar, vector, and second-order tensor field types each come in a physical-space and a spectral representation. The two lowest orders carry their own names, ScalarFieldPhysical and VectorFieldPhysical; higher orders are TensorFieldPhysical{R} / TensorFieldSpectral{R}. The tensor order R is a type parameter of every field type.
  • Persistence — write_field and read_field map a field to and from one self-describing HDF5 group (methods load with the HDF5 package, as a weak-dependency extension).
  • Transforms — FieldTransformPlans holds the FFT plans, and to_physical and to_spectral move a field between the two representations. The allocating forms preserve their input, and the plain in-place ! forms may overwrite the source — except the four-argument scratch arity of to_physical!, which guarantees preservation by consuming a caller-supplied scratch instead; set_fft_threads! sets the thread count FFTW bakes into plans built afterwards.
  • Spectral multipliers — FieldSpectralMultipliers holds the wavenumber arrays the differential operators apply as spectral multipliers.
  • Spectral kernels — SpectralKernel is the supertype of every coefficientwise multiplier a convolve-style operation can apply, whatever storage it uses — including the stored class, which wraps a field of coefficients. It lives here, rather than with the kernels themselves, so every module that accepts one names a single type; Convolution defines the concrete classes.
  • Allocation — similar_field returns uninitialized storage carrying a reference field's representation, tensor order, grid and backend, which is how an operation builds scratch or a result without naming a concrete field type.
  • The reality condition — reality_residual measures how far a spectrum is from a real field's, and reality_projection! projects it onto one, on the two stored self-conjugate planes where the half-spectrum can disagree with itself.
  • Moving between grid resolutions — embed_modes! writes a coarser field's Fourier modes into a finer field over the same box and extract_modes! reads them back, each leaving the destination's other modes untouched and costing the coarse field rather than the fine one. Amplitudes are physical, so the pair are exact adjoints of each other.
  • Moving between storage families — adapt moves a field, its multipliers, its kernels or its transform plans between host and device arrays (or any other Adapt.jl storage family), preserving the element type and everything else the object carries. Operations refuse a pair that disagrees rather than transferring one to meet the other, so that the cost of crossing the bus is always visible at the call site.
  • Broadcasting — a dotted assignment writes into the destination's storage, an out-of-place dotted expression allocates a like field in the same representation, and physical and spectral representations cannot be mixed in one broadcast.

Uniform three-dimensional grid for a periodic rectangular domain.

The grid is uniform, so the spacing is not independent: it must equal domain_size ./ grid_size along every axis. The two-argument constructor computes it and is the one to prefer; the four-argument form checks what it is handed and throws an ArgumentError on a spacing that contradicts the domain. Every grid size must be positive, every domain length finite and positive, and every origin coordinate finite.

Arguments

  • grid_size — the number of grid points along each axis, each positive.
  • domain_size — the length of the periodic box along each axis, each finite and positive.
  • grid_spacing — the four-argument form only: the spacing between adjacent points, which must equal domain_size ./ grid_size.
  • origin — the physical coordinates of the first grid point, each finite: positional in the four-argument form, a keyword defaulting to zero in the two-argument form.

Fields

  • grid_size::NTuple{3, Int} — the number of grid points in each spatial direction.
  • domain_size::NTuple{3, T} — the length of the domain in each spatial direction.
  • grid_spacing::NTuple{3, T} — the spacing between adjacent grid points in each spatial direction. Stored rather than recomputed, but not independent — it must equal domain_size ./ grid_size, which the four-argument constructor enforces.
  • origin::NTuple{3, T} — the physical coordinates of the first grid point.

GBGPeriodicFields.Fields.RealFourierLayout — Type
RealFourierLayout()
RealFourierLayout(fft_dims::NTuple{3, Int})

Layout convention for three-dimensional real-to-complex Fourier transforms.

The main role of the ordering is to specify the real-FFT half dimension: in dimension fft_dims[1], only the nonnegative frequencies are represented, while the other dimensions use the full complex FFT frequency ordering.

The zero-argument constructor uses fft_dims = (1, 2, 3).

Fields

  • fft_dims — the tuple of transformed dimensions passed to the FFT planner, whose first entry is the halved (folded) axis.

GBGPeriodicFields.Fields.AbstractFieldPhysical — Type
AbstractFieldPhysical{T, R}

Abstract supertype for fields represented by values in physical space.

Here T<:AbstractFloat is the real scalar type associated with the field and R is the tensor order stored as an integer value parameter. Concrete subtypes provide the actual storage and metadata. The generic field interface obtains T and R through field_scalar_type and field_tensor_order, and obtains the stored data through field_data.

A field in physical representation owns its storage

A concrete subtype's constructor rejects borrowed storage — a SubArray anywhere in the parent chain — so slicing a larger preallocated buffer and wrapping the view will throw. Ownership is what makes an aliased in-place call safe (FieldAlgebra). Allocate with similar_field, or copy the slice. Any owning array is accepted: Array, CuArray, ROCArray, or a reshape of one.

The function constructor constructs a scalar field in physical representation by sampling a real-valued function on a three-dimensional physical grid.

Arguments

  • grid — the Grid3D the values are sampled on.

Fields

  • values_at_grid — the real scalar values, one per grid point.
  • grid — the Grid3D on which the values are sampled.

  family::Type{<:AbstractArray},
  grid::Grid3D{T},
  layout::RealFourierLayout = RealFourierLayout();
  fft_flags = nothing,
  fft_timelimit = Inf,
) where {T<:AbstractFloat}

Forward and inverse FFT plans connecting compatible fields represented in physical and spectral space.

Arguments

  • physical — a field in physical representation, supplying the grid, the layout and the storage family; its values are never read or written.
  • spectral — a field in spectral representation on the same grid and layout, likewise only a template.
  • family, grid, layout — in place of the two fields: the storage family (Array, CuArray, ROCArray), the Grid3D and the RealFourierLayout, defaulting to the standard one. This form needs no fields at all, the plans being built on one-component arrays of their own either way.
  • fft_flags — an optional backend-specific FFT planner flag.
  • fft_timelimit — the planner time limit, used when fft_flags is given.

Only the spatial dimensions, the layout's fft_dims, are transformed; tensor-fiber dimensions are left untransformed.

The plans are backend-, array-type- and scalar-type-specific, and carry no tensor order: a real Fourier transform on a periodic box is defined on the box, and a rank-$R$ field is that transform applied along a fiber, so one pair of plans serves scalar, vector and tensor fields alike. Construct a separate FieldTransformPlans object for each CPU/GPU backend and element type, but not for each tensor order.

The default `ESTIMATE` planner can badly mis-plan single-precision CPU transforms

On the CPU the plans are FFTW plans, and with fft_flags unset FFTW picks the algorithm by its built-in ESTIMATE heuristic — instant, but a guess. On some CPUs that guess is far off: measured on a Zen 5 desktop, the Float32 transforms ran 2.3–5.1× slower than a timed plan at $256^3$ (the widest gap single-threaded, narrowing as threads are added), and at $512^3$ still slower than Float64 serially and at two threads, the gap closing (and reversing) only as more threads are added. For a long CPU run, pass fft_flags = FFTW.MEASURE (or FFTW.PATIENT): the one-time timed plan search costs seconds and removes the guess. MEASURE overwrites the arrays it plans on, which are one-component arrays the constructor allocates itself, so the caller's fields are untouched. The setting is CPU-specific — the GPU FFT libraries take no planner flag and are unaffected — and the default stays ESTIMATE because it is instant, deterministic, and right for tests and short sessions.

Fields

  • grid::G — the Grid3D for which the plans were constructed.
  • fourier_layout::L — the RealFourierLayout for which the plans were constructed.
  • plan_forward_fft::PF — the plan transforming physical values to spectral coefficients, for one component.
  • plan_inverse_fft::PI — the plan transforming spectral coefficients to physical values, for one component.
  • fft_flags::Union{Nothing, UInt32} — the planner flag these plans were built with, or nothing for the default. It is retained rather than merely used, so that rebuilding these plans in another storage family can replay the intent they were created with — see adapt.
  • fft_timelimit::Float64 — the planner time limit paired with fft_flags, retained for the same reason.
  • component_scratch::S — a component-sized buffer, or nothing. It exists only where a device backend would refuse a component's starting address, and is nothing for every grid whose component offsets align — which includes every grid a solver is likely to run.

Moving between storage families

Host and device are storage families, not representations: a field has both, and they vary independently — the representation says whether its values are the field or its Fourier coefficients, the family says which kind of array holds them. Moving between families is Adapt.jl's verb, extended here for every section, kernel and plan and re-exported, so a consumer needs nothing beyond using GBGPeriodicFields; and because it dispatches on a generic target, CUDA and AMDGPU each supply their own storage rule without this package depending on either. Whether a CUDA array sits in device or unified memory is a CUDA.jl setting rather than a different family; Running on a GPU explains it.

Adapt.adapt — Function
adapt(storage, object)

Move a section — a field or point-values — or its multipliers, its kernels, its point set or its transform plans to another storage family, host to device or device to host, returning an object of the same kind whose arrays live in the requested family. The element type is preserved exactly.

A storage family is the kind of array holding the values — Array on the host, or one vendor's device array. Use this when something built on one family has to be used on another. Two fields combine arithmetically only when they share a family and an element type, and a mixed pair is refused rather than promoted or transferred, because a copy across the bus is a cost that belongs at the call site; adapt is that call site. The argument storage is the target array type (Array, CuArray, ROCArray, …) or any other Adapt.jl adaptor, and object is what to move — a field or point-values (the sections), or one of the companions a section is useless without: multipliers, a kernel, or transform plans.

The whole surface a solver needs is covered: the six field types, the point-value types, a PointSet, a FieldSpectralMultipliers, the four spectral-kernel classes (StoredKernel, SeparableKernel, RadialKernel and ProductKernel, all subtypes of SpectralKernel), and FieldTransformPlans. Everything the moved object carries besides its storage — the grid, the Fourier layout, the origin, the tensor order — is preserved by construction, since it is rebuilt through the same allocator the package uses everywhere else.

Element-type conversion is deliberately not part of this: a transfer that silently changed precision would change what a solver computes. No operation in this package converts precision today.

Examples

u_device      = adapt(CuArray, u)                 # host  -> device
u_host        = adapt(Array, u_device)            # device -> host
mult_device   = adapt(CuArray, multipliers)       # must share the field's family
plans_device  = adapt(CuArray, plans)             # rebuilt on the device
Moving to the family an object is already in returns it unchanged

Following Adapt.jl and convert, adapting to the family an object already belongs to is the identity: it returns the very same object, sharing storage, rather than a copy. Write copy when a distinct object is what is wanted.

Transform plans are rebuilt, not moved, and that costs a planning pass

An FFT plan is a compiled schedule tied to one storage family and cannot be transferred, so adapting a FieldTransformPlans constructs new plans on the target. It needs nothing from the caller: the plans carry their own grid, layout and element type — and no tensor order — so the two arrays the planner needs as witnesses are allocated internally and released immediately. The planner request the plans were built with is replayed, with one exception. Planner flags are an FFTW concept — cuFFT rejects them outright — so a move to any non-host family does not apply them when building the new plan, but the returned plans still record the original flags, so a later move back to the host rebuilds them with the intent they were created with.

Moving between grid resolutions

Two spectral fields over the same box whose grids differ in size name the same Fourier modes where they overlap, because a grid of N points over a domain of length L resolves 2π/L times the integers it stores. These two verbs move exactly those shared modes, leaving the rest of the destination untouched, at a cost set by the coarser field — the mode-space counterpart of the storage-family crossing above, and the route by which content computed on a small grid reaches a large one without a transform. Amplitudes are physical: the ratio of the two grids' point counts is applied inside, so the two are exact adjoints of each other.

This writes exactly those, which is how content computed cheaply on a small grid — a forcing, a prescribed initial condition — reaches a large one without a transform. The cost is the coarse field's size. Use extract_modes! for the other direction.

Reading them back with extract_modes! returns what was written, and the two verbs are exact adjoints of each other under inner.

A mode at the coarse grid's Nyquist frequency on an even axis describes one sampled wave that the finer grid splits into two distinct modes, so the single coarse coefficient does not determine them. The real-field reality condition

GBGPeriodicFields.Fields.reality_residual — Function
reality_residual(field::AbstractFieldSpectral) -> Real

Measure how far a field's coefficients are from being the spectrum of a real field, returning 0 exactly when they are one.

A real field's spectrum satisfies $\hat f(-k) = \overline{\hat f(k)}$, and the real-to-complex layout exploits that by storing only half the modes — so for most of them the redundant partner is not stored and cannot disagree. Two planes are the exception: the folded axis's zero plane, and its Nyquist plane when that axis has even length, are each their own mirror image, so within them both partners are stored and the constraint becomes a relation between entries that a caller can break. This returns the largest such discrepancy,

\[\max \bigl\lvert \hat f(k) - \overline{\hat f(-k)} \bigr\rvert,\]

over those planes and every fiber component. A mode that is its own partner — the corners where each axis sits at zero or, on an even-length axis, at Nyquist; eight of them when all three axes are even, fewer when an axis is odd and so has no Nyquist plane — must be real, and this reports twice its imaginary part, that being the same discrepancy applied to a self-paired entry.

The residual is in the units of the stored coefficients, which the forward transform leaves unnormalized: a Fourier mode of physical amplitude $a$ is stored with magnitude about $a M$, $M$ the number of grid points, not $a$. So judge it against the field's largest stored coefficient, not against a physical amplitude.

Reach for it where responsibility for the coefficients changes hands: after writing or accepting them — and after any step that scales the coefficients in place, because a spectrum built by transforming a real field satisfies the constraint only to round-off (FFTW is exact at some power-of-two sizes and ulp-level elsewhere; rocFFT and cuFFT are ulp-level at every size), and a forcing proportional to the field amplifies that residual where viscosity does not damp it. The projection reality_projection! removes it exactly. The cost is one or two planes, $O(N^2)$, per-axis count squared, not the $O(N^3 \log N)$ of the round trip below.

It reports rather than repairs, so the caller decides; the repair is reality_projection!, an explicit verb costing the same one or two planes. A physical round trip — to_physical followed by to_spectral — also projects, since the inverse real transform discards what no real field has, but it costs two transforms, perturbs every mode by round-off, and resets this residual only to the transform's own floor, the forward pass reseeding it.

The Nyquist plane is reported, never zeroed

Some codes symmetrize by zeroing the Nyquist planes outright. This does not: the package keeps Nyquist content and treats the two wavenumber families as disagreeing there on purpose, so a violation on that plane is named like any other and what to do about it stays the caller's.

GBGPeriodicFields.Fields.reality_projection! — Function
reality_projection!(destination::AbstractFieldSpectral,
                    source::AbstractFieldSpectral) -> destination
reality_projection!(field::AbstractFieldSpectral) -> field

Project a field's coefficients onto the spectrum of a real field, so that reality_residual of the result is exactly zero — the reality-condition twin of helmholtz_projection!.

In physical space nothing visible changes: the inverse real transform already discards the part of the coefficients that no real field has, so the image of field is unchanged. What changes is the stored spectrum. The real-to-complex layout stores both members of a conjugate pair only on the folded axis's zero plane and, for an even-length axis, its Nyquist plane; there the condition $\hat f(-k) = \overline{\hat f(k)}$ is a relation a caller — or a library's round-off — can break, and this replaces each stored pair by its projection,

\[\begin{aligned} \hat f(k), \hat f(-k) \leftarrow{} &\tfrac{1}{2} \bigl( \hat f(k) + \overline{\hat f(-k)} \bigr), \\ &\overline{\tfrac{1}{2} \bigl( \hat f(k) + \overline{\hat f(-k)} \bigr)}, \end{aligned}\]

with a self-paired corner mode reduced to its real part by the same formula. Every other coefficient is untouched. This is the orthogonal projector onto real-field spectra in the Parseval inner product: linear, exactly idempotent, and it commutes with every per-mode multiplier $m$ satisfying $m(-k) = \overline{m(k)}$ — the differential operators, the exponential and radial kernels, the translation phases.

Reach for it where round-off on those planes is amplified, not damped. A spectrum freshly transformed from real data satisfies the condition only to round-off, and a solver whose forcing is proportional to the field grows that round-off exponentially; projecting once per step where the state is deposited removes it exactly, which a physical round trip does not, since the forward transform reseeds it. The physical representation has no method: there the projection is the identity.

The destination may be the source, and the one-argument form projects in place; the cost is then one or two planes, $O(N^2)$, per-axis count squared. With a distinct destination the whole source is copied first, so that form costs a field copy, $O(N^3)$, before the projection — the same shape as the two-argument helmholtz_projection!, kept so the twins read alike, but not the cheap one. The two fields must share a grid, layout, tensor order, element type and storage family, and a mismatch is refused rather than converted.

Removing the mean

GBGPeriodicFields.Fields.mean_free_projection! — Function
mean_free_projection!(field::AbstractFieldSpectral) -> field

Remove a field's mean exactly, in place: the orthogonal projector onto fields of zero mean, the companion of reality_projection! and of helmholtz_projection!.

In physical space it subtracts the average over the domain $\Omega$ from every component,

\[f(x) \leftarrow f(x) - \frac{1}{\lvert\Omega\rvert} \int_\Omega f(y) \, \mathrm{d}y,\]

and in spectral representation that is setting the zero Fourier coefficient $\hat f(0)$ of every fiber component to zero, both its real and imaginary parts, leaving every other coefficient untouched. The physical representation has no method. There the mean occupies no single stored value, so the projection is a pass over the whole field, which subtract!(field, field, mean(field)) already is.

Spectral kernel protocol

The kernel-taking operations dispatch on SpectralKernel, each accepting all four storage classes: convolve, the kernel-composed differential operators, and weighted_inner — the last subject to the separate requirement that its weight be real.

GBGPeriodicFields.Fields.SpectralKernel — Type
SpectralKernel{T}

Supertype of every spectral kernel: a coefficientwise multiplier applied as the product $\hat f \hat g$ of a field's coefficients $\hat f$ and the kernel's own multiplier $\hat g$, in whichever storage its symbol admits. Convolution defines the concrete classes under Kernel storage classes — StoredKernel holding one coefficient per mode, SeparableKernel holding per-axis factors, RadialKernel holding the symbol itself, and ProductKernel holding two factors unmultiplied — and they differ only in cost, never in meaning. This supertype and the two generics below live here so that every module which applies a kernel — Convolution, DifferentialOperators, Reductions — can name one type, whichever of them is included first.

A field in spectral representation is not a kernel. The two hold identical data, so nothing but a type can say which role is meant, and the distinction is load-bearing: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it, while the same operation on a field is one the package does not define. Wrap a field of coefficients in StoredKernel to declare the role, which is what materialize_kernel returns.

A concrete kernel implements two methods: _kernel_data, returning the multiplier it contributes per mode, and _check_kernel_compatibility, checking it against the field it is applied to.

HDF5 persistence

GBGPeriodicFields.Fields.write_field — Function
write_field(parent::HDF5.H5DataStore, name::AbstractString, field::AbstractField)

Persist field — any of the six field types, scalar / vector / tensor in either representation — as a new HDF5 group name under parent, returning the group it created. Use it to checkpoint a field for restart, save a full-resolution snapshot for later analysis, or pass a field to another tool; the reload with read_field is exact.

The group is self-describing: the field's numeric array becomes the dataset data, and its metadata become attributes — a type tag, a schema version, a representation tag ("physical" or "spectral"), the Grid3D geometry (grid_size, domain_size, origin), the Fourier layout (fft_dims), the element type, and the tensor order — so any HDF5 tool can read it. A physical field stores a real array; a field in spectral representation stores its complex half-spectrum. A host array is written directly, without a copy, and a device (GPU) array is copied to the host on write. The sugar parent[name] = field is equivalent.

Because parent is a handle you opened and own, this never opens or closes a file: a caller bundles a whole snapshot (velocity, vorticity, …) into one file under separate names and attaches its own time / iteration attributes — the package serializes the fields, and the caller owns the bundling and any notion of time.

Arguments

  • parent — an open HDF5 File or Group to create the new subgroup under.
  • name — the name of the group to create.
  • field — the field to write.

Provided by a package extension, so it is available only when HDF5.jl is loaded.

GBGPeriodicFields.Fields._check_shared_mode_compatibility — Method

GBGPeriodicFields.Fields._project_pair! — Method
_project_pair!(data, ix, iy)

GBGPeriodicFields.Fields._refuse_field_as_fiber_map — Method
_refuse_field_as_fiber_map(φ)

Refuse a field handed to a fiber-map slot, and do nothing for anything else.

A field in physical representation is callable — f(x) samples it at a position — so passing one where map!/map expect the fiber map φ type-checks and runs. What it then computes is nonsense of the worst kind: for a vector source the fiber is an SVector{3}, which the callable happily reads as a position, so the call silently interpolates the field at its own source's values and returns a plausible number.
