Fields

GBGPeriodicFields.Fields — Module
Fields

Field representation and transform core for scalar, vector, and second-order tensor fields on three-dimensional rectangular periodic domains, for CPU and GPU array backends. A field is a physical object, and the physical-space and spectral types (for example ScalarFieldPhysical and ScalarFieldSpectral) are two representations of the same field.

The parts are:

  • Grid and layout — Grid3D describes the periodic domain geometry, and RealFourierLayout describes the real-to-complex transform layout.
  • Field types — the scalar, vector, and second-order tensor field types each come in a physical-space and a spectral representation (higher orders exist as TensorFieldPhysical{R} / TensorFieldSpectral{R}).
  • Persistence — write_field and read_field map a field to and from one self-describing HDF5 group (methods load with the HDF5 package, as a weak-dependency extension).
  • Transforms — FieldTransformPlans holds the FFT plans, and to_physical and to_spectral move a field between the two representations. The allocating forms preserve their input, while the in-place ! forms may overwrite the source; set_fft_threads! sets the thread count FFTW bakes into plans built afterwards.
  • Spectral multipliers — FieldSpectralMultipliers holds the wavenumber arrays that the spectral differential operators multiply by.
  • Spectral kernels — SpectralKernel is the supertype of every coefficientwise multiplier that is not stored as a field. It lives here, rather than with the kernels themselves, so every module that accepts one names a single type; Convolution defines the concrete classes.
  • Allocation — similar_field returns uninitialized storage carrying a reference field's representation, tensor order, grid and backend, which is how an operation builds scratch or a result without naming a concrete field type.
  • Broadcasting — a dotted assignment writes into the destination's storage, an out-of-place dotted expression allocates a like field in the same representation, and physical and spectral representations cannot be mixed in one broadcast.

Uniform three-dimensional grid for a periodic rectangular domain.

The fields are

  • grid_size::NTuple{3, Int}: the number of grid points in each spatial direction.
  • domain_size::NTuple{3, T}: the length of the domain in each spatial direction.
  • grid_spacing::NTuple{3, T}: the spacing between adjacent grid points in each spatial direction.
  • origin::NTuple{3, T}: the physical coordinates of the first grid point.

The grid is uniform, so the spacing is not independent: it must equal domain_size ./ grid_size along every axis. The two-argument constructor computes it and is the one to prefer; the four-argument form checks what it is handed and throws an ArgumentError on a spacing that contradicts the domain, since a grid whose stored spacing disagrees with its domain would silently mislocate every interpolated point rather than fail. The comparison is a floating-point tolerance, so a spacing computed by a different but equivalent route is accepted. Every grid size must be positive, every domain length finite and positive, and every origin coordinate finite.

GBGPeriodicFields.Fields.RealFourierLayout — Type
RealFourierLayout()
RealFourierLayout(fft_dims::NTuple{3, Int})

Layout convention for three-dimensional real-to-complex Fourier transforms.

The main role of the ordering is to specify the real-FFT half dimension: in dimension fft_dims[1], only the nonnegative frequencies are represented, while the other dimensions use the full complex FFT frequency ordering.

The zero-argument constructor uses fft_dims = (1, 2, 3).

The fields are

  • fft_dims: the tuple of transformed dimensions passed to the FFT planner, whose first entry is the halved (folded) axis.

AbstractField

Either representation of a field: the union of AbstractFieldPhysical and AbstractFieldSpectral.

It names the argument type of the operations that do not care which representation they are handed — the grid, layout, element-type and tensor-order accessors, and the compatibility checks. Transform-plan and multiplier types

GBGPeriodicFields.Fields.FieldTransformPlans — Type
FieldTransformPlans(
  physical::AbstractFieldPhysical{T, R},
  spectral::AbstractFieldSpectral{T, R};
  fft_flags = nothing,
  fft_timelimit = Inf,
) where {T<:AbstractFloat, R}

Forward and inverse FFT plans connecting compatible fields represented in physical and spectral space.

The arguments are:

  • physical: the field supplying the real-space storage array to plan against.
  • spectral: the field supplying the real-to-complex Fourier coefficient array.
  • fft_flags: an optional backend-specific FFT planner flag.
  • fft_timelimit: the planner time limit, used when fft_flags is given.

Only the spatial dimensions field_layout(physical).fft_dims are transformed; tensor-fiber dimensions are left untransformed.

CPU planner choice: the default `ESTIMATE` can badly mis-plan single-precision transforms

On the CPU the plans are FFTW plans, and with fft_flags unset FFTW picks the algorithm by its built-in ESTIMATE heuristic — instant, but a guess. On some CPUs that guess is far off: measured on a Zen 5 desktop, the Float32 transforms ran 3.4–5.4× slower than a timed plan at $256^3$, and at $512^3$ no faster than Float64, in both directions and at every thread count. For a long CPU run, pass fft_flags = FFTW.MEASURE (or FFTW.PATIENT): the one-time timed plan search costs seconds and removes the guess. MEASURE overwrites both reference arrays while planning, so construct the plans on scratch or zero-filled fields before seeding data. The setting is CPU-specific — the GPU FFT libraries take no planner flag and are unaffected — and the default stays ESTIMATE because it is instant, deterministic, and right for tests and short sessions.

The fields are

  • grid::G: the Grid3D for which the plans were constructed.
  • fourier_layout::L: the RealFourierLayout for which the plans were constructed.
  • plan_forward_fft::PF: the plan transforming physical values to spectral coefficients.
  • plan_inverse_fft::PI: the plan transforming spectral coefficients to physical values.

The plans are backend-, array-type-, scalar-type-, and tensor-order-specific; construct a separate FieldTransformPlans object for each CPU/GPU backend and field tensor order.

GBGPeriodicFields.Fields.FieldSpectralMultipliers — Type
FieldSpectralMultipliers(
  grid::Grid3D{T},
  fourier_layout::RealFourierLayout,
  wavenumber_1, wavenumber_2, wavenumber_3,
  squared_wavenumber_1, squared_wavenumber_2, squared_wavenumber_3,
) where {T<:AbstractFloat}

FieldSpectralMultipliers(
  field::AbstractFieldSpectral{T},
  wavenumber_1, wavenumber_2, wavenumber_3,
  squared_wavenumber_1, squared_wavenumber_2, squared_wavenumber_3,
) where {T<:AbstractFloat}

One-dimensional Fourier wavenumber arrays for coefficientwise spectral operators such as derivatives, the Laplacian, and the Helmholtz projection.

The fields are

  • grid, fourier_layout: the Grid3D and RealFourierLayout the multipliers were built for.
  • wavenumber_1, wavenumber_2, wavenumber_3: the per-axis physical (angular) wavenumbers $k$ along each axis, used for first derivatives via multiplication by $\mathrm{i} k$.
  • squared_wavenumber_1, squared_wavenumber_2, squared_wavenumber_3: per-axis squared wavenumbers, used for the Laplacian via multiplication by $-k^2$.

Each array runs along one spatial axis in the FFT frequency ordering of fourier_layout; the half axis fourier_layout.fft_dims[1] stores only the nonnegative frequencies. The arrays must live on storage (CPU or GPU) matching the fields the multipliers are applied to.

These two constructors are explicit: you supply both the wavenumbers and the squared wavenumbers, and only their lengths are checked. The two array families are stored independently rather than squaring one to obtain the other, because on even grids they use different conventions for the Nyquist mode (the highest representable frequency). A convenience constructor FieldSpectralMultipliers(field) builds both families from the field's grid and layout with the correct Nyquist treatment;

Whether the arrays were derived from the grid or supplied by the caller is recorded in the type, as a final Canonical parameter: the convenience constructor marks them canonical, the explicit forms do not. It is in the type rather than in a field because it decides, statically, whether two multiplier sets provably hold the same coordinates — two canonical sets on a matching grid and layout are derived the same way from the same inputs, so they agree by construction. That is what lets convolve collapse two radial kernels into one without testing anything at run time, and it is why a caller supplying its own coordinates (a sheared, time-dependent set, say) never has its kernels merged with one built on the grid's own wavenumbers. it carries its own docstring.

GBGPeriodicFields.Fields.FieldSpectralMultipliers — Method
FieldSpectralMultipliers(field::AbstractFieldSpectral{T}) where {T<:AbstractFloat}

Build the spectral multipliers from the grid and Fourier layout of field, allocated on the field's storage backend.

The wavenumbers are the physical angular wavenumbers $k = 2\pi n / L$ along each axis, where $L$ is the domain length and $n$ runs over the FFT frequency indices. On an even-length axis the highest stored mode is the Nyquist mode: its first-derivative wavenumber is set to zero, so that derivatives of real fields stay real, while its squared wavenumber keeps the true $k^2$, so that the Laplacian and Poisson-type solves stay correct. On an odd-length axis there is no exact Nyquist mode and no special treatment is applied.

Transform a field from spectral space to physical space in place, returning the modified physical destination.

Here physical is the destination, spectral is the source, and transform_plans provides the inverse FFT plan.

The source is used as scratch

The inverse transform uses spectral as scratch space and may overwrite it: on return its coefficients are left in an undefined state (the FFTW CPU backend destroys them — complex-to-real transforms have no input-preserving algorithm in the multidimensional case; some GPU backends happen to preserve them, but this is not guaranteed). Use the allocating to_physical when spectral must be preserved.

Spectral kernel protocol

SpectralKernel is the supertype every kernel-taking operation dispatches on. It is defined here rather than in Convolution because DifferentialOperators also takes kernels and is included first, so the protocol has to precede both consumers. The concrete classes that subtype it, and the builders returning them, are documented with Convolution.

GBGPeriodicFields.Fields.SpectralKernel — Type
SpectralKernel{T}

Supertype of every spectral kernel: a coefficientwise multiplier applied as the product $\hat f \hat g$, in whichever storage its symbol admits. Convolution defines the concrete classes under Kernel storage classes — StoredKernel holding one coefficient per mode, SeparableKernel holding per-axis factors, RadialKernel holding the symbol itself, and ProductKernel holding two factors unmultiplied — and they differ only in cost, never in meaning. This supertype and the two generics below live here so that every module which applies a kernel — Convolution, DifferentialOperators, Reductions — can name one type, whichever of them is included first.

A field in spectral representation is not a kernel. The two hold identical data, so nothing but a type can say which role is meant, and the distinction is load-bearing: the coefficientwise reciprocal of a kernel is the kernel that deconvolves by it, while the same operation on a field is one the package does not define. Wrap a field of coefficients in StoredKernel to declare the role, which is what materialize_kernel returns.

A concrete kernel implements two methods: _kernel_data, returning the multiplier it contributes to a fused pass, and _check_kernel_compatibility, checking it against the field it is applied to.

HDF5 persistence

Serialize a field to, and reconstruct it from, an HDF5 file — for checkpoint/restart, or to dump a full-resolution snapshot for later analysis. Provided by a package extension, so these are available only when the HDF5 package is loaded; the core carries no HDF5 dependency. Each field becomes one self-describing HDF5 group, and the consumer owns the file — every method takes an open File or Group, so a whole iteration snapshot (several fields, plus the consumer's own time and iteration attributes) goes into one file.

GBGPeriodicFields.Fields.write_field — Function
write_field(parent::HDF5.H5DataStore, name::AbstractString, field::AbstractField)

Persist field — any of the six field types, scalar / vector / tensor in either representation — as a new HDF5 group name under parent, returning the group it created. Use it to checkpoint a field for restart, save a full-resolution snapshot for later analysis, or pass a field to another tool; the reload with read_field is exact.

The group is self-describing: the field's numeric array becomes the dataset data, and its metadata become attributes — a type tag, a schema version, a representation tag ("physical" or "spectral"), the Grid3D geometry (grid_size, domain_size, origin), the Fourier layout (fft_dims), the element type, and the tensor order — so any HDF5 tool can read it. A physical field stores a real array; a field in spectral representation stores its complex half-spectrum. A device (GPU) array is copied to the host on write. The sugar parent[name] = field is equivalent.

Because parent is a handle you opened and own, this never opens or closes a file: a consumer bundles a whole snapshot (velocity, vorticity, …) into one file under separate names and attaches its own time / iteration attributes — the package serializes the fields, and the consumer owns the bundling and any notion of time.

The arguments are:

  • parent — an open HDF5 File or Group to create the new subgroup under.
  • name — the name of the group to create.
  • field — the field to write.

Provided by a package extension, so it is available only when HDF5 is loaded.

source
GBGPeriodicFields.Fields.read_field — Function
read_field(parent::HDF5.H5DataStore, name::AbstractString)

Reconstruct the field written by write_field from the HDF5 group name under parent, dispatching on the stored type attribute to return the reconstructed field in the matching type (ScalarFieldPhysical, VectorFieldSpectral, …). The reload is exact — the array data, the Grid3D geometry, the Fourier layout, the element type, and the tensor order are recovered bit-for-bit.

The reconstructed field is a host (CPU) object regardless of where the written one lived; move it to a device afterward if needed.

Here parent is an open HDF5 File or Group holding the group, and name is the name (or path) of that field group under parent.

Provided by a package extension, so it is available only when HDF5 is loaded.

GBGPeriodicFields.Fields._squared_wavenumber_broadcast — Method
_squared_wavenumber_broadcast(multipliers::FieldSpectralMultipliers)

Return the total squared wavenumber $|k|^2 = k_1^2 + k_2^2 + k_3^2$ as a lazy Broadcasted over the three per-axis squared-wavenumber vectors (reshaped to the three spatial dimensions). Used by the Laplacian, inverse Laplacian, and Helmholtz projection.

Lazy on purpose: returning the unfused Broadcasted lets callers compose it into their own broadcasts over the coefficients $\hat s$ of a field in spectral representation ($-|k|^2 \hat s$, $\hat s_i - k_i k_j \hat s_j / |k|^2$, …) without ever materializing the $O(N^3)$ array. That keeps those operators allocation-free in place: no $O(N^3)$ $|k|^2$ scratch is built, which on the GPU would otherwise accumulate in the memory pool on each call.
