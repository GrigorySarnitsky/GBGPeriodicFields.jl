Points

GBGPeriodicFields.Points — Module
Points

The unstructured base of the package's fiber-bundle model: off-grid sample positions and the field values sampled at them. A point set plays the role the grid plays in Fields, and point values are sections over it.

The parts are:

  • Positions. Point is a single coordinate triple, and PointSet holds M positions in a structure-of-arrays layout. A point set carries no grid; a periodic domain wraps any coordinate, so the grid is supplied by the transfer operator at use time.

  • Point-value sections. ScalarPointValues, VectorPointValues, and TensorPointValues, gathered under AbstractPointValues, mirror the field tensor orders. They are representation-free, because a sampled value is always a physical-space quantity.

  • A full fiberwise algebra on the point values. Addition, real scaling, scalar multiplication and division, dot, cross, mul!, transpose, norm, the tr and det invariants, and the sym/skew/dev decompositions form the same physical surface the fields carry, together with the arbitrary-fiber-map escape hatch map!/map — see FieldAlgebra for each operation, documented once there. The algebra reuses the shared FiberSections formula builders and fused values functions over the point-value section interface, so no per-component formula is written twice.

  • Base-space motion. displace! moves the points themselves along coefficient-weighted vector sections — in unwrapped coordinates, or, given a Grid3D, landing back in the periodic box in the same fused pass — and wrap! reduces positions to their canonical in-box representatives. The one family that couples base and fiber; positions deliberately have no + with point values.

  • Allocation. similar_pointvalues returns uninitialized storage carrying a reference's tensor order and backend — the point-value twin of similar_field, and what the broadcast machinery and the allocating algebra wrappers build their results with.

  • Persistence. write_points and read_points map a point set or a point-value section to and from one self-describing HDF5 group, positions and values kept separate (methods load with the HDF5 package, as a weak-dependency extension). They are the point-layer twins of write_field/read_field.

  • Moving between storage families. adapt moves a PointSet or any point values between host and device memory, exactly as it moves a field; the operation is documented once, with its field methods, in Fields.

The grid-to-point transfer (interpolation) and its adjoint (anterpolation) live in the Interpolation module.

Point and point-set types

GBGPeriodicFields.Points.Point — Type
Point{T} = SVector{3, T}

A single position in the domain, stored as a coordinate triple. Point is the base-space analog of FiberVector: it shares the SVector{3,T} representation but plays a different role, naming a location rather than a field value. It is a type alias rather than a wrapper, so arithmetic on positions stays StaticArrays-native and the position-versus-value distinction is one of role, not of dispatch.

source
GBGPeriodicFields.Points.PointSet — Type
PointSet(coordinates::AbstractArray{T, 2}) where {T<:AbstractFloat}

A collection of M off-grid positions, stored structure-of-arrays so that each coordinate axis is contiguous across points, mirroring the fiber-last field layout. Storage is backend-generic: the array may live on the CPU (Array) or a GPU (CuArray/ROCArray). A point set carries no grid, because a periodic domain wraps any coordinate; a transfer operator takes the grid from the field it acts on.

The fields are

  • coordinates — the positions, an AbstractArray of shape (M, 3) — point index first, coordinate axis last — whose second axis must have length 3.

Point-value types

GBGPeriodicFields.Points.AbstractPointValues — Type
AbstractPointValues{T<:AbstractFloat, R}

Abstract supertype for field values sampled at the M positions of a PointSet. The parameter T is the real scalar type, and R is the tensor order, an integer value parameter. Point values are representation-free: a sampled value is always a physical-space quantity, so there is no physical/spectral distinction here, unlike the field types. The concrete subtypes are ScalarPointValues at tensor order 0, VectorPointValues at order 1, and TensorPointValues at order 2 and above.

A section owns its storage

Every constructor here — and PointSet's — rejects borrowed storage, a SubArray anywhere in the parent chain, so wrapping a view into a larger buffer will throw. Ownership is what makes aliasing safe by construction: two sections can then share memory only by being the same array. Allocate with similar_pointvalues, or copy the slice. Any owning array is fine — Array, CuArray, ROCArray, or a reshape of one.

source

Point-value allocation

GBGPeriodicFields.Points.similar_pointvalues — Function
similar_pointvalues(reference::AbstractPointValues, data)
similar_pointvalues(reference::AbstractPointValues, ::Val{R}) where {R}

Allocate point values shaped like reference. The data form wraps the supplied array in a point-value type of the same tensor order as reference. The Val{R} form allocates a fresh (M, fiber_shape(Val(R))...) array of order R on reference's backend, through similar, and wraps it. The broadcast machinery and the allocating algebra wrappers use it to build their results.

Deliberately not an extension of `Base.similar`

The reasoning is similar_field's: Base.similar's second argument means an element type or dimensions rather than a tensor order, similar(q, Float32) would read as a precision change the package never makes implicitly, and the data form wraps supplied storage rather than allocating.

Point-value algebra

The point values carry the same fiberwise algebra as fields in physical representation, through the very same generics — add!, subtract!, multiply!, divide!, dot!, cross!, mul!, transpose!, norm!, tr!, det!, the sym/skew/dev decompositions, and the arbitrary-fiber-map map!/map — extended here to accept AbstractPointValues. A PointSet and any point values also move between storage families through adapt, documented with its generic on the Fields page. (The combine! combination is deliberately absent, and for the no-consumer reason rather than a mathematical one: the weighted combination is linear and coefficientwise, so it would be perfectly well defined on point-values. It exists on fields because a solver's stage updates are the one place the fused axpby saves a whole pass over a field; nothing asks it of the point layer, so it is unbuilt rather than invalid — the package declines speculative structure, and this absence is that rule at work rather than a mathematical restriction a user could rely on.) There is no second set of docstrings for them: each per-component formula is generated from one builder shared with FieldAlgebra, so the operations are documented once, on the FieldAlgebra page. Point values are representation-free, so the surface mirrors the physical field surface only — there is nothing spectral to mirror.

Base-space motion

Displacement moves the points themselves — the one operation family that couples the base and the fiber, where the algebra above maps sections to sections and never moves a point. Each point is carried along the weighted sum of vector values over it; without a grid the motion happens in unwrapped coordinates, and with a grid it lands back in the periodic box in the same fused pass. There is deliberately no + between a PointSet and a VectorPointValues — positions are locations, not vectors — and no allocating sibling, displacement being motion of an existing base.

GBGPeriodicFields.Points.displace! — Function
displace!(destination::PointSet, source::PointSet, terms...)
displace!(destination::PointSet, source::PointSet, grid::Grid3D, terms...)
displace!(points::PointSet, [grid::Grid3D,] terms...)

Move each point of a point set along the weighted sum of vector values over it: writing $x_p$ for the position of point $p$ and $v_j(p)$ for the value the $j$-th section holds at that point,

\[x_p \leftarrow x_p + \sum_j c_j v_j(p) .\]

Each element of terms is a tuple (coefficient, section): the $j$-th term supplies one host scalar $c_j$ — a single number, applied to every point, not a per-point array — and one VectorPointValues section $v_j$, which does hold one vector per point. The subscript $j$ counts the terms of the call, so a two-term call has $c_1, c_2$ and $v_1, v_2$. All terms are applied in one fused traversal: the positions are read once, each section once, and the positions written once, on CPU and GPU alike. This is the one operation that crosses the position-versus-value role split, and it is a named operation rather than a + method because positions are points of the periodic domain, not vectors: what is being applied is a displacement, exact because the domain is flat and the fiber carries one global frame.

Without a grid the sum is taken literally, in the universal cover — the unwrapped picture of the torus, in which a coordinate keeps growing instead of folding back: coordinates may leave the box, and sampling such positions remains correct because the transfer kernels wrap their stencil indices periodically. With a grid the displaced coordinates are additionally reduced, componentwise and in the same fused pass, to the canonical representative in the fundamental domain — the same reduction wrap! applies on its own, whose docstring states the endpoint and non-finite contract. Displacement on the periodic domain proper is the grid form; the grid-free form is its lift to the cover, which preserves winding information (a mean-square-displacement diagnostic needs the unwrapped trajectory).

The arguments are:

  • destination — the PointSet receiving the displaced positions. It may be the source itself (the two-argument convenience forms are exactly that call): the pass reads each element's inputs before writing its outputs, so the aliased call is computed directly.
  • source — the PointSet holding the starting positions. When omitted, points is both source and destination.
  • grid — optional; a Grid3D supplying the periodic domain. Only its domain_size and origin enter: the wrap needs the box, not the mesh.
  • terms... — zero or more (coefficient, section) tuples, each pairing one real number with one section. The coefficients are part of what the operation is — the displacement $\sum_j c_j v_j$ — so they are named coefficients rather than the α/β accumulation scalars of invariant 10, and there is no trailing α/β pair. With no terms the call copies (and, with a grid, wraps) the source positions.

There is deliberately no allocating sibling: displacement is motion of an existing base, and a freshly allocated destination would have no consumer. Sections and point sets must agree in point count, scalar type and storage family; a mixed pair is refused, never converted.

GBGPeriodicFields.Points.wrap! — Function
wrap!(points::PointSet, grid::Grid3D)

Reduce every position to its canonical representative in the periodic domain: componentwise,

\[x_{p,a} \leftarrow \operatorname{mod}(x_{p,a} - o_a,\ L_a) + o_a ,\]

which lands each coordinate in the half-open fundamental domain $[o_a, o_a + L_a)$, where $L_a$ is the domain extent along axis $a$ and $o_a$ the domain origin — both read from grid, whose mesh plays no role. Wrapping is never required for sampling — the transfer kernels wrap their stencil indices, so interpolation is invariant under shifting any coordinate by whole periods — but it is the operation that keeps coordinates bounded over a long run (absolute floating-point resolution degrades as a coordinate grows, single precision especially) and that presents in-box positions to a consumer bucketing by cell index. It discards winding: a mean-square-displacement diagnostic must run on unwrapped positions, which is why displacement and wrapping are separate operations rather than one.

The endpoint is folded, and non-finite coordinates pass through non-finite

Floating-point mod can return exactly $L_a$ for a coordinate a hair below the origin (measured: mod(-1e-20, 2π) === 2π), so the excluded endpoint is folded back to $o_a$ explicitly. The fold tests equality rather than order, because an order test is false for NaN and Inf and would silently rewrite a diverged trajectory into a tidy in-box position — a non-finite coordinate comes out non-finite (an infinity as NaN, mod's own image of it), never boxed.

The reduction runs in place and returns points. The domain's element type must match the point set's; a mixed pair is refused, never converted. To wrap in the same pass as a displacement, use the grid form of displace!.

HDF5 persistence

Serialize a PointSet or a point-value section to, and reconstruct it from, an HDF5 file — the point-layer twin of the field pair on the Fields page, for checkpointing the unstructured base and its samples. Provided by a package extension, so these are available only when the HDF5 package is loaded; the core carries no HDF5 dependency. Each object becomes one self-describing HDF5 group, and the consumer owns the file. Positions and values are written separately, because they are separate objects — a base, and sections over it — which also lets several value sets share one stored set of positions.

GBGPeriodicFields.Points.write_points — Function
write_points(parent::HDF5.H5DataStore, name::AbstractString, points::PointSet)
write_points(parent::HDF5.H5DataStore, name::AbstractString,
             values::AbstractPointValues)

Persist a point object — a PointSet of positions, or any of the three point-value types — as a new HDF5 group name under parent, returning the group it created. Use it to checkpoint the unstructured base and its samples for restart, or to hand them to another tool; the reload with read_points is exact. It is the point-layer twin of write_field, which persists a field.

The group is self-describing: the numeric array becomes the dataset data, and the metadata become attributes — a type tag, a schema version, the element type, the point count, and, for point values, the tensor order — so any HDF5 tool can read it. A device (GPU) array is copied to the host on write. The sugar parent[name] = points is equivalent.

Positions and values are written separately, one group each, because they are separate objects: a PointSet is the base, and point values are sections over it. A consumer that wants them together writes both under one parent group, which also lets several value sets share one stored set of positions.

Because parent is a handle you opened and own, this never opens or closes a file, and the package attaches no notion of time — the consumer bundles a snapshot and owns any time / iteration attributes.

The arguments are:

  • parent — an open HDF5 File or Group to create the new subgroup under.
  • name — the name of the group to create.
  • points, values — the PointSet or point-value section to write.

Provided by a package extension, so it is available only when HDF5 is loaded.

GBGPeriodicFields.Points.read_points — Function
read_points(parent::HDF5.H5DataStore, name::AbstractString)

Reconstruct the point object written by write_points from the HDF5 group name under parent, dispatching on the stored type attribute to return it in the matching type (PointSet, ScalarPointValues, VectorPointValues, TensorPointValues). The reload is exact — the array data, the element type, the point count, and the tensor order are recovered bit-for-bit. It is the point-layer twin of read_field.

The reconstructed object is a host (CPU) one regardless of where the written one lived; move it to a device afterward if needed.

Here parent is an open HDF5 File or Group holding the group, and name is the name (or path) of that group under parent.

Provided by a package extension, so it is available only when HDF5 is loaded.

Internal API

These symbols are not part of the public interface; they are documented for contributors — the point-value broadcast style, the compatibility checks the algebra routes through, the shape and unwrapping helpers, and the base-space motion internals of decision 73 — the coefficient conversion, the fused displacement expression, the per-axis terms and the single-coordinate wrap. (The section-interface accessors the FieldAlgebra builders reuse — field_data and the component accessors — are extended here but owned by Fields, so they are documented on that page.)

Types

GBGPeriodicFields.Points.PointValuesBroadcastStyle — Type
PointValuesBroadcastStyle{N}

Broadcast style for point values, where N is one plus the tensor order — 1, 2, or 3 for the (M,), (M, 3) and (M, 3, 3) storage layouts at tensor orders 0, 1 and 2, and one more dimension for each order above that. Inside a broadcast a point-value object stands for its storage array, and this style materializes the result back into a point-value object of the same order.

GBGPeriodicFields.Points._check_combinable — Method
_check_combinable(values...)

Check that point-value operands may be added or subtracted: equal point count, tensor order and scalar type, throwing otherwise.

A vector-space combination is only defined between sections of the same bundle, and the broadcast that implements it is not fussy enough to say so. Two failures followed, both order-dependent, which is the tell that no operation was being expressed. Mixed precision NARROWED toward the first operand, so a32 + a64 silently truncated a Float64 operand while a64 + a32 did not. Mixed tensor order was accepted in one order — a scalar broadcast across a vector's fiber — and rejected in the other, so + was not commutative; and adding a scalar section to a vector one is not in the method set for fields either.

GBGPeriodicFields.Points._displacement_rhs — Method
_displacement_rhs(base, terms...)

Fold the displacement terms into one lazy broadcast expression $\texttt{base} + \sum_j c_j v_j$ — the argument base is a coordinate array (or a lazy expression over one) and each element of terms is a (coefficient, data) tuple whose parts are already converted and unwrapped. The recursion keeps the term count in the type domain, so the fused pass specializes per arity and allocates nothing. The public methods name the vararg count N in their signatures because Julia does not specialize an unbounded Vararg that is only forwarded — the same trap as the forwarded-Function spelling pinned in test/allocations.jl — and without it a three-term call boxed per element.
