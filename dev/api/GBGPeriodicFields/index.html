GBGPeriodicFields

GBGPeriodicFields carries real-valued scalar, vector and second-order-tensor fields on three-dimensional rectangular periodic domains, in physical-space and real-to-complex spectral representations, on CPU and GPU backends, with HDF5 field persistence.

The tensors are Cartesian — components on one fixed right-handed orthonormal frame, with no curvilinear coordinates or metric machinery — so this is an applied field toolkit rather than a general differential-geometry package.

These words recur in every operation's documentation:

  • a base is the set of locations a value is attached to: a Grid3D of nodes, or a PointSet of off-grid positions. A grid cell carries the quadrature weight a reduction integrates against; the values themselves sit on the nodes.
  • a fiber is the value at one such location — a scalar, a FiberVector, or a FiberTensor2.
  • a section puts the two together: it assigns one fiber to every point of a base, which is what a field and a set of point-values each are, and why one set of formulas serves both.
  • the resolved band is the set of wavenumbers a grid's resolution actually represents, excluding the Nyquist frequency of each even-length axis. Those planes are excluded because there the wavenumbers used for first derivatives are zeroed while the squared ones used for the Laplacian keep the true value — so every identity scoped "on the resolved band" holds off them and may fail on them. An odd-length axis has no exact Nyquist mode and so loses nothing.
  • a field is band-limited when its Fourier content vanishes above the wavenumbers the grid stores, so the finite trigonometric series those coefficients define represents it exactly. A product of two such fields is not band-limited, which is why the operations that form one are offered in physical representation only.
  • a section's scalar type is its real precision — the T <: AbstractFloat every field and point-value type is parameterized on, Float64 or Float32, read back by field_scalar_type. Its element type is what the storage array actually holds, and the two part company in spectral representation: physical storage holds T, spectral storage holds Complex{T} at the same scalar type. Precision is the scalar type; the complex storage is representation detail, so a field in spectral representation is no less a Float64 field.
  • a section's storage family is the kind of array its data lives in — Array on the host, CuArray or ROCArray on a device — taken as the array's underlying type rather than its wrapping, so a reshape of an Array is still the Array family. Two sections combine only within one storage family and one element type; a mixed pair is refused rather than converted, and adapt moves one explicitly — a field, the wavenumber multipliers and convolution kernels built for it, its transform plans, a point set or point values — into another family, never changing the element type.
Scalar, vector and second-order tensors only

Sections of tensor order $R = 0, 1, 2$ — scalar, vector and second-order tensor — are the supported surface: no operation reaches past it, though not all span all three. Some are defined at one order by their own mathematics — det and tr need a matrix, cov a vector, std, var and the bare maximum/minimum/extrema a scalar — and each says so in its own docstring. The field and point-value types are parameterized on R, so higher orders can be constructed and several layers serve them (storage, HDF5 persistence, the vector-space operations, inner, l2norm, and spline interpolation between grid and points). Others do not: the reductions returning a fiber or taking a fiber map (mean(det, A)), map, and sym/skew/dev are defined for $R \le 2$ and throw above it.

General R was deferred rather than declined, to ship a usable field layer for the second-order surface a pseudospectral solver actually needs. Above the ceiling an operation either works or raises — none returns a wrong answer — and the test suite checks that.

The package is the field layer for pseudospectral fluid and turbulence solvers, and it carries a point layer that evaluates fields between grid nodes for Lagrangian-particle methods. A field is one real physical object; the physical and spectral forms are two representations of that same object.

This top-level module assembles its public interface from the submodules below. Each module's own docstring maps what it provides, so this list says what each is for rather than repeating it:

  • FiberSections — the base-agnostic foundation both layers share: the fiber types FiberVector and FiberTensor2/FiberTensor3/FiberTensor4, which name the value at one base point and so belong to neither base in particular.
  • Fields — the field and grid types, the two representations and the transforms between them, allocation, broadcasting, HDF5 persistence, and the storage-family move adapt.
  • FieldAlgebra — the fiberwise algebra on fields, including map!/map for any fiber map it does not name.
  • DifferentialOperators — the differential operators, applied as spectral multipliers.
  • Convolution — periodic convolution against a kernel, and the kernel builders. A kernel is its own kind of object rather than a field.
  • Points — the unstructured base: point-data types, their fiberwise algebra mirroring the field surface, spatial motion, and HDF5 persistence.
  • Interpolation — the grid↔point transfer, interpolate and anterpolate as an adjoint pair, under a choice of scheme.
  • Reductions — the L²/measure reductions over fields and point-values, against the base's own measure.
