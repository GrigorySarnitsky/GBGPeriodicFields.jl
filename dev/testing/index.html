Testing — GBGPeriodicFields

This is one of three design companions: ARCHITECTURE.md explains why the package is built the way it is, PERFORMANCE.md how it performs and is benchmarked, and this one explains how the tests are built and what they must cover. Read it before adding or changing tests. The goal is not a test count — it is that every claim the package makes is checked against something independent of the package.

1. Philosophy

Verify against independent ground truth, never against the code's own other path. A test that compares one package routine to another package routine only proves they agree, not that either is correct.

That bar is enforced, not stated (decision 55). Every public value-returning operation carries a recorded oracle provenance in test/oracle_registry.jl, and two assertions hold the line: an operation with no entry fails the suite, and so does one whose only coverage is other package operations. The rule existed here for a year before anything checked it, which is how weighted_inner came to be verified entirely against inner, laplacian, gradient and convolve — every assertion sound, and none of them a value derived independently of the package.

Four kinds of oracle are used:

  • Analytic oracles — for the differential operators. A field is taken to spectral representation, the operator applied, and the result compared to a known closed form: $\partial_x \sin x = \cos x$, $\Delta \sin x = -\sin x$, $\nabla \times (0, 0, \sin x) = (0, -\cos x, 0)$, a Helmholtz-projected field is divergence-free. These catch sign, axis, and scaling errors that a self-consistent round-trip would silently reproduce.
  • Independent computation — a direct evaluation written out in the test, taking no package routine but the one under test: a per-point LU for det, an explicit $\sqrt{\sum_i u_i^2}$ for norm, a binned circshift autocorrelation for radial_correlation, an $O(M^2)$ pair count for the point RDF. Slow and obviously correct, which is the trade being made.
  • Trusted reference — for representation parity and for the GPU path. The CPU path is pinned by analytic oracles and the parity baseline; then another computation of the same quantity (the spectral form, or the same operation on a device array) is required to match it. This is still "two computations of one quantity," not a thing against itself.
  • Structural identities — relations the operators must satisfy for any input: the vector-calculus identities ($\nabla\cdot(\nabla\times u) = 0$, $\nabla\times(\nabla\varphi) = 0$) and, on a periodic box, the adjoint relations (divergence as the negative gradient adjoint, self-adjoint curl, a self-adjoint negative-semidefinite Laplacian, an exactly idempotent self-adjoint Helmholtz projection — decision 42). Tested on randomized band-limited fields, they pin the discrete energy/entropy structure of the scheme.

A fixture must be able to falsify the claim its test makes. A symmetric fixture cannot see an asymmetric defect, and a self-referential assertion — threaded against serial, device against host, compressed kernel against stored — cannot see a defect shared by both sides. Both classes shipped here: a gradient testset named for an index convention whose fixture had a diagonal gradient, and a tensor divergence with no analytic oracle at all and nine identical components. Where a convention is stated in a name or a docstring, the fixture must be capable of contradicting it — and since that is a mechanical property, generated_analytic.jl obtains it by construction rather than by care.

The public method set is the spec. Two mechanisms enforce this:

  • the parity baseline (test/method_parity.jl) locks the method counts two ways. The per-generic list (206 public methods) is enumerated — it names 28 generics in two modules — and is therefore blind to anything not on the list: decisions 48, 49 and 51 each added public surface that never moved it. Beside it sits a derived baseline (decision 53), one frozen count per module over every function that module owns, so any new method anywhere moves a number and must be refrozen deliberately — the pass-audit protocol applied to the method table. Prefer adding to the derived one; the enumerated one stays because it localizes a change to the generic that moved. The derived count asks about ownership (m.module === mod) over the surface public_surface.jl derives, not about a module's namespace: a method defined under a qualified name — Base.inv(kernel::SeparableKernel) = … — creates no binding to scan, so a namespace-based count silently missed it (decision 56). The two baselines count different denominators and are deliberately not compared;
  • intentional-absence tests assert that invalid combinations do not exist (@test_throws MethodError), symmetrically across representations: nonlinear products are absent in spectral (field×field, division by a scalar field, pointwise norms), and the differential operators are absent in physical (differentiation is spectral-only — there are no finite-difference physical operators yet). A deliberate gap is a tested gap.

"Should work" is not done. The minimum bar for any change is: the package loads, the parity baseline and ambiguity check pass, and the suite is green.

A GATE and a SURVEY, and how to tell which a test is

Pkg.test() and test/exhaustive/ answer different questions, and the difference decides where any new test belongs.

Pkg.test()test/exhaustive/
the questiondid this change break something we know about?is there something we do not know about?
the verdictbinary — green, or the change does not shipa report, read by a person
may be non-greenneveryes, while a known limitation stands
cadenceevery changeoccasionally, on demand
its oraclespecific, per claim ($\langle \sin^2 \rangle = 1/2$)universal, per property (aliasing must not change the answer)
what it holdsclaims, completeness guards, intentional absencesproducts over the coverage axes

Four rules follow, and they settle placement without further argument:

  1. A specific oracle goes in the gate. $\langle \sin^2\rangle = 1/2$ is a claim about one operation: it must always hold, it costs microseconds, and a regression must block a commit.
  2. A universal oracle over a product goes in the survey. "Aliasing must not change the answer" ranges over every operation × every storage relation, and hand-picking instances of it is exactly how the aliasing axis came to hold two of its six values (decision 56).
  3. A completeness guard goes in the gate — the two ledgers, the oracle registry, the derived baselines. They are microseconds, and their whole purpose is to fail the moment an operation arrives without coverage. An occasional run cannot do that job.
  4. Anything that may legitimately be non-green goes in the survey. This is the decisive one. The aliasing failures cannot sit in the gate: they would have to be fixed or suppressed, and a suppressed failure is worse than an absent test because it reads as a pass.

The two are connected by a lifecycle: the survey discovers, a fix lands, the gate pins it forever, and rule 3's guards are what stop a new operation from skipping the first step.

Getting the split backwards fails in both directions, and both have happened here. Products in the gate slow it until someone trims coverage; oracles in the survey let regressions ship because nobody ran it.

Note that the GPU suite and the benchmarks are opt-in for an unrelated reason — they need hardware, or a quiet machine. "Opt-in" is not the axis; gate-versus-survey is.

The survey is a report, not a gate that has been silenced: it runs blind to what the package has decided, prints everything that does not work, and where a failure matches a recorded decision or a documented contract it prints the citation beside the failure rather than in place of it. It also reports what it could not construct, since a lane whose silence reads as a pass is the failure the whole file exists to prevent. See test/exhaustive/README.md.

3. Writing a test here

Helpers and conventions. Build fields from coordinate functions (ScalarFieldPhysical((x,y,z) -> …, grid)); take component slices with the local comp/tcomp helpers; build matching transform plans with a plans_for(field) helper that allocates the spectral scratch with similar(field_data(field), …) so it inherits the field's backend. Compare with field_data(result) ≈ expected.

Tolerances — the part that bites. ≈ (isapprox) uses a relative tolerance with atol = 0 by default:

  • For an O(1) result, bare ≈ is correct.
  • For a result that is mathematically ~zero, bare ≈ degenerates to an almost-exact comparison and will fail on nothing but rounding. Either assert maximum(abs, data) < 1e-12, or pass an explicit atol. Also choose inputs so the expected result is not accidentally zero — e.g. an axis-aligned field $(\sin x, \sin y, \sin z)$ is irrotational and longitudinal, so both curl and the Helmholtz projection return ~0 and test nothing. Use a field whose components depend on more than one coordinate.
  • For cross-backend comparison (GPU vs CPU), the two run the same formula and agree to roundoff, so compare with isapprox(Array(device), host; rtol, atol) carrying a small absolute floor.
  • The same trap appears for inner products of independent fields (e.g. $\langle \nabla\varphi, u\rangle$): they are near-orthogonal, so the common value of two equal inner products is small relative to the operand magnitudes. Scale the floor by the Cauchy–Schwarz product $\lVert a\rVert \lVert b\rVert$, not by the (tiny) result.

Pick the right oracle. Operators → analytic closed form. Representation parity and backend parity → trusted CPU reference. Never assert an operator only by inverting itself.

4. The coverage contract

For each public operation, a test must establish:

  • [ ] Physical-space correctness against an analytic or hand-computed result.
  • [ ] Spectral-space behaviour — correctness where the operation is linear in the field (valid in both representations); an asserted intentional absence (@test_throws MethodError) where it is nonlinear (physical-only).
  • [ ] Both element types — Float64 and Float32. (Float32 is the realistic GPU precision; consumer GPUs run Float64 far slower.)
  • [ ] An anisotropic domain — at least one test with $L_x \ne L_y \ne L_z$, so the $2\pi/L$ wavenumber scaling is actually exercised and a dropped length factor is visible.
  • [ ] The in-place ! form with a caller-supplied destination, including the aliased in-place branch for the by-construction alias-safe operations (cross, transpose, sym/skew/dev, the curl wrapper) — and, for mul!, the LinearAlgebra no-alias contract. An op whose kernel is alias-safe by construction (the one-pass helmholtz_projection!, decision 32) asserts the aliased call bitwise equal to the non-aliased one instead — a stronger check than the guard's tolerance.
  • [ ] Element traffic (decision 36): a new or rewritten operation gets a pass_audit.jl row — its exact per-array read and write counts measured through the CountingArray harness and frozen beside the fused ideal, with a named holder for any deliberate gap. This is the layer that catches an unfused recompute, which correctness, allocation, and static analysis all pass.
  • [ ] Allocation-free (invariant 13): every in-place ! operator gets an @allocated assertion in allocations.jl — on preallocated buffers with a distinct destination it allocates $\sim 0$ field-sized bytes, both element types. Run on the CPU: there a materialized field's full bytes are counted, whereas GPU @allocated reports only the host wrapper of a device buffer and would miss the materialization that wedges a hot loop (the code is generic, so a CPU materialization is a GPU one). A deliberate materializer (norm!/lpnorm/std/var, radial_correlation, the mixed spectral inner(f, g)) instead gets a bounded guard that catches an O(N)/O(shells) regression.
  • [ ] Both α/β branches for the five-argument kernels — overwrite ($\beta = 0$, which must ignore the destination's prior contents, NaN included) and accumulate ($\beta \ne 0$).
  • [ ] GPU parity — the result matches the CPU path on a device array, under allowscalar(false).

Grid coverage. Use a mixed-parity grid (even and odd axis lengths, e.g. (8, 7, 6)) so the Nyquist split is exercised; where the Nyquist mode matters, include a field that actually populates it and confirm the derivative of a real field stays real.

The coverage axes — the explicit denominator (2026-07-23). The checklist above is exhaustive only over the axes it names; a bug class living on an unnamed axis is invisible to it by construction. Three defects taught this in one week (decisions 41/42 and the NUFFT layout wrapper): each sat on an input-space axis that existed in the type system yet was never varied by any test — the rfft fold fft_dims had exactly one value ever constructed, and the adjointness fixtures deliberately dodged the Nyquist band. So the denominator is written down. Every operation's coverage is judged against the full axis list:

  1. representation (physical/spectral, including the asserted intentional absences);
  2. tensor order $R$;
  3. element type (Float64/Float32) on the CPU lane — GPU parity alone leaves the default Pkg.test() blind to the Float32 numerics;
  4. rfft layout — the fold must follow a non-default fft_dims (the permuted-layout lane, §2);
  5. axis parity (even and odd, folded and unfolded);
  6. grid-size cubicity (distinct extents, e.g. (8, 6, 4) — a cubic-only suite cannot see a transposed extent);
  7. domain-length anisotropy (distinct per-axis $2\pi/L$ factors appearing in the oracle's own formula, so a dropped factor cannot cancel);
  8. origin $\ne 0$ where the operation consumes coordinates (the transfer layer);
  9. degenerate bases (an empty PointSet; an axis of length 1 or 2) — pinned or asserted-absent;
  10. α/β including the $\alpha = 0, \beta \ne 0$ branch (the pure $\beta$-rescale);
  11. aliasing patterns per arity (dest === a and dest === b are different hazards);
  12. Nyquist content — at least one fixture populating the Nyquist planes, including the mixed case (Nyquist on one axis, resolved on another); a deliberately band-limited fixture states why (the dissipation identity is the standing example);
  13. backend (GPU parity — remembering parity is shared-bug-blind, so an analytic oracle on some CPU lane must also cover the non-default shapes);
  14. thread count (bitwise for the gated routes, tolerance for the two Atomix accumulators).

The rule. A new type parameter, constructor argument, or admissible input region is a new axis: it gets a row in this list and a lane in the suite in the same change, or an explicit NA with its reason. "Exhaustive" means exhaustive over this written list — an axis missing from the list is the failure mode, so extending the list is part of extending the type system. The cross-file permuted-layout lane (§2) and the anisotropic-box operator and radial testsets are the reference implementations.

5. GPU testing

GPU testing is opt-in and dependency-free for the package. The default Pkg.test() stays backend-free and portable; a GPU backend is only ever a test dependency. This is possible because the data layer is generic over AbstractArray, FFT plans are built through AbstractFFTs (dispatched on the array type), and allocations inherit their backend via similar — so a field on a ROCArray/CuArray just works.

  • Per-backend environments live under test/gpu/ (rocm/ and cuda/). Each is instantiated only on matching hardware (AMD at home, NVIDIA at the office); a no-GPU CI box never installs a vendor stack.
  • A single backend-agnostic test/gpu/suite.jl holds the test logic. A thin per-backend entry script (test/gpu/<backend>/runtests.jl) supplies to_device, device_functional, GPU_BACKEND, and calls <Backend>.allowscalar(false) before including the suite. With scalar indexing disabled, any stray scalar index into device memory inside a package method throws — turning invariant 6 into a checked guarantee rather than a convention.
  • Strategy: run the public surface on device arrays and compare against the trusted CPU result (matches, with an atol floor per §3). If no device is present the suite warns and skips.
  • Manifests are gitignored (repo convention — none are tracked); each environment reproduces from its Project.toml plus a [compat] bound, via Pkg.instantiate().

Run it on hardware:

julia --project=test/gpu/rocm -e 'using Pkg; Pkg.instantiate()'   # one-time
julia --project=test/gpu/rocm test/gpu/rocm/runtests.jl

Adding a backend = mirror rocm/ (see test/gpu/README.md); the suite needs no changes.

6. Maintenance

  • After any code-generation change, re-verify the method set is unchanged: update the counts in test/method_parity.jl only with a deliberate, reviewed reason, and keep detect_ambiguities empty.
  • Keep the test summary in CLAUDE.md (roadmap item 4) roughly current.
  • Aqua.jl (test/aqua.jl) runs Aqua.test_all on every Pkg.test() — ambiguities, unbound type parameters, undefined exports, project/compat consistency, stale deps, type piracy, persistent tasks. Keep it green; among other things it enforces that every dependency carries a [compat] bound.
  • JET.jl (test/jet.jl) runs @test_call on the public operations, filtered to the package's own modules — a per-Julia-version static check for inference-detected errors (MethodError, BoundsError, undefined variables). It is left uncapped in test/Project.toml so each CI Julia version resolves a compatible JET. Note it analyzes the running version, so it does not catch version-divergence (that is the CI matrix's job).
  • CI (.github/workflows/CI.yml) is manual-only — workflow_dispatch plus release tags, not every push: each commit is authored locally and the full matrix is run before pushing, so a push-triggered run would only re-verify what is already green (a tagged release additionally exercises a from-scratch clean-environment resolve, the one thing a single local run cannot give). The matrix is Julia 1.12 (the compat floor) at -t1 and current stable at -t4, so both lanes run on one Julia and differ only in thread count — running them locally needs no manifest juggling. The floor was 1.11 until it was dropped: the package ran faster there, but every operation cost several times more to compile (_assign! alone 4.5×), which made the local suite take about six times as long for a Julia nothing in the fleet runs.
  • Performance is tracked separately, not by Pkg.test(): the opt-in benchmark/ suite and its coverage contract live in PERFORMANCE.md (the third design companion).
