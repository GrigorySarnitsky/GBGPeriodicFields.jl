Performance — GBGPeriodicFields

This is the third companion to ARCHITECTURE.md and TESTING.md: where those explain why the package is built as it is and how its correctness is checked, this one explains how performance is reasoned about, measured, and tracked. Read it before optimizing anything or adding a benchmark. The throughline is the same as for tests: a performance claim is only as good as the independent measurement behind it — and on the platform that matters.

1. Philosophy

Memory-bound, GPU-first, measure-don't-guess. Three principles set everything below.

  • The baseline is memory bandwidth, not flops. Every operation here has low arithmetic intensity — a handful of floating-point operations per element moved (§2). So "fast" means "moving the necessary bytes efficiently," and adding cores or tuning arithmetic helps only until the memory system saturates. The roofline ceiling for this package is the bandwidth roof, not the compute roof (roofline).
  • GPU-first (invariant 6). Production runs on the GPU; the CPU path is for development, testing, and small problems. When an optimization helps one platform and hurts the other — which happens, and is proven below — the GPU wins. CPU multithreading is a supported feature (docs/ARCHITECTURE.md §9), but it is not the platform performance is optimized for.
  • Measure before you optimize, and measure on the production platform. No optimization is kept without a same-session side-by-side comparison showing it helps the GPU. This session's record is instructive: of the candidates that looked like wins, polynomial-eval tuning was already free, the periodic-wrap hoist made the default scheme slower, and particle sorting — the textbook locality optimization — regressed the GPU gather. Only the one the measurement pointed at (loop order) survived (§4).

A scope note carried from the architecture: platform optima diverge, so every result below is reported per platform, never as a single number. (The L²/measure reductions — integral, inner, l2norm, mean, …; docs/ARCHITECTURE.md decision 18 — are bandwidth-bound streaming reductions whose only subtlety is floating-point summation order, tolerance-tested rather than bitwise; they are now part of the suite, §5.)

2. The performance model

What bounds each public operation class — the mental model a benchmark either confirms or refutes.

  • FFT transforms (to_physical/to_spectral) → bound by FFTW (CPU) / rocFFT (GPU). The package adds only the normalization convention and the fiber-last layout (docs/ARCHITECTURE.md §3–4); the transform itself is the library's. Not something we tune — but the dominant cost of any spectral step, so it is benchmarked to track the libraries and our plan/layout overhead.

  • Field algebra (M2 + M3), spectral differential operators, and convolution → memory-bandwidth-bound. A fiberwise add, contraction, wavenumber multiply, or kernel multiply (convolve) reads and writes O(1) numbers per grid point and does O(1) flops on them — arithmetic intensity well below the roofline ridge. Consequence: on CPU, thread scaling saturates once the cores jointly saturate DRAM bandwidth (the plateau in §4); on GPU, the figure of merit is achieved bandwidth, not occupancy.

  • The grid↔point transfer (interpolate/anterpolate), local-stencil spline schemes → the subtle one. Each point gathers (or scatters) a $(2n{+}2)^3$ stencil ($n$ the spline half-width) with data-dependent indices, so it is bound by irregular memory access, and the binding differs by platform:

    • GPU: maximize memory-level parallelism — many distinct cache lines and DRAM banks in flight at once to hide latency (coalescing/occupancy). Scattered (unsorted) points naturally spread access and feed that parallelism; and at the grids we run the field is largely cache-resident (a 256³ Float32 field is 67 MB, inside the RX 6700 XT's 96 MB Infinity Cache), so there is little locality left to win.
    • CPU: bound by the cache hierarchy + hardware prefetchers, which reward locality — the opposite pull.

    This single fact — GPU wants spread, CPU wants locality — explains the platform-divergent results in §4 (loop order, sorting) and is the most important thing to internalize before touching the transfer.

  • The spectral transfer (DirectDFT/NUFFT) → a different cost class. DirectDFT is the exact $O(N M)$ double sum (compute-bound, no FFT, no window) — the oracle; NUFFT is its $O(N\log N + M)$ fast form, an oversampled FFT plus a windowed spread/gather, so it is FFT-bound in the grid size $N$ and carries the same irregular-access spread/gather as the splines in the point count $M$.

3. Best practices

Short checklists, each grounded in an external reference. Most are already enforced by the architecture or the tests; they are collected here so an optimizer has them in one place.

Julia (Julia Performance Tips; Modern Julia Workflows):

  • Type stability — non-concrete types force boxing and allocation. Checked package-wide by test/jet.jl (JET.@test_call).
  • Zero allocations in hot paths — an unexpected allocation almost always signals a type problem. Prefer the in-place ! forms; allocate scratch once and reuse. (@allocated/BenchmarkTools report it.)
  • @inbounds in kernels, isbits / SVector kernel arguments (so the spline coefficient matrices pass into GPU kernels by value, no device array), and fused broadcasts through _assign! rather than a bare .= (the codegen + threading contract, docs/ARCHITECTURE.md §9).
  • Allocate via similar/similar_field so results inherit the input's backend (the one-line reason a CPU-written method runs on a ROCArray unchanged).

GPU (ROCm/HIP performance guidelines):

  • No scalar indexing of device arrays (invariant 6) — a checked guarantee under allowscalar(false) in both the test and benchmark GPU runs.
  • Favour spread access for memory-level parallelism, and loop the contiguous (x) axis innermost so per-thread stencil access is stride-1 (§4 measured this at up to 3.9×).
  • Minimize host↔device transfer; keep fields resident on the device. Allocate once, operate in place.

Methodology (BenchmarkTools.jl manual):

  • Warm up (compile) before timing; synchronize the backend — GPU work is asynchronous, so an un-synced timer measures launch latency, not the kernel (the suite's bench_sync).
  • Report the minimum of many samples (least-noise estimator) alongside the median.
  • Side-by-side comparison in one session: build both variants (baseline and candidate) and time them on identical data, back-to-back, in a single process — the only reliable way to resolve a difference smaller than the ~10% run-to-run variance (separate launches drift with thermal state, allocation layout, and cache).
  • Control the thread count (-t1 vs -t4), and always confirm on the GPU before keeping an optimization (platform divergence is real, §4).

4. What we have found

Measured on the home AMD Radeon RX 6700 XT (gfx1031, 12 GB, 96 MB Infinity Cache, ~384 GB/s peak) and Intel i7-12700K (8 P-cores), Float32, ~1 point per 27 grid cells. These are the cumulative results of the transfer-layer optimization work; the benchmark suite (§5) regenerates the tracked subset on demand.

(a) Memory-bound, and smoothness is free. Interpolation runs at ~12% of peak bandwidth at 256³; cost scales with the stencil volume $(2n{+}2)^3$, and the spline degree (m) is invisible — the weight polynomials hide under memory latency. So pick the smoothness for accuracy, never for speed.

(b) Loop order — contiguous axis innermost (KEPT). Iterating the contiguous x axis innermost (stride-1 stencil access) vs z-innermost (stride $N_x N_y$, the grid's $x$,$y$ dimensions):

Kept x-inner as a GPU-first choice — the CPU's large caches absorb the strided access and its z-inner form vectorizes better, but the GPU is the production platform.

(c) Rejected by measurement. Two "obvious" optimizations that did not survive:

  • Wrap-hoist (precompute the $3(2n{+}2)$ periodic node offsets to kill inner-loop mods): bit-identical, but regressed the default Catmull–Rom by 10–14% — the extra registers cut occupancy. Proof the kernels are memory/occupancy-bound, not ALU-bound.
  • Morton particle sorting (the textbook GPU-locality optimization): 0.5–1.0× on GPU (gather) — concentrating access kills the memory-level/DRAM-bank parallelism the GPU needs, and the field is cache-resident anyway — though 2.2–4.4× on CPU. The companion atomic-free node-centric scatter is correct, conserving and bit-deterministic, but 6–24× slower on GPU: at our sparse 1-per-27 density it traverses ~27× more (empty) reverse-stencil cells than the atomic scatter touches particles. Sorting + node-centric deposition is a dense-particle (PIC) technique; wrong for this regime. (If deterministic anterpolation ever becomes a hard requirement, it is the available — slow-at-sparse — answer.)

(d) Anterpolation and contention. The scatter costs ≈2.2–2.7× the gather (atomic read-modify-write + a full-grid prescale). On gfx1031 Float32 atomic-add is native but Float64 is emulated (CAS loop) ⇒ ≈1.3–1.7× slower; contention is worst at moderate clustering (~2 pts/cell), not extreme (extreme stays cache-hot).

(e) CPU vs GPU. The transfer threads on CPU through KernelAbstractions' CPU() backend with no code change, scaling ≈4.5–5.7× on 8 threads before the bandwidth plateau; the GPU is ≈9–22× the 8-thread CPU (≈ the 384-vs-~60 GB/s bandwidth ratio for the heavy schemes, more for the light ones via parallelism).

(f) Allocation-free in-place operators — the GPU hot-loop discipline. A pseudospectral solver applies the spectral operators thousands of times in its time loop, so any per-call scratch an operator allocates internally matters. On the GPU it matters a lot: such scratch escapes Julia's GC (which triggers on host memory, while the scratch is device memory), so the device pool grows every step until VRAM fills and the run wedges (allocator spinning, GPU idle) or hipMalloc aborts — observed at 192³/256³. The fix made the in-place spectral operators allocate nothing: _squared_wavenumber_broadcast (the $|k|^2$ coordinate) is returned lazily (an unfused Broadcasted, no $O(N^3)$ array), and the helmholtz_projection! / laplacian! / inverse_laplacian! kernels fuse their former temporaries into the component broadcasts — each now allocates $\sim 0$ bytes in place (measured; guarded by test/allocations.jl), with identical results. Payoff: a preallocated, in-place pseudospectral DNS step allocates nothing per step → no manual GC.gc()/reclaim, flat VRAM. The forced-HIT example (examples/gpu/rocm/HIST_ROCm.jl, 192³ Float32, $\mathrm{Re}_\lambda \approx 93$) sustains ≈ 34 ms/step (8000 steps, ≈ 270 s) on the RX 6700 XT this way. Discipline for consumers: preallocate a workspace and use the ! forms with a destination distinct from the sources; the fiber norm/lpnorm/dev! deliberately materialize one field and are the exceptions (use maximum(abs, …) for a CFL speed). [Decision 24.]

(g) Allocation-bounded radial diagnostics — the same GC trap, in the binning. The same device-GC hazard as (f) lived in the diagnostics. The radial_spectrum / radial_correlation reductions binned by looping over the $|k|$- (or $|r|$-) shells and reducing a masked broadcast per shell. The shell count scales with the grid ($\approx \sqrt{3} N/2$, $\approx 220$ at $N = 256$, with $N$ the per-axis size here — not the total $N$ of §2), and each iteration allocates a full-grid mask — and, because a mapreduce over a Broadcasted materializes on this GPU stack rather than fusing, the masked product too: $O(N)$ full-grid temporaries per call, which the host-triggered GC does not reclaim. A single $256^3$ radial_correlation snapshot churned several GB and wedged a 12 GB card at the first snapshot. The fix bins in a single scatter-add pass — one portable KernelAbstractions + Atomix histogram kernel atomically accumulating each element into its shell — so per-call temporaries drop from $O(N)$ to $O(1)$. Correctness is unchanged (same per-shell sums; CPU test/reductions.jl + GPU parity hold). Payoff: the $256^3$ Float32 forced-HIT example ($\approx 87$ ms/step) now runs to completion on the RX 6700 XT at a flat $\sim\!6$ GB ($\approx 8$ GB peak) through its snapshots, where the per-shell form wedged at the first one. The scatter contends on the small accumulator set, acceptable for an occasional diagnostic (not a per-step call); a privatized histogram is a possible future optimization. [Decision 25.]

(h) FFTW ESTIMATE can badly mis-plan single-precision transforms — pass MEASURE for production. FieldTransformPlans builds its FFTW plans with the default ESTIMATE flag (instant, but it guesses the algorithm instead of timing candidates). On a Ryzen 9800X3D (Zen 5, stock FFTW 3.3.11) that guess is ~5× too slow for the 256³ Float32 transforms — in both directions, at every thread count — because its hardcoded single-precision codelet heuristics misjudge this CPU generation. Rebuilding with FFTW.MEASURE (a one-time, timed plan search) fixes it, and the planning cost (seconds) amortizes over a long run. Pure in-place transform, 256³ Float32, minimum time:

threadsc2r (to_physical!), ESTIMATE→MEASUREr2c (to_spectral!), ESTIMATE→MEASURE
1163 → 30 ms (5.4×)167 → 31 ms (5.3×)
443.7 → 9.5 ms (4.6×)41.7 → 8.3 ms (5.1×)
823.5 → 6.8 ms (3.4×)21.8 → 4.8 ms (4.5×)

It is size- and CPU-specific (128³ is fine; the i7-12700K shows no such inversion) — a classic ESTIMATE pitfall on a new CPU, not a package issue. The default stays ESTIMATE (cheap, deterministic, right for tests and short runs); the escape hatch already exists, FieldTransformPlans(phys, spec; fft_flags = FFTW.MEASURE) (or FFTW.PATIENT). MEASURE overwrites its input arrays while planning, so build the plans on scratch fields before seeding data. The forced-HIT CPU example (examples/HIST_CPU.jl) now plans with MEASURE.

(i) A fused reduction needs a different shape per backend — get that right and it wins on both. The mapped forms (decision 30) reduce a function of the fiber value at every base point without materializing it. A single formulation cannot serve both devices, and the first implementation shipped the GPU's shape to the CPU, where it ran slower than the materializing route it was meant to replace. Splitting it fixes that. Measured with the same map on both sides (mean(det, A) against mean(det(A)), $N = 128$, Float64):

backendfusedmaterialize + reduce
CPU (vectorized blocked loop)5.1 ms, 0 B13.0 ms, 16.8 MBfused 2.5× faster
GPU, RX 7900 XTX (fused Broadcasted)0.55 ms, 0 B0.69 ms, 16.8 MBfused 1.3× faster

Decomposing the CPU side shows why one shape could not do both, and it is not the layout:

step$N = 128$, Float64, 1 threadfactor
maximum over a contiguous array0.56 msbaseline
reducing a lazy Broadcasted instead (one stream, no gather)3.1 ms5.6×
three strided streams instead of one6.4 ms2×
building the StaticArray per base point5.6–6.4 msfree
LinearAlgebra.norm instead of naive $\sqrt{\sum_i u_i^2}$27.7 ms4.3×

The dominant term is the reduction losing its vectorized blocked loop, which costs more than the extra section of traffic that materializing pays — so on a CPU the fix is simply not to reduce a lazy expression: the implementation runs its own blocked loop over the component arrays instead. A GPU has no such loop to forfeit (thread-parallel, bandwidth-bound), so index arithmetic hides behind memory latency and the skipped section write and read-back is pure profit; it keeps the fused Broadcasted. Blocking the CPU loop pairwise, as Base's own reduction does, additionally makes it the most accurate route (relative error $1.2\times10^{-16}$, against $3.7\times10^{-15}$ for the lazy form and $1.6\times10^{-16}$ for materializing). The strided gather that fiber-last layout (invariant 3) forces contributes only $2\times$, and the StaticArray build is free.

The last row is a measurement trap worth recording: LinearAlgebra.norm on a fiber uses the overflow-safe scaled 2-norm, $4.3\times$ the plain magnitude the fieldwise norm evaluates. So comparing maximum(norm, u) against lpnorm(u, Inf) varies the algorithm and the route together and reads as a fusion penalty that is not the fusion — given the same formula the fused form is 1.8 ms against 4.2 ms. This analysis reported the confounded number twice before decomposing it. Vary one thing at a time here.

Three formulations that look equivalent are not, and each silently reintroduces allocation: a multi-argument mapreduce (fused by GPUArrays, but materializing a full section on the CPU), an anonymous vararg closure (uninferrable component count), and a forwarded Function-typed argument left untyped in the signature (Julia declines to specialize on it). All three are pinned at zero bytes by test/allocations.jl. [Decision 30.]

(j) A multi-output kernel beats broadcast recomputation — the one-pass Helmholtz projection. The projection writes three output components that share one intermediate (the longitudinal factor $k_j\hat u_j/|k|^2$), which a broadcast cannot express: the three-broadcast form recomputed the shared dot product per component — nine component reads and three divisions per mode for three writes. The one-pass KernelAbstractions kernel (decision 32) reads each source component once, computes the factor once, and writes all three components — and, reading a whole mode before writing it, serves the aliased in-place call with no guard temporary. Measured on the 12700K ($64^3$–$128^3$, Float64; the fused-vs-three-broadcast ratio):

threads$64^3$$128^3$
13.9×4.1×

Two costs worth recording. The KA launch allocates a small size-independent host-side bookkeeping (~1.5 KB serial, ~7 KB at four threads — task spawning), where the broadcast route allocated ~0.3 KB; the allocation audit's fraction-of-a-field threshold absorbs it, and the field-sized guard temporary of the aliased call (~0.84 MB at the audit size, IT's 3.19-unit transient at $256^3$) is what is gone. And the kernel-composed form (helmholtz_projection!(…, kernel), decision 32) adds one scalar-field read to the same pass — measured +6–16% over the plain projection, against ~+50% for the separate convolve! pass it replaces.

(k) A lazy kernel is a reuse question, not a free win — and the naive A/B forgets the build pass. The exponential family (decision 33) evaluates $\exp(c|k|^2)$ per mode instead of reading a stored kernel field. Whether that pays depends on what the stored route would actually do:

comparison (vector field)CPU $128^3$ F64, 4 threadsGPU $256^3$ F32, RX 7900 XTX
lazy vs stored kernel, kernel fixed9.1 vs 5.4 ms — stored 1.7×0.94 vs 0.87 ms — stored 1.08×
lazy vs rebuild + apply, exponent variescomparable (the rebuild pays the same exp)0.94 vs 0.46 + 0.87 ms — lazy 1.4×

Three lessons. The fusion forms (the bottom two rows) win on both backends — they save a destination write and re-read, which no amount of exp cost eats. The lazy-vs-stored single-operand trade is governed by reuse: a fixed kernel amortizes its build and then wins on pure bandwidth (the per-mode exponential costs more than the field read it saves — dramatically so on CPU, where exp is expensive and the broadcast re-evaluates it once per fiber component); a varying exponent forces the stored route to pay a full build pass per change, and the lazy form then wins. And the measurement trap: an A/B of exponential_convolve! against a prebuilt convolve! silently compares against a route whose build pass happened outside the timer — state which reuse pattern is being measured before quoting a ratio. A possible future optimization — hoisting the exponential over the fiber in a mode-loop kernel, the decision-32 shape — would cut the CPU vector case's threefold exp re-evaluation; it waits for a CPU-bound consumer (the audits' consumer runs GPU-first).

5. The benchmark suite

A standing suite under benchmark/ (sibling of test/), opt-in — not part of Pkg.test(), exactly like the GPU tests. A call to build_suite(; array_type, types, sizes) builds a BenchmarkTools.BenchmarkGroup parameterised by the device array type (Array on CPU; ROCArray/CuArray on GPU — the same approach test/gpu/suite.jl uses with to_device), so one suite runs everywhere. A bench_sync blocks the backend so BenchmarkTools times GPU work to completion.

Classes covered: FFT transforms, field algebra (M2 + M3, representative — including the weighted combination combine! and the determinant det!), spectral operators (including the fused symmetric_gradient! and the kernel-composed helmholtz_projection!/divergence! forms of decision 32, whose baseline is the sequential operator + convolve! pair they replace), convolution (convolve! scalar/vector, the lazy exponential_convolve! and the kernel-composed combine! of decision 33 — their baselines the stored-kernel convolve! and the sequential combine! + convolve! pair — + the builders spectral_cutoff / spectral_band / squared_wavenumber_field / assignment_window / translation_kernel — a builder is paid once and its kernel applied many times, so it is swept for regressions, not for hot-path cost), the interpolation/anterpolation transfer (the spline schemes plus the spectral NUFFT; the exact DirectDFT is its oracle, not a swept regression target), and the L²/measure reductions (integral/mean/inner/l2norm/lpnorm/maximum, the fused multiplier-weighted weighted_inner, the spectral Parseval inner, the spectral zero-mode integral/mean (an O(1) DC-coefficient read, not a streaming reduction), and the radial pair radial_spectrum / radial_correlation plus the two-field co-spectra radial_spectrum(f, g) / radial_correlation(f, g) — a single scatter-add shell-binning pass and an inverse rfft, diagnostic-cost; the co-spectra cost the same as the single-field forms, sharing their binning), including the mapped forms maximum(norm, u) / mean(norm, u) / mean(det, A) / mean(tr, A), whose maximum(norm, u) row pairs with the lpnorm vec Inf row as a direct A/B — the same quantity, one materializing a magnitude section and one not. Run it:

julia --project=benchmark -e 'using Pkg; Pkg.instantiate()'   # one-time
julia --project=benchmark -t1 benchmark/runbenchmarks.jl       # serial lane
julia --project=benchmark -t4 benchmark/runbenchmarks.jl       # threaded lane
julia --project=benchmark/gpu/rocm benchmark/gpu/rocm/runbenchmarks.jl   # GPU (on hardware)

The tracked SUITE uses modest grids (64³, 128³) for fast, repeatable, regression-sensitive runs; the large characterisation sweep behind §4 (256³/512³) is reachable with build_suite(; sizes = (256,)). Manifests are gitignored (repo convention); each environment reproduces from its Project.toml.

The coverage contract. Every public operation class is benchmarked (representative members) over {Float64, Float32} × {representative grid sizes} × {CPU -t1, CPU -t4, GPU}. New code adds its benchmark to the matching per-class file — the performance analogue of the test coverage contract (TESTING.md §4).

6. Tracking regressions, and per-platform results

Workflow (manual, BenchmarkTools). Save a baseline, then judge a later run against it on the minimum-time estimates:

julia --project=benchmark benchmark/runbenchmarks.jl save results/cpu-baseline.json
julia --project=benchmark benchmark/runbenchmarks.jl judge results/cpu-baseline.json   # :regression / :improvement / :invariant

Because CI runners have no GPU, GPU tracking is manual: run the GPU suite on the device and record the numbers here. Adding a platform = mirror benchmark/gpu/rocm/ (a Project.toml + a 2-line runbenchmarks.jl); the suite needs no changes.

Two scales. The tracked SUITE (runbenchmarks.jl, grids 64³/128³) is the quick, regression-sensitive run used with save/judge above. The exhaustive characterization (benchmark/characterize.sh) runs the full matrix — every op-class (including FFT) over grids 64³–256³, on the CPU thread sweep 1/2/4/8 (powers of two up to the performance cores) and the GPU — building one (grid size, element type) at a time to bound memory (a 256³ Float64 tensor field is ~1.1 GB; holding all classes for both types at 256³ overflows the 12 GB GPU — gap 5), and assembles it into the committed report benchmark/RESULTS.md (the raw per-run JSON under benchmark/results/ is gitignored). Regenerate it on any platform with that one script; it stamps the date, commit, and host.

A representative slice — 128³, Float64, minimum time (CPU = i7-12700K, GPU = RX 6700 XT). The last two columns are speedups in ×: CPU thread scaling (-t1 → -t4) and the GPU's lead over the 4-thread CPU. RESULTS.md now carries two CPU thread sweeps (i7-12700K and Ryzen 9800X3D) and four GPU columns — the GTX 1070 (Pascal, CUDA, pre-swap), the RX 6700 XT shown here, the RX 7900 XTX (gfx1100, 24 GB), and the RTX 5070 Ti (Blackwell sm_120, CUDA, 16 GB). At 256³ (kernel-dominated, not launch- or gcsample-floored) the 7900 XTX runs ~1.7–3.8× faster than the 6700 XT — widest in Float32 — and adds a 512³ Float32 point; the 5070 Ti covers the full 256³ matrix (both element types, all six classes). Across vendors the reductions class shows the widest gap and the clearest architectural signature: the radial diagnostics (radial_spectrum/radial_correlation) bin on an Atomix scatter-add histogram, and CUDA's atomic throughput far outruns RDNA3's — radial_spectrum at 256³ is ≈12× faster on the 5070 Ti than the 7900 XTX in Float32, widening to ≈32× in Float64 (92 → 2.9 ms); the extra Float64 factor is the emulated-atomic penalty of §4(d) (RDNA has no native global Float64 atomics), the 7900 XTX paying ≈4.3× for Float32→Float64 on this op against the 5070 Ti's ≈1.7×. The full operation × type × grid × thread/backend matrix is in RESULTS.md:

Two patterns the speedup columns make plain. The bandwidth-bound classes barely thread at this size — algebra and operators gain only ≤1.2× from 4 threads (the cheapest, add!, even regresses: it is already DRAM-bandwidth-saturated on one core), confirming §2. The transfer threads well (≈3.9× on the Catmull–Rom gather) because its stencil gather carries more work per byte. And the GPU leads the 4-thread CPU by ~10–14× (and the serial CPU by up to ~50× — e.g. Catmull–Rom gather, 13.8 → 0.28 ms), widest for the light/parallel ops and narrowing toward the bandwidth ratio for the heavy streaming ones. (Float32 is ~0.6–0.7× of these Float64 times on the GPU; the full operation × type × grid × thread/backend matrix — including the per-grid scaling and the 1/2/4/8 thread sweep — is in benchmark/RESULTS.md.)

7. Current coverage and known gaps

Covered: the public operation classes (FFT, algebra, operators, convolution, transfer, reductions) parameterised by element type and grid size, runnable on CPU (-t1/-t4) and GPU (ROCm or CUDA) through one device-parameterised suite; the manual save→judge regression workflow; and the exhaustive characterization (characterize.sh → committed benchmark/RESULTS.md): every op-class (incl. FFT) at grids 64³–256³, across two CPU 1/2/4/8 thread sweeps (i7-12700K, Ryzen 9800X3D) and four GPUs — GTX 1070 (Pascal, CUDA), RX 6700 XT, RX 7900 XTX, and RTX 5070 Ti (Blackwell sm_120, CUDA); the 7900 XTX is extended to a 512³ Float32 point for the bandwidth-bound classes. The decision-27 additions (combine!, det!, symmetric_gradient!, weighted_inner) are wired into their classes and CPU-verified (0 allocations for combine!/det!/symmetric_gradient!; the small bounded guard for weighted_inner); they enter the committed RESULTS.md table on its next GPU-host refresh.

Gaps:

  1. GPU reductions/convolution are measured with gcsample — read them as latency, not throughput. Both classes are now in RESULTS.md for every platform (CPU 1/2/4/8 + GPU). The GPU figures use gcsample = true (gap 5): a GC before each sample bounds memory but adds a fixed per-sample cost, so the small-grid GPU times (≈1.5 ms at 64³) are dominated by that overhead, not by the kernel — read those as per-call latency, and trust the 256³ figures, where the kernel dominates and the GPU pulls ahead of the CPU. The CPU columns and the non-allocating GPU classes are unaffected (gcsample is cheap when there is nothing to collect).

  2. CUDA spans two NVIDIA generations, both on Enteropia (the office box; CPU Ryzen 9800X3D). characterize.jl now takes a cuda backend beside gpu/rocm (CuArray + CUDA.reclaim(), no comgr warm), so the memory-bounded one-class-at-a-time sweep runs on NVIDIA too. The archived GTX 1070 (Pascal, 8 GB) stays a 64³/128³ column — an 8 GB Pascal card tops out below 256³, so those rows read —. Its in-place replacement, the RTX 5070 Ti (Blackwell sm_120, 16 GB), covers the full 64³–256³ matrix (both element types, all six classes; ~10.8 GB peak). 512³ exceeds 16 GB — the mul! tensor field alone is 4.5 GB and the build OOMs — but unlike AMD's HIP (gap 5), CUDA OOMs gracefully (a Julia OutOfGPUMemoryError, no context corruption), so probing the ceiling is safe. Enteropia now also contributes its 9800X3D CPU thread sweep beside the i7-12700K (host Aiporetne).

  3. Automated CI regression — deferred. The BenchmarkGroup layout keeps AirspeedVelocity.jl (PR-over-PR CPU comparison) or PkgBenchmark.jl a drop-in later.

  4. Run-to-run variance — absolute numbers carry ~10% jitter, so cross-platform/-commit comparisons are only meaningful within a single session (hence the side-by-side discipline of §3); the tables here are indicative magnitudes, not contract values.

  5. GPU at 256³ — three traps, none a rocFFT bug (RX 6700 XT, gfx1031, 12 GB, ROCm 7.2.4). Earlier notes blamed "rocFFT 256³ planning"; that was wrong. The facts, measured:

    • 256³ FFT works. Scalar and vector r2c/c2r at 256³ take ~1 s to plan and ~15–20 ms to run; the full fft class passes at 256³.
    • Cold kernel compilation looks like a hang. The first GPU use after a reboot compiles kernels host-side via AMD comgr → 0% GPU, 100% CPU, VRAM pool reserved, no output, for minutes. Never kill a cold first run — a killed compile never persists to ~/.cache/comgr, so the next run restarts cold. characterize.jl warms the cache with one trivial kernel up front.
    • The 256³ working set overflows 12 GB VRAM, and HIP segfaults instead of erroring — the crash is hipMallocFromPoolAsync in libamdhip64.so. Two compounding causes, two fixes: (i) holding all six classes' fields live for one (size, type) exceeds 12 GB at 256³ (a 4-class sweep fit; adding reductions + convolution did not) → characterize.jl builds one (op-class, size, element-type) at a time, bounding the working set to a single class (~few GB); (ii) GC returns freed device memory to the AMDGPU pool, not the OS, so the pool high-water mark accumulates across iterations and 256³ OOMs late (the first pairs fit, the last does not) → AMDGPU.reclaim() between iterations releases blocks back to the OS. Knock-on: a VRAM-OOM segfault can still degrade the HIP context until a reboot / rocm-smi --gpureset, after which even small ops segfault under load.
    • A GC-free benchmark loop wedges the allocating reductions — independent of grid size (seen at 64³), and the cause of a 4-hour hang. lpnorm materializes a pointwise-magnitude field per call; BenchmarkTools' tune!/run does almost no host allocation, so Julia's GC (host-pressure triggered) never fires, the dead GPU temps pile into the AMDGPU pool until it hits 12 GB, and the allocator spins — CPU pegged, GPU idle, VRAM maxed, for hours. It is GC-lag, not a leak (GC.gc() every ~50 calls holds the pool flat; a real solver fires GC every step, so the op is fine in use). Fixed by gcsample = true for GPU runs (characterize.jl and the ROCm runner): a GC before each sample bounds the pool — the reductions class then completes at ~0.5 GB peak. Distinct from the cold-compile hang above — there comgr is active (compiling, minutes); here it is idle (wedged, hours).

    With the per-(op-class, size, type) build the full 64³–256³ GPU column is in RESULTS.md. The standing limit on the 6700 XT is the 12 GB ceiling itself: even one class's both-element-type 256³ fields strain it (hence the one-class-at-a-time build), and 512³ won't fit on that card. If a future OOM-segfault degrades the context, reset with rocm-smi --gpureset from a console (it can crash an active display session) or reboot.

    Update (2026-06-26, RX 7900 XTX, gfx1100, 24 GB). On RDNA3 256³ is indeed trivial for every class (both element types), and a 512³ Float32 point is now in RESULTS.md for the bandwidth-bound classes (fft, algebra, operators, convolution). But 512³ is not free even at 24 GB: transfer is omitted (its NUFFT oversamples ×2 to a 1024³ work grid) and reductions is omitted (the radial diagnostics hold a ≈24 GB live set at 512³ — vector physical + spectral fields + the inverse-rfft plans). A 512³ Float64 sweep of the heavy classes exceeds 24 GB, and a HIP OOM wedges the allocator (GPU 0 %, one host core spinning, VRAM full) rather than erroring — the same trap as the cold-compile / GC-free hangs above, and gcsample does not help when the live set (not GC lag) is what overflows. So the 512³ column is Float32 and skips those two.
