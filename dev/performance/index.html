Performance — GBGPeriodicFields

This is the third rationale companion to ARCHITECTURE.md and TESTING.md: where those explain why the package is built as it is and how its correctness is checked, this one explains how performance is reasoned about, measured, and tracked. Read it before optimizing anything or adding a benchmark. The throughline is the same as for tests: a performance claim is only as good as the independent measurement behind it — and on the platform that matters.

1. Philosophy

Memory-bound, GPU-first, measure-don't-guess. Four principles set everything below.

  • The baseline is memory bandwidth, not flops. Every operation here has low arithmetic intensity — a handful of floating-point operations per element moved (§2). So "fast" means "moving the necessary bytes efficiently," and adding cores or tuning arithmetic helps only until the memory system saturates. The roofline ceiling for this package is the bandwidth roof, not the compute roof (roofline).

  • GPU-first, and the CPU path targets a whole cluster node. Production runs on the GPU, and where an optimization helps one platform and hurts the other — which happens, and is proven below — the GPU wins across the range both can run. One carve-out, exercised once: the rule ranks platforms, not the particular card a number came from, so where the measured GPU disagrees with the production one the production target decides. §4(c) is that case — an option ≈6% slower in Float64 on the test card was kept, the reversal tracing to that card's Float64 throughput rather than to the code. A carve-out claimed without a measured reason the test hardware is unrepresentative would just be the rule being ignored. The CPU path is not, however, a convenience for toy problems. It carries two roles that must not be confused. Development and small tests run on the CPU because that is where a workstation is, and at those grids performance rarely decides anything. The role the CPU path is tuned for is the other one: a single large CPU node, running the resolutions that do not fit one GPU's memory. Distributed and multi-GPU execution are out of scope (docs/ARCHITECTURE.md §1), so the ceiling is whatever one node holds — and on a CPU node that ceiling is high. A NAISS Arrhenius thin CPU node pairs two 128-core AMD EPYC 9755 processors with 768 GB of DDR5, a fat node carries 3 TB, and one GH200 in the GPU partition offers 96 GB of HBM. Counting one scalar field in either representation as 8 bytes per grid point in Float64 and a solver's live set at order 25 such fields, a single GH200 runs out near $768^3$ while a thin CPU node reaches roughly $1536^3$ and a fat node beyond it. The CPU therefore owns a band of resolutions no GPU's memory can hold, and inside that band it is the production platform, not a fallback. CPU multithreading (docs/ARCHITECTURE.md §9) is the mechanism that band rests on.

  • Measure before you optimize, and measure on the production platform. No optimization is kept without a same-session side-by-side comparison showing it helps the GPU. This session's record is instructive: of the candidates that looked like wins, polynomial-eval tuning was already free, the periodic-wrap hoist made the default scheme slower, and point sorting — the textbook locality optimization — regressed the GPU gather. Only the one the measurement pointed at (loop order) survived (§4). The lesson is the method, not those verdicts: both negative results were re-measured on current hardware in 2026-08-07 and reversed sign for the default scheme — which is the same principle applied twice, since a verdict is only ever about the platform it was taken on (§4(c)).

  • A benchmark run owns the machine, and a number is not a result until it is explained. Two obligations, both learned the hard way. Run benchmarks alone — no test suite, no documentation build, no second lane, nothing else on the host, and especially not while a GPU sweep is in flight. A device benchmark is host-bound at small grids (the synchronisation and, on the GPU path, the per-sample GC), so competing work inflates it by a roughly fixed amount per case; that alone invented a 2.2× "regression" at $64^3$, an inflated canary baseline (the frozen per-host regression-guard suite benchmark/regress.jl judges against; §7), and a phantom "environment shift" attributed to a driver, all in one session. Check uptime and the GPU's utilisation before starting, and wait rather than measure into a busy box. Then read what came back. Running a sweep and reporting that it completed is not a measurement: compare against the previous archive

(the saved per-sweep result file a characterization run writes; §6), state which operations moved and in which direction, and account for every systematic movement before naming a cause. The cheapest discriminator is whether a penalty is additive or proportional — a fixed offset that is constant in absolute time while its ratio collapses with grid size is overhead, not arithmetic — and the second is whether the same commit range moved the other backend, since a real code regression is not confined to one device.

A scope note carried from the architecture: platform optima diverge, so every result below is reported per platform, never as a single number. (The L²/measure reductions — integral, inner, l2norm, mean, …; docs/ARCHITECTURE.md decision 18 — are bandwidth-bound streaming reductions whose only subtlety is floating-point summation order, tolerance-tested rather than bitwise; they are now part of the suite, §5.)

2. The performance model

What bounds each public operation class — the mental model a benchmark either confirms or refutes.

  • FFT transforms (to_physical/to_spectral) → bound by FFTW (CPU) / rocFFT/cuFFT (GPU). The package adds only the normalization convention and the fiber-last layout (docs/ARCHITECTURE.md §3–4); the transform itself is the library's. Not something we tune — but the dominant cost of any spectral step, so it is benchmarked to track the libraries and our plan/layout overhead. The GPU libraries have no FFTW-style planner search, and the tuning surfaces they do have are currently out of reach from Julia — recorded here so nobody re-discovers them: cuFFT offers a patient-JIT plan property (LTO-finalized kernels — slower planning for faster execution) and LTO load/store callbacks that fuse user ops into the transform's own passes, none of it wrapped by CUDA.jl's FFT interface (cuFFT docs); rocFFT has an offline tuner producing per-size/per-architecture solution maps, not surfaced by AMDGPU.jl. The one reachable lever is rocFFT's ROCFFT_RTC_CACHE_PATH kernel cache (an environment variable; see §7 gap 6).

  • Field algebra (M2 + M3), the differential operators, and convolution → memory-bandwidth-bound. A fiberwise add, contraction, wavenumber multiply, kernel multiply (convolve), or arbitrary fiber map (map! — its adapter assembles the fiber in registers, adding no memory traffic over the named ops, so it tracks det!) reads and writes O(1) numbers per grid point and does O(1) flops on them — arithmetic intensity well below the roofline ridge. Consequence: on CPU, thread scaling saturates once the cores jointly saturate DRAM bandwidth (the plateau in §4); on GPU, the figure of merit is achieved bandwidth, not occupancy.

  • The grid↔point transfer (interpolate/anterpolate), local-stencil spline schemes → the subtle one. Each point gathers (or scatters) a $(2n{+}2)^3$ stencil ($n$ the spline half-width) with data-dependent indices, so it is bound by irregular memory access, and the binding differs by platform:

    • GPU: maximize memory-level parallelism — many distinct cache lines and DRAM banks in flight at once to hide latency (coalescing/occupancy). Scattered (unsorted) points naturally spread access and feed that parallelism. The corollary once drawn here — that the field is largely cache-resident at the grids we run, so little locality is left to win — is FALSIFIED. It reasoned from a retired card's 96 MB against a 67 MB $256^3$ scalar Float32 field; decision 78 then won $3.06\times$ by reordering for locality on that very grid (finding (ad)). A consumer's fields are often Float64 or rank-1, several times 67 MB, and no current card carries 96 MB.
    • CPU: bound by the cache hierarchy + hardware prefetchers, which reward locality — the opposite pull.

    This single fact — GPU wants spread, CPU wants locality — explains the platform-divergent results in §4 (loop order, sorting) and is the most important thing to internalize before touching the transfer. Hold it as a mechanism rather than a verdict: it explains why sorting can fail to pay on a GPU, and on the card that recorded that result it did. On the RX 7900 XTX the same experiment reversed for the default scheme (§4(c)), so the balance between the two pulls is a property of the card, not a constant.

  • Deliberately unbenchmarked, so the absence reads as a decision rather than a gap. Two public surfaces carry no row on purpose. The allocating constructors (decision 74) have none because an allocator's cost is the backend allocator's, and finding (y) records what a per-call field-sized allocation does to a row: it lands in a process-history-selected regime and stops being comparable across process shapes, so the row would measure the harness's memory history. Scheme persistence (decision 75) has none because it writes four HDF5 attributes and there is no persistence class to put it in — inventing one to time a constant would measure the library rather than the package.

  • Base-space motion (decision 73) → four rows in the transfer class (displace! one- and three-term, the three-term torus arity, and wrap!): $O(M)$ streaming over $(M, 3)$ arrays, bandwidth-trivial beside a gather — 30–300× cheaper than the CatmullRom gather at the same point count, which is the boundary-costs-nothing claim the rows document. The fused wrap is free in traffic (the torus row's counts equal the cover row's, pinned by the pass audit) but not in serial arithmetic: floating-point mod is compute-visible where one core does all the work ($256^3$-derived points, Float64: torus 7.0 against cover 2.2 ms at $t1$) and vanishes into bandwidth where the pass is memory-bound (1.41 against 1.24 ms at $t8$; 91.5 against 64.6 µs on the RX 7900 XTX). The fusion itself pays exactly there: at $t8$ the fused torus pass beats cover-then-wrap! by 33% (1.41 against 2.12 ms), and on the device by 22%.

  • The spectral transfer (DirectDFT/NUFFT) → a different cost class. DirectDFT is the exact $O(N M)$ double sum (compute-bound, no FFT, no window) — the oracle; NUFFT is its $O(N\log N + M)$ fast form, an oversampled FFT plus a windowed spread/gather, so it is FFT-bound in the grid size $N$ and carries the same irregular-access spread/gather as the splines in the point count $M$.

3. Best practices

Short checklists, each grounded in an external reference. Most are already enforced by the architecture or the tests; they are collected here so an optimizer has them in one place.

Julia (Julia Performance Tips; Modern Julia Workflows):

  • Type stability — non-concrete types force boxing and allocation. Checked package-wide by test/jet.jl (JET.@test_call).
  • Zero allocations in hot paths — an unexpected allocation almost always signals a type problem. Prefer the in-place ! forms; allocate scratch once and reuse. (@allocated/BenchmarkTools report it.)
  • @inbounds in kernels, isbits / SVector kernel arguments (so the spline coefficient matrices pass into GPU kernels by value, no device array), and fused broadcasts through _assign! rather than a bare .= (the codegen + threading contract, docs/ARCHITECTURE.md §9).
  • Allocate via similar/similar_field so results inherit the input's backend (the one-line reason a CPU-written method runs on a ROCArray unchanged).

GPU (ROCm/HIP performance guidelines):

  • No scalar indexing of device arrays (invariant 6) — checked under allowscalar(false) in both the test and benchmark GPU runs, but only when those are run: they need a physical device, they are opt-in, they are not part of Pkg.test(), and CI is manual-only. It is a guarantee the design makes and a check that confirms it on demand — not a gate a regression cannot get past. A scalar index introduced during CPU-only work stands until someone runs the GPU suite.
  • Favour spread access for memory-level parallelism, and loop the contiguous (x) axis innermost so per-thread stencil access is stride-1 (§4 measured this at up to 3.9×).
  • Minimize host↔device transfer; keep fields resident on the device. Allocate once, operate in place.

Methodology (BenchmarkTools.jl manual):

  • Warm up (compile) before timing; synchronize the backend — GPU work is asynchronous, so an un-synced timer measures launch latency, not the kernel (the suite's bench_sync).
  • Report the minimum of many samples (least-noise estimator) alongside the median.
  • Side-by-side comparison in one session: build both variants (baseline and candidate) and time them on identical data, back-to-back, in a single process — the only reliable way to resolve a difference smaller than the ~10% run-to-run variance (separate launches drift with thermal state, allocation layout, and cache).
  • Control the thread count (-t1 vs -t4), and always confirm on the GPU before keeping an optimization (platform divergence is real, §4).

4. What we have found

The transfer-layer results below were measured on an Intel i7-12700K (8 P-cores) and on a since-retired AMD card, Float32, ~1 point per 27 grid cells. That card is gone from the fleet and from RESULTS.md; what is kept here is the qualitative finding in each case, not its absolute numbers, and anything re-measured on the current cards (RX 7900 XTX, RTX 5070 Ti) says so explicitly. These are the cumulative results of the transfer-layer optimization work; the benchmark suite (§5) regenerates the tracked subset on demand.

Three things follow. The recorded occupancy mechanism is right, and $R = 3$ on the GPU is where it shows: 24 registers per thread turns a $2\times$ win at $64^3$ into a $2\times$ loss at $256^3$ as the working set grows and occupancy becomes the binding constraint. But it does not bite the default scheme on RDNA3 — CatmullRom hoisted is 10–30% faster at every grid, where the the retired AMD card recorded 10–14% slower. And the CPU, never measured for this, wins hugely and everywhere — up to $3.6\times$ — which is what the mechanism predicts: a CPU thread has no occupancy to lose, and mod by a runtime grid size is a genuine integer division rather than a compiler-strength-reduced constant. That matters because the CPU path carries the beyond-VRAM grids (ARCHITECTURE.md decision 37). On both backends the benefit shrinks as the grid grows and the gather becomes more latency-bound, converging toward 1 without crossing it for $W \le 4$.

Reopened, not adopted, and the caveat is load-bearing: these are standalone kernels sharing the package's loop order but not its spline weights, and the hoist is written with ntuple, which need not compile like the original attempt did. The ratios establish that the trade is worth re-examining on current hardware, not what the package's own kernel would measure.

  • Morton particle sorting (the textbook GPU-locality optimization): recorded as 0.5–1.0× on GPU (gather) — concentrating access kills the memory-level/DRAM-bank parallelism the GPU needs, and the field is cache-resident anyway — though 2.2–4.4× on CPU. That gather result does NOT reproduce on the RX 7900 XTX (re-measured 2026-08-07), and the question is reopened. Identical points, reordered only, at the same 1-per-27 density: Morton reaches 1.43× (Float32 $128^3$ CatmullRom, 105.7 → 73.6 µs) and 1.40× (Float32 $256^3$ trilinear, 116.8 → 83.4 µs), and helps in three of four cells for CatmullRom — the default scheme. One cell clearly loses, Float64 $256^3$ trilinear at $0.74\times$. The original was measured on a since-retired card, so this is plausibly an RDNA2-versus-RDNA3 difference rather than a bad measurement; either way the recorded range no longer describes the hardware the project runs on. It is reopened, not overturned, and three things must hold before it is adopted: the ordering must be rebuilt as points move (measured host cost 31.7 ms at $256^3$, paying back after 377 gathers; an on-device radix sort at an estimated 1–2 ms would pay back after 12–24, which is the number that matters and is not yet measured), the benchmark compares perfectly-sorted against perfectly-random while a real point set drifts between the two, and the companion scatter result below is unaffected and remains the larger objection. The companion atomic-free node-centric scatter is correct, conserving and bit-deterministic, but 6–24× slower on GPU: at our sparse 1-per-27 density it traverses ~27× more (empty) reverse-stencil cells than the atomic scatter touches particles. Sorting + node-centric deposition is a dense-particle (PIC) technique; wrong for this regime. (If deterministic anterpolation ever becomes a hard requirement, it is the available — slow-at-sparse — answer.)
  • Storing the Helmholtz denominator as a precomputed derivative-squared wavenumber family (rather than squaring $a$ in-register — decision 42 dropped exactly these arrays, and after decision 47 restored the gated CPU loop the question was whether to bring them back). Measured head-to-head, in-register vs a stored $a^2$ array, same projection otherwise: CPU in-register wins everywhere — Float64 $+4\%$ ($128^3$/$256^3$), Float32 $+10\%$ — because a register multiply of the already-loaded $a$ beats an extra stride-1 load, and the stored form keeps three more arrays resident. On the GPU in-register ties in Float32 but is $\approx 6\%$ slower in Float64 — and that lone reversal is a test-hardware artifact, not a production signal. The kernel is memory-bound (the F64/F32 time ratio is $\approx 2.1\times$ at $256^3$, tracking the $2\times$ byte ratio, not any compute ratio); the reason dropping three squaring-multiplies helps in F64 is that the RTX 5070 Ti's consumer-Blackwell FP64 runs at $\sim 1/64$ rate, so its FP64 ALU becomes co-limiting alongside memory and the extra multiplies tip it over. The production GPU is GH200 (decision 37 — Grace-Hopper, full-rate $1{:}2$ FP64), where that ALU has $\sim 32\times$ the F64 throughput and cannot be co-limiting on a memory-bound kernel — so the F64 case is expected to behave like F32 (a tie), and the stored array's extra reads to help nowhere. That is an inference from the memory-bound measurement and the known FP64 rates, not measured on a GH200 (none on hand). Even taking the $6\%$ at face value, capturing it needs a per-backend kernel split — re-introducing the two-bodies-in-sync coupling that produced the decision-47 dead-loop bug — for a win seen only on a card the production runs will not use. Kept in-register; the arrays stay dropped. This also retires the original (wrong) hypothesis that decision 42's in-register arithmetic cost the regression the canary flagged — it did not; the dead loop did (decision 47), and the arithmetic is free-to-favourable on every path that matters.

(d) Anterpolation and contention. The scatter costs ≈2.2–2.7× the gather (atomic read-modify-write + a full-grid prescale). On that RDNA2 card Float32 atomic-add was native but Float64 is emulated (CAS loop) ⇒ ≈1.3–1.7× slower; contention is worst at moderate clustering (~2 pts/cell), not extreme (extreme stays cache-hot).

(e) CPU vs GPU. The transfer threads on CPU through KernelAbstractions' CPU() backend with no code change, scaling ≈4.5–5.7× on 8 threads before the bandwidth plateau; the GPU is ≈9–22× the 8-thread CPU (≈ the 384-vs-~60 GB/s bandwidth ratio for the heavy schemes, more for the light ones via parallelism).

(f) Allocation-free in-place operators — the GPU hot-loop discipline. A pseudospectral solver applies the differential operators thousands of times in its time loop, so any per-call scratch an operator allocates internally matters. On the GPU it matters a lot: such scratch escapes Julia's GC (which triggers on host memory, while the scratch is device memory), so the device pool grows every step until VRAM fills and the run wedges (allocator spinning, GPU idle) or hipMalloc aborts — observed at 192³/256³. The fix made the in-place differential operators allocate nothing: _squared_wavenumber_broadcast (the $|k|^2$ coordinate) is returned lazily (an unfused Broadcasted, no $O(N^3)$ array), and the helmholtz_projection! / laplacian! / inverse_laplacian! kernels fuse their former temporaries into the component broadcasts — each now allocates $\sim 0$ bytes in place (measured; guarded by test/allocations.jl), with identical results. Payoff: a preallocated, in-place pseudospectral DNS step allocates nothing per step → no manual GC.gc()/reclaim, flat VRAM. The forced-HIT example (examples/gpu/rocm/HIST_ROCm.jl, 192³ Float32, $\mathrm{Re}_\lambda \approx 93$) sustains ≈ 34 ms/step (8000 steps, ≈ 270 s) on the retired card this way. Discipline for consumers: preallocate a workspace and use the ! forms with a destination distinct from the sources; the fiber norm/lpnorm deliberately materialize one field and are the exceptions (dev! left the list when decision 39 fused its trace into a register; use maximum(abs, …) for a CFL speed). [Decision 24; decisions 38/39 later retired the alias-guard copies — aliased in-place calls are now computed directly and stay zero-byte — and the decision-40 threaded reductions run on the same audit.]

(g) Allocation-bounded radial diagnostics — the same GC trap, in the binning. The same device-GC hazard as (f) lived in the diagnostics. The radial_spectrum / radial_correlation reductions binned by looping over the $|k|$- (or $|r|$-) shells and reducing a masked broadcast per shell. The shell count scales with the grid ($\approx \sqrt{3} N_a/2$, $\approx 220$ at $N_a = 256$, with $N_a$ the per-axis point count), and each iteration allocates a full-grid mask — and, because a mapreduce over a Broadcasted materializes on this GPU stack rather than fusing, the masked product too: $O(N)$ full-grid temporaries per call, which the host-triggered GC does not reclaim. A single $256^3$ radial_correlation snapshot churned several GB and wedged a 12 GB card at the first snapshot. The fix bins in a single scatter-add pass — one portable KernelAbstractions + Atomix histogram kernel atomically accumulating each element into its shell — so per-call temporaries drop from $O(N)$ to $O(1)$. Correctness is unchanged (same per-shell sums; CPU test/reductions.jl + GPU parity hold). Payoff: the $256^3$ Float32 forced-HIT example ($\approx 87$ ms/step) now runs to completion at a flat $\sim\!6$ GB ($\approx 8$ GB peak) through its snapshots, where the per-shell form wedged at the first one. The scatter contends on the small accumulator set, acceptable for an occasional diagnostic (not a per-step call); a privatized histogram is a possible future optimization. [Decision 25.] Decision 34 later fused the remaining $O(1)$ staging — the shell-index, magnitude, and weighted planes — into the binning kernels themselves (shell, fiber contraction, and Parseval weight derived per element from the index; the shell count analytic from the corner), taking radial_spectrum from three staged spectral planes per call to its $\sim\!1.4$ KB accumulator and leaving radial_correlation only its substance (the power field and the allocating inverse transform).

(h) FFTW ESTIMATE can badly mis-plan single-precision transforms — pass MEASURE for production. FieldTransformPlans builds its FFTW plans with the default ESTIMATE flag (instant, but it guesses the algorithm instead of timing candidates). On a Ryzen 9800X3D (Zen 5, stock FFTW 3.3.11) that guess is ~5× too slow for the 256³ Float32 transforms — in both directions, at every thread count — because its hardcoded single-precision codelet heuristics misjudge this CPU generation. It is size- and CPU-specific (128³ is fine; the i7-12700K shows no such inversion) — a classic ESTIMATE pitfall, not a package issue.

The inversion is Zen 5's; the mis-planning is not — corrected 2026-08-23 from a corpus-wide sweep of the committed table. Reading ESTIMATE/MEASURE as a ratio rather than looking for a Float32-slower-than-Float64 ordering, the i7-12700K mis-plans single precision too, at $256^3$/t1: 2.13× (to_physical scalar), 2.40× (to_spectral scalar) and 2.10× (to_physical vector), against $5.17$/$5.07$/$4.10×$ on the 9800X3D. Double precision is $1.20$–$1.46×$ on the i7 and $1.15$–$2.83×$ on the Ryzen. So the effect is precision-specific on both microarchitectures and merely three times worse on Zen 5. What is genuinely Zen-5-only is that it is severe enough to flip the ordering — on the i7 the ESTIMATE Float32 transform is still faster than its Float64 twin ($88.0$ against $127.3$ ms), so nothing looks wrong unless the measure twin is consulted, which is exactly why the narrower attribution was recorded. The sentence above stays true as written about the inversion; what changes is that "misjudge this CPU generation" must not be read as "and only that generation", and a consumer on any x86 CPU doing long single-precision runs should pass MEASURE.

This widens rather than narrows the ARM concern in §7 gap 8, which cites this finding as a Zen 5 artifact among the reasons no x86 CPU result transfers to aarch64. An ESTIMATE heuristic that mis-plans single precision on two unrelated x86 microarchitectures is more likely to do so on a third platform, not less — so MEASURE should be in the first Arrhenius measurement, not discovered there. The default stays ESTIMATE (cheap, deterministic, right for tests and short runs); the escape hatch already exists, FieldTransformPlans(phys, spec; fft_flags = FFTW.MEASURE) (or FFTW.PATIENT). MEASURE overwrites its input arrays while planning, so build the plans on scratch fields before seeding data. The forced-HIT CPU example (examples/HIST_CPU.jl) now plans with MEASURE. (m) exp producing a Float32 subnormal costs ~16× per element — and a fixed benchmark exponent measured exactly that. On x86 an arithmetic result in the subnormal band — between the smallest normal $\approx 1.2\times10^{-38}$ and the underflow-to-zero point $\approx 1.4\times10^{-45}$ for Float32 — is produced through a microcode assist: measured 37.1 ns/element, against 2.4 for a normal result and 1.2 for a full underflow to exact zero. For the lazy kernel $\exp(c\lvert k\rvert^2)$ the affected arguments, $c\lvert k\rvert^2 \in [-103, -87]$, form a spherical shell in $k$-space; the benchmark's former fixed $c = -0.1$ put ~11% of a $64^3$ grid's modes inside it, inflating the Float32 exponential_convolve! cell to 2.7–3.1× its Float64 twin (the blend $1 + 0.11 \times 15 \approx 2.6$; the sublinear $64^3 \to 128^3$ size step was the tell), so the row measured libm underflow handling, not the operation. The benchmark coefficient is now scale-aware — $c = -4/\lvert k\rvert^2_{\mathrm{corner}}$, the kernel spanning $[e^{-4}, 1]$ at every size — verified to close the $64^3$ type gap from 3.0× to 1.05–1.08×; cells swept before 2026-07-23 carry the old exponent. The operation keeps exact semantics (no flush-to-zero guard): Float64's band (arguments below $\approx -708$) is unreachable by physical kernels, GPUs flush subnormals natively, and a Float32 CPU consumer with a genuinely deep kernel — an aggressive Gaussian filter — pays the shell honestly; the exponential_convolve! docstring carries the caveat.

(n) The shell-binning atomics contend on an accumulator smaller than a dozen cache lines — threading inverts at small grids, and Float32 bins double the collisions. The radial family (radial_spectrum, radial_correlation, the co-spectra) ends in one Atomix.@atomic add per stored mode into a packed bins array of 56 ($64^3$) to 223 ($256^3$) entries — on x86 a CAS loop that must own the bin's cache line exclusively, so true same-bin contention (serialized retries) stacks with false sharing (different bins on one 64-byte line). A model scatter (4M adds, eight threads) reproduces the table: serial 4.6 ns/element; threaded over a $64^3$-scale packed bin array 17–19 ns — threading quadruples the per-add cost, the table's $64^3$ inversion (t8 1.3–1.6× slower than t1); Float32 packed at 223 bins runs 1.51× Float64 (16 bins per line versus 8 — the table's t8 type reversal, 1.44–1.5×); one-bin-per-line padding equalizes the types and finally scales at 223 bins (2.7–2.8 ns) yet still trails serial at the $64^3$ count (same-bin collisions, $\approx 8/56$ per add). At production sizes the mode reads are DRAM-bound and the contention hides, so the anomaly is confined to small-grid diagnostics costing single-digit milliseconds — recorded, not fixed. Read the ≈48× Float64 radial gap at both of its levels, which are not in tension: its mechanism is vendor hardware — RDNA emulates the global Float64 atomic with a CAS loop where NVIDIA has it natively, which is why the gap collapses to 1.11× in Float32 (§6) — while its exposure is an addressable implementation gap, because the global atomic scatter has no per-workgroup pre-reduction, the standard technique for exactly this kernel shape, and with one the emulated atomic would be hit a few times per workgroup instead of once per mode. Every other cross-vendor ratio in this document sits in the 1.5–4× band a bandwidth ratio explains; this one is an order of magnitude larger because the un-pre-reduced kernel runs straight into the one operation the two vendors implement most differently. Candidates when a consumer's cadence makes it matter: bin padding (backend-uniform; kills the Float32 reversal, not the $64^3$ inversion); per-thread private bins with an ordered merge on CPU (kills both and makes the CPU binning bitwise thread-invariant, retiring one of docs/ARCHITECTURE.md §9's two tolerance-tested accumulators, at the price of splitting the deliberately single-source KernelAbstractions kernel); workgroup-local bins on GPU — the same redesign's lever on the ~48× CUDA-over-ROCm Float64 radial gap (§6 and §7 measure it at 48–49× on the current archive), which is this kernel under RDNA3's CAS-loop Float64 atomics.

(o) An axis-factored kernel is bandwidth-bound like the stored kernel it replaces, so what decides its speed is how the per-axis product is INDEXED and how the launch is SHAPED — not how few streams it reads. Decision 50 stores a separable kernel (SeparableKernel) as three $O(N)$ per-axis factors instead of an $O(N^3)$ field, which removes one field-sized stream from every application (three down to two). That alone predicts a speed-up; it does not deliver one, and the two failed attempts are the instructive part. Handing the lazy product to the linear-indexed fiberwise executor makes every element convert a linear index to a cartesian one — an integer division, emulated on a GPU — measured 0.29× a stored kernel (vector, $256^3$, Float64, RTX 5070 Ti). Replacing that with a hand-written three-dimensional KernelAbstractions kernel removed the conversion and gained nothing (0.78× vector) while halving the scalar case to 0.55×: the folded axis is $N/2 + 1$ — 129 at $256^3$ — so a three-dimensional launch fragments warps against a row length that is not a multiple of the warp size, where the stored path's flat launch stays coalesced. What works is the plainest form, one flat broadcast over the whole section with the factors carrying singleton axes (they extend along the remaining mode axes and along the fiber): cartesian indexing and a flat, coalesced launch.

The CPU needs the opposite route, and the same measurement says so. That five-operand broadcast, three of whose operands carry singleton axes, does not vectorize: it ran at a fixed ~330 M elements/s — the same rate in Float32 as in Float64, the signature of an element-bound loop rather than a bandwidth-bound one. So the CPU takes a gated hand-written twin (§9's kernel-pair shape): the two outer factors hoisted to scalars, leaving an inner pass over contiguous storage for @simd. Loop order in that twin is worth stating, because the obvious choice is wrong — with the fiber components innermost the pass jumps between component blocks every row and the threaded case fell to 0.98×; walking each component's block start-to-end inside a thread's slab restored 1.14×.

The Float64 GPU column is a consumer-card artifact, not the production case. The same split applies to the kernel-composed combine!, which initially kept the linear-indexed route and so ran the rejected shape at $R \ge 1$ — measured at roughly a third of the stored kernel's speed until it took the cartesian routes as well, after which it is 1.1× faster than the stored kernel at $256^3$ threaded. A kernel storage class is only as fast as the slowest entry point that accepts it.

The radial class of decision 51 (RadialKernel) takes the same two routes, for the same reason. A kernel depending on the mode only through $|k|^2$ stores no coefficients at all — a symbol closure and three references to the squared-wavenumber rows — so it removes the same field-sized stream, and its arithmetic is one extra add plus the symbol evaluation. Everything above transfers: a device takes the flat broadcast, a CPU takes the gated component-major twin, and both index the wavenumber axes cartesian. The one addition is an ordering constraint the separable class does not have. The squared wavenumber must be summed $(\kappa_1^2 + \kappa_2^2) + \kappa_3^2$, matching the left association the broadcast itself uses, or the compressed and stored paths agree only to rounding rather than bit for bit — and the suite asserts the stronger form.

The symbol is a closure, and it must capture values rather than a type. Capturing an element type — writing one(T) inside the closure with T closed over — makes the captured object a Type, which is not a bitstype, and a GPU launch rejects it outright. Hoist the constants to values before the closure is built.

Three rules generalize. Reach for the broadcast route before a hand-written kernel on a device — §9's execution-route policy, here vindicated by measurement, since Julia's broadcast machinery chose a better launch than the hand-rolled kernel did. A broadcast over singleton-axis operands is the exception on a CPU, where it does not vectorize and a hand-written twin is worth its keep. And when a fused pass underperforms, measure the launch shape and the traversal order before blaming the arithmetic — both failed attempts here were layout problems wearing an arithmetic costume.

That is a workaround, and it sharpens the diagnosis rather than closing it. The fault is unchanged and a plain -t8 invocation still dies here. But a fresh process doing only $128^3$ also crashed, 2.5 minutes in, so the trigger is not simply a long-lived process accumulating state; splitting helps because it shortens each exposure and makes a retry cheap, not because it removes the hazard. Combined with the crash point moving between attempts, the fault reads as a low-probability race whose rate rises with the number of threaded transform executions — which is why the small grids, with their enormous call counts per second, are where it keeps landing.

The conditions, tabulated from five crashes — and the four things that are NOT enough. The tally is five because the four failures of the single-process lane (three on 2026-08-09, one on 2026-08-05, against one success) are joined by a fifth from the split run of 2026-08-10, whose $128^3$ process crashed on its first attempt before succeeding on its second. Every crash on record shares four properties: -t8 (FFTW's thread count tracks Julia's, so eight workers; -t1, -t2 and -t4 have never failed across many lanes), the host Enteropia, the reductions class — five times out of five, never fft, algebra, operators, convolution or transfer — and a small or middling grid ($128^3$ four times, $64^3$ once, never $256^3$ or $512^3$, though that last is partly survivorship because the monolithic lanes died before reaching them). What it is not is an accumulation threshold: the allocation counter at death spans 158M to 1071M and the collection count 1753 to 14598, a sevenfold spread on both.

Four reproduction attempts at -t8 on the failing host all came back clean, and each one narrows the cause: 2,400 radial_correlation calls; twelve rounds of build → run → drop → GC.gc(true) over fft, transfer and reductions; five rounds of the reductions class alone at the exact crashing cell; and the full Pkg.test() suite. So neither the operation, nor plan churn, nor the class, nor eight threads is sufficient on its own.

What every real crash had that none of those had is the rest of the process. In each one, fft, algebra, operators, convolution and transfer had already run before reductions was reached — and fft is the class that builds the most plans, including the measure twins that invoke FFTW's timed planner. That is the exact window FFTW.jl documents, quoted below: the collector may run during the spawnloop callback while the planner is executing. Its deferred plan destruction and GC.safepoint() spin exist to stop that deadlocking; a segfault is the other failure, the shape of a plan freed by its finalizer while another thread is still executing it. The working description is therefore a low-probability race, per threaded transform execution, whose window is opened by earlier planner activity in the same process — which explains both why the small grids catch it (their call counts per second are enormous) and why splitting the lane helps without fixing anything.

Separately, the package itself is fine at eight threads. Pkg.test() under JULIA_NUM_THREADS=8 passes in full — 6182 tests across 92 testsets, zero failures, identical to -t1 and -t4 — so this is not a general $-t8$ hazard for a consumer, and the CI matrix's -t1/-t4 pair is not hiding a broken configuration. It is the sustained benchmark lane, with its millions of small threaded transforms, that finds the race.

What the attempt did establish. FFTW.jl's own source documents this interaction zone: "the garbage-collector may run at unexpected times. For example, it may run during the spawnloop callback while the FFTW planner is executing", and it carries deferred plan destruction plus a GC.safepoint() spin specifically so that case cannot deadlock on the fftwlock. A segfault is a different failure from the one that machinery guards, and the shape that produces one is a plan being destroyed by its finalizer while another thread is still executing it — a use-after-free reached through spawn_apply. That is consistent with every recorded detail: it needs plan lifetime to overlap execution, it needs the collector to run at an unlucky moment, and it appeared only in the -t8 lane, the one driving the callback with eight workers.

What it does not establish. A non-reproduction bounds the rate, it does not clear the code: under adversarial conditions the fault is rarer than about 1 in 50,000 transforms on this host, against an original of one occurrence in one 30-minute lane. The crash was also seen on Enteropia (9800X3D) and this attempt ran on Aiporetne, so a host-specific trigger is not excluded.

The mitigation, if it ever bites a consumer, is known and is not free. Building plans under set_fft_threads!(1) removes the callback entirely — the thread count is fixed at plan-build time (finding (t)) — and also removes that finding's per-call allocation. The cost is real: FFTW threading is worth about $2\times$ at $256^3$ on the 12700K (to_physical scalar Float64, 153.4 ms at -t1 against 78.2 ms at -t8), so this is a robustness-for-throughput trade to make deliberately, not a default to change.

The hoist was prototyped, measured, and DECLINED. The $R = 0$ column gains, but $R = 0$ never paid the fiber penalty in the first place — that gain is over the broadcast machinery itself, at a tensor order with no fiber to extrude over.

The premise behind wanting the fix was also wrong, and measuring is what showed it. A traffic count says the radial class should beat stored by $1/(2R+1)$ — about 14% at $R = 1$ — and that the recompute was eating it. At $256^3$ Float64 the radial broadcast measures 41.9 ms against stored's 45.0 ms, already 6.8% ahead: it is realizing its memory saving at production scale, and there was no forfeited 14% to recover. So the penalty is real but confined to the regime nobody ships in. It appears at $64^3$ and serial, where the pass is compute-bound; the CPU path's tuning target is the beyond-VRAM band (ARCHITECTURE.md decision 37), and there the radial class is already the faster of the two. Decision 51 stands as measured: $O(1)$ builders, competitive application at production grids, and a small-grid compute penalty that no reasonable fix removes without costing more elsewhere. No change is warranted, and the pass audit's separate $\hat w$ extrusion holder should be re-priced against this result before anyone acts on it either.

That runs a full GC.gc() before every sample, whose finalizers free device buffers and synchronize the device — a cost that lands on a measurement whose operation is tens of microseconds. Measured A/B on the RX 7900 XTX, Float64, the whole convolution class run through the suite's own code with only that one parameter changed:

  • $128^3$: inflation $5.8$–$19.8\times$ (convolve! scalar 1.128 ms against 56.9 µs)
  • $256^3$: inflation $1.9$–$4.25\times$ (convolve! vector 2.494 ms against 1.218 ms)

The gcsample = true figures reproduce the committed archive to within a few percent, which is what identifies the archive as this regime rather than some other.

The tell was visible in the table all along. With the overhead in, convolve! scalar and convolve! vector at $128^3$ read 1.094 and 1.177 ms — a 3× difference in bytes moved appearing as 1.08×, because both were dominated by a shared ~1 ms floor. With it out they read 57 and 182 µs, a ratio of $3.2$ that matches the data volume. A device column whose scalar and vector rows nearly coincide is not measuring the device.

It is not a uniform scale factor, so it corrupts comparisons within a column too. The inflation varies per row ($1.94$–$4.25\times$ at $256^3$ alone), and at least one documented conclusion reverses when it is removed: convolve! vector ∘ radial against ∘ stored reads $1.48\times$ slower for the radial class at $256^3$ with gcsample, and $0.90\times$ — faster — without it, with the same flip at $128^3$. The claim recorded in bd1e4f30 that decision 51's trade "has opposite sign on the two vendors" is retracted: it rested on a probe that also ran gcsample = true, and the apparent sign came from two rows being inflated by different factors ($9.5\times$ against $5.8\times$), not from the kernels.

Scope. gcsample is gated on USEGPU in both harnesses, so CPU columns and CPU canary baselines are clean and every GPU column of RESULTS.md — all four cards, every grid — plus both hosts' GPU canary baselines are affected. Cross-card GPU comparisons are affected twice over, since each vendor's free-and-synchronize cost differs; the recorded "RTX 5070 Ti is ≈1.8× the RX 7900 XTX" was not safe to rely on until re-measured, and on re-measurement (both cards, fixed regime) it fell to 1.09× in Float64 at $256^3$ — see the resolved cross-card entry in (v).

Why it was there, and why deleting it was not the fix. It was added deliberately (2026-06-11) because the reductions class wedged the device: lpnorm materializes a magnitude field per call, BenchmarkTools' sampling loop does almost no host allocation, so Julia's GC never fired, and the AMDGPU pool grew until the allocator spun. That failure is real, and a bare gcsample = false reinstates it.

The fix, landed and validated: gcsample is now decided PER ROW, by measurement. Only a row that creates device arrays fast enough to exhaust the pool within its own trial needs the per-sample collector, and _apply_gcsample_policy! in characterize.jl finds those rows rather than assuming them. Each row is warmed up, then run with the collector disabled while the device pool is watched; the growth is projected over the trial from the row's own per-call time, and a row projected to exceed 2 GiB keeps gcsample. Host bytes cannot serve as the signal — a KernelAbstractions launch allocates host bytes per call, so a first attempt using them classified every launching row as allocating and changed nothing.

The probe's own output is the evidence it works, because it independently reproduces invariant 13. At $128^3$ it measures 0.0 MiB of pool growth for every in-place operation and finds exactly the documented materializers: lpnorm 144 MiB, radial_correlation and the cross-correlation 1310 MiB, the spectral inner's $O(N^2)$ correction planes 13.5 MiB, materialize_kernel 146 MiB. That list was written from the code years before this probe existed, and the probe was not told it.

Validated on the case the setting existed for. Running characterize.jl itself over convolution and reductions at $128^3$ and $256^3$ Float64: it completes without wedging, keeps gcsample on exactly six rows (the two materialize_kernel rows and the four documented reduction materializers), and the in-place rows recover their physics — convolve! scalar against vector reads 57.3 against 181.0 µs, a ratio of $3.16$ matching the data volume, where the archive read 1.094 against 1.177 ms. The figures reproduce an independent gcsample = false measurement to within 1%. CPU lanes are untouched, the policy being gated on the backend.

The probe could wedge the card it was written to protect, and did. It runs GC-free, so its first version's fixed eight calls were themselves an unbounded allocation: transfer at $256^3$, whose NUFFT allocates oversampled work arrays per call, filled the pool and hung a re-sweep for two and a half hours with VRAM at 99%, device activity at 0%, and one core spinning in the allocator. The catch-based fail-safe did not fire because a wedge is a hang, not an exception. The probe is now bounded by memory with an early exit — one call at a time, stopping the moment growth passes 512 MiB, which is already decisive — so its peak use is that ceiling plus one call rather than the pool. SIGTERM did not reach the spinning process; SIGKILL released the pool cleanly and the archive survived, characterize.jl writing its JSON only at the end.

An allocating row need not pay a GC per sample either. Since the probe measures per-call growth, samples is capped from it (a 4 GiB budget, evals pinned to 1) and the row runs GC-free with a bounded pool. This matters because the user-facing transforms allocate their result by definition, so the whole device fft column was otherwise still timed on the collector. Only a row whose single call is too large to repeat — the vector transforms, at ~400 MB each — keeps the per-sample GC. A capped row's parameters are deliberate and must not be passed to tune!, which would search evals upward and undo the cap.

The second test was meant to catch a capped row, which reports allocating = false but has had evals pinned to 1 — except that 1 is also BenchmarkTools' untuned default, so the test matched every row in the suite and tune! ran on none of them. Its footprint is bounded, confined to the fastest rows, and MEASURED — it is 6–8% on three of them. (t) A threaded FFTW plan allocates Julia-side task state on every call — size-independent, nondeterministic, and fixed when the plan is BUILT rather than when it is called. The 2026-08-04 survey run reported to_spectral! allocating 8–12 KB per step on odd grids under permuted layout folds, which invariant 13 would make a per-step leak. It is not one, and the package is allocation-free there.

FFTW.jl reaches its worker threads through a Julia callback, so a plan built with more than one thread allocates task state per transform call. Three properties identify it as harness rather than scratch:

  • Size-independent. The same 7008 B/step for a 12 KB field and for a 2.6 MB one, over grids from $8^3$ to $48^3$. Field-sized scratch would scale; this does not.
  • Nondeterministic. The same configuration measured 7008, 10464, 23173 and 48557 B/step on different runs, since the number of tasks actually spawned varies with scheduling.
  • Set at plan-build time. A plan built under set_fft_threads!(1) measures exactly 0 B/step even when called from a four-thread session, while one built under four threads measures 7008 in the same session. Restoring the setting before the call changes nothing.

The value also depends on the layout fold — 7008 for the default and $(2,1,3)$, 10464 for $(3,1,2)$ — which is what made it look like a permuted-layout defect. It is the plan's stage count, not the package's code path.

The gate was already right and the survey was not. test/allocations.jl bounds this class with $4096 \times$ the thread count, which is why it passes at -t4; the survey's sequences lane used a purely field-proportional bound, so a constant several-kilobyte cost overran it on the small fixtures. The lane now builds a dedicated single-threaded plan for the allocation measurement — the only place the cost can be removed — and reports 0 B/step deterministically across repeated -t4 runs, with the tight field-proportional bound kept for detection power. Raising the bound would have been the wrong fix: it would have set a threshold against a quantity that varies 7× run to run, which is how a harness stops measuring anything.

(x) The storage class, measured at last: the identity is free, and the two bus directions are not symmetric. The class decision 63 added was swept on the RTX 5070 Ti on 2026-08-17 (42 rows, $64^3$ to $256^3$, both element types) and says three things.

Adapting to the family a section already lives in costs $118$ ns, flat. (z) A fused multiply-add is not faster here, and writing one to force cross-backend agreement was declined (2026-08-26). The CUDA parity suite found decision 73's displace! disagreeing with its CPU twin in the last bit. The cause is compiler contraction, established rather than assumed: the device folds x + c * v into a fused multiply-add — one rounding — where the host multiplies and then adds, two. On CUDA the device result equals the host's muladd form exactly, in both precisions and for the two-term call, and the host's own plain-against-muladd mismatch count (151 of 900 in Float64, 136 in Float32) matches the device-against-host count element for element.

The obvious repair is to write muladd on the CPU side so both contract identically. It was measured on all three grounds and fails on each.

  • Speed: none. The pass reads three arrays and writes one, so it is bandwidth-bound and the instruction count of the innermost expression is invisible behind the traffic. On the 9800X3D the ratios are 0.998 at $3 \times 10^5$ elements and 1.010 at $1.7 \times 10^7$ in Float64, 1.006 and 1.051 in Float32; at 900 elements, amortized over a thousand inner repetitions to clear the timer floor, 0.964 and 0.970 — two nanoseconds of a forty-six nanosecond call. On the 5070 Ti it changes nothing at all (0.999 and 1.003 at $1.7 \times 10^7$), which is the expected result and worth stating: the device already emitted the fused instruction, so naming it in the source cannot move anything.
  • Accuracy: a better bound, not a better answer. Against a BigFloat reference the maximum error improves from $8.99 \times 10^{-16}$ to $7.95 \times 10^{-16}$ in Float64 and from $5.09 \times 10^{-7}$ to $4.54 \times 10^{-7}$ in Float32 — one rounding per term rather than two. Element by element it is not uniformly better: over 30,000 elements per type it wins 3162 and loses 1800 in Float64, wins 3116 and loses 1765 in Float32. A luckily-cancelling double rounding can land closer than a single one.
  • Footing: the agreement is a vendor coincidence. It holds because the device compiler contracts and associates exactly as muladd does, which is documented nowhere. A future release changing contraction policy would reopen the divergence and turn a bitwise assertion red with nothing anyone could act on. That is the objection invariant 14 raises against resting a package guarantee on a vendor's behaviour, and it applies here as squarely as it does to a method table.

Scope decides the rest. The package uses muladd nowhere, and the pattern is systemic — eight alpha_beta codegen sites plus the explicit $\alpha a + \beta b$ expressions in FiberSections, Points and Convolution, since the accumulation of invariant 10 is two multiplies and an add. So adopting it in displace! alone would fix the line rather than the class, and adopting it across the class is a numerics-changing sweep of every in-place operator, invalidating pass-audit and benchmark baselines, in exchange for a bound. The comparison moved to a tolerance instead, which is what TESTING.md already prescribed across backends.

(ad) The transfer was spending most of its time on cache misses it did not need, and on integer division (2026-08-30, user-directed). Two independent changes, measured on an RTX 5070 Ti and a Ryzen 9800X3D at the regime a consumer actually runs — $256^3$ grid, $10^6$ points, CatmullRom.

the walk keeps six live indices across the nest and makes each index depend on its predecessor, where mod computes all of them independently, and at width 8 × 3 components that serial chain and its registers cost more than the divisions saved. Building the order cost 0.098–0.13 ms on device against a gather it saves 1.7 ms on, so it repays inside a SINGLE transfer — where the estimate it replaces guessed 12–24, having assumed a vendor sort. Validating the permutation (the adversarial review below) roughly doubled that to 0.24–0.27 ms, which still repays six times over in one transfer; the figure is quoted post-validation everywhere else, since that is the code that ships. It is not a sort: a counting pass over blocks of cells, three portable kernels, no new dependency. The vendor sortperm over the same keys costs 2.8 ms, $25\times$ more.

Three things were measured and NOT adopted, which is the more useful half.

Morton order loses to plain lexicographic tile order (3.10 vs 3.49 on the $256^3$ Float64 scatter), and the same result is published: Domínguez et al. (2011) find lexicographic beats Z-order in SPH and name the discriminator — Morton wins where cell access is RANDOM, lexicographic where it is a sequential sweep, which a sorted stencil transfer is. The recorded plan had assumed Morton.

Stability within a bucket buys nothing, within noise everywhere but one cell, so the atomic placement stands and no backend split was built for it. One bucket per cell is not better and costs $14\times$ more to build (1.55 ms against 0.11 at $256^3$), the $16.7$ million buckets dominating the cumulative sum; including the build, the default 4 is optimal on both backends.

Where it does not pay, which the option exists for. At $64^3$ with $10^5$ points every backend is launch-bound and building an order for one transfer loses ($0.9\times$ including the build). On CPU at Float32 scalar the field is small enough to sit in a 96 MB V-Cache, so there is little to win and the order's own scattered reads of the coordinates cost more than they save.

And the headline ratios measure the INPUT, not the method — the sharpest correction an adversarial re-measurement produced, since every figure above was taken with uniformly random point positions, which is the worst possible order. Re-seeding the same count four ways (Float32 vector gather, $256^3$, $10^6$ points): uniformly random $12.28\times$, a lattice in sweep order $0.93\times$, a lattice jittered by one cell $0.98\times$, and a lattice advected far enough to decorrelate $5.09\times$. The ORDERED arm barely moves across all four (0.313–0.433 ms) — the traversal order normalises the access pattern — while the baseline varies eighteenfold. So the honest span for a consumer is $0.93$–$12\times$, and what the option repairs is a bad order rather than improving a good one: a lattice-seeded set runs the UNORDERED kernel faster than any ordered configuration. The docstring's original justification — that a solver's seeding order is usually unrelated to the grid — was backwards for a sweep-seeded set and has been corrected. The traversal order gives locality to the FIELD reads and takes it from the COORDINATE reads, which is why it grows with tensor order — a vector field reads three components per point against one coordinate triple.

5. The benchmark suite

A standing suite under benchmark/ (sibling of test/), opt-in — not part of Pkg.test(), exactly like the GPU tests. A call to build_suite(; array_type, types, sizes) builds a BenchmarkTools.BenchmarkGroup parameterised by the device array type (Array on CPU; CuArray/ROCArray on GPU — the same approach test/gpu/suite.jl uses with to_device), so one suite runs everywhere. A bench_sync blocks the backend so BenchmarkTools times GPU work to completion. Every row that writes to a device buffer synchronizes it, including the transfer rows: relying on a driver's internal synchronization is what left NUFFT anterpolation's final assignment outside its own measurement, and a benchmark should assume nothing about where a driver happens to block.

The resolution class (decision 85) measures what no other class does: an operation whose cost is set by a field the caller does not pass as its destination. Both embed_modes! and extract_modes! walk the COARSE field, so their rows should follow the coarse grid and barely move as the swept grid grows; a row that tracks the sweep instead is the regression the class exists to catch, a pass over the fine field. Two ratios are swept per lane, a fixed small block and a half-sized coarse grid, because an index map can be right at one ratio and wrong at another. The rows enter RESULTS.md at the next sweep, src/ having moved with the decision.

Classes covered: FFT transforms (each CPU row with a measure twin planned via FFTW.MEASURE, so the default-ESTIMATE experience and the tuned production path sit side by side and finding (h) is re-measured per host/size/type on every sweep; GPU rows have no twin, the device FFT libraries taking no planner flag; plus, per scalar/vector, the decision-64 pair — the preserving scratch arity of to_physical! and the destructive three-argument baseline it is priced against, whose delta is the cost of preservation), field algebra (M2 + M3, representative — including the weighted combination combine! and the determinant det!), differential operators (including the fused symmetric_gradient! and the kernel-composed helmholtz_projection!/divergence! forms of decision 32, whose baseline is the sequential operator + convolve! pair they replace, and the reality projector reality_projection! of decision 83, scalar and vector — an $O(N^2)$ row beside the $O(N^3)$ ones, priced in place), convolution (convolve! scalar/vector, the lazy exponential_convolve! — its exponent scale-aware, so every size measures the streaming pass and not the Float32 subnormal band (finding (m)) — and the kernel-composed combine! of decision 33 — their baselines the stored-kernel convolve! and the sequential combine! + convolve! pair — + the builders spectral_cutoff / spectral_band / radial_kernel / assignment_window / translation_kernel — a builder is paid once and its kernel applied many times, so it is swept for regressions, not for hot-path cost, and a builder returning a compressed kernel is timed on one factor rather than a field it never allocates — the spectral_cutoff and spectral_band rows previously wrapped their builder in materialize_kernel and so reported an $O(1)$ lazy build at the cost of an $O(N^3)$ materialization, with neither trackable on its own). Each compressed kernel class is additionally swept against its materialized twin at the point of application — convolve! on a vector field with the kernel axis-factored, radial, and stored — since the classes compute the same coefficients and only their cost differs, so the stored form is the baseline that makes a storage change legible (finding (o)). The class OPERATIONS join it: the general radial_kernel builder against the two named bands, materialize_kernel on both compressed classes (the escape hatch allocates the $O(N^3)$ field the classes exist to avoid, so its cost is what a consumer trades away by materializing), the in-place translation_kernel! against its allocating sibling, and inv — whose row doubled when decision 56 gave it a zero policy, and deliberately so: that guard is three $O(N)$ reductions over the axis factors, measured at 40.6 µs on an RTX 5070 Ti against a 9.5 µs reciprocal, so it dominates the operation. It is accepted rather than optimized away, because a kernel is inverted once and applied many times — this class is swept for regressions, not for hot-path cost — and because the alternative is returning a non-finite coefficient that poisons every later result. Read against an archive from before 2026-07-30, that step is the guard, not drift. Then the interpolation/anterpolation transfer (the spline schemes plus the spectral NUFFT; the exact DirectDFT is its oracle, not a swept regression target), and the L²/measure reductions (integral/mean/inner/l2norm/lpnorm/maximum, the covariance tensor cov — the one reduction whose result is fiber-valued at $R = 2$, so it streams a vector field and writes nine accumulators — the scalar-only var in both representations, which prices what skipping the transform is worth (decision 49 gave it a Parseval form), the fused multiplier-weighted weighted_inner, the spectral Parseval inner, the spectral zero-mode integral/mean (an O(1) DC-coefficient read, not a streaming reduction), and the radial reductions radial_spectrum / radial_correlation plus the two-field co-spectra radial_spectrum(f, g) / radial_correlation(f, g) — a single scatter-add shell-binning pass and an inverse rfft, diagnostic-cost; the co-spectra cost the same as the single-field forms, sharing their binning), including the mapped forms maximum(norm, u) / mean(norm, u) / mean(det, A) / mean(tr, A), whose maximum(norm, u) row pairs with the lpnorm vec Inf row as a direct A/B — the same quantity, one materializing a magnitude section and one not.

Storage-family moves (adapt, decision 63) are the seventh class, and the only one whose cost is a link rather than a device: a host↔device copy is bounded by the bus, so it does not improve with the card and does not scale like anything else in the table. The class is device-only and empty on a CPU lane — adapt to the family one already occupies is the identity, so a host row would time a no-op and report nanoseconds as though a transfer had happened. It sweeps both directions separately (they are not symmetric on any real link), the identity case (so that its being nearly free is visible rather than merely asserted), the multipliers (six $O(N)$ axis vectors, so latency-bound where the field rows are volume-bound), and adapt on a FieldTransformPlans, which is not a transfer at all but a planning pass on the target and is priced separately for that reason. The practical guidance the class exists to support is unchanged by any of its numbers: a solver should cross the bus during setup and stay resident, because a per-step transfer of a $256^3$ Float64 field is tens of milliseconds against the tens of microseconds its operations take.

The tracked SUITE uses modest grids (64³, 128³) for fast, repeatable, regression-sensitive runs; the large characterisation sweep behind §4 (256³/512³) is reachable with build_suite(; sizes = (256,)). Manifests are gitignored (repo convention); each environment reproduces from its Project.toml.

The coverage contract. Every public operation class is benchmarked (representative members) over {Float64, Float32} × {representative grid sizes} × {CPU -t1, CPU -t4, GPU}, unless a class has an explicit exemption with its reason — the storage class of decision 63 is device-only, because adapt to the family one already occupies is the identity and a CPU row would time a no-op. New code adds its benchmark to the matching per-class file — the performance analogue of the test coverage contract (TESTING.md §4).

An adjoint pair is two configurations, never one. Where an operation ships as a pair — the transfer's interpolate and anterpolate, the transforms' to_spectral and to_physical — an axis the two verbs share (the scheme, the stencil width, the grid, the element type) counts as swept only once it has been swept on each verb. This is the twentieth axis of TESTING.md §4, recorded in both places because a benchmark sweep is what taught it: finding (ad) varied the scheme on the gather and left the scatter pinned at CatmullRom, so the width-8 scatter was never measured at any width, and it is that cell which regressed $1.45$–$1.48\times$ at $512^3$ and shipped for two days before the history scan found it (finding (am)). A one-verb sweep does not license the sentence "the scheme axis is covered".

6. Tracking regressions, and per-platform results

Workflow (manual, BenchmarkTools). Save a baseline, then judge a later run against it on the minimum-time estimates:

julia --project=benchmark benchmark/runbenchmarks.jl save results/cpu-baseline.json
julia --project=benchmark benchmark/runbenchmarks.jl judge results/cpu-baseline.json   # :regression / :improvement / :invariant

Because CI runners have no GPU, GPU tracking is manual: run the GPU suite on the device and record the numbers here. Adding a platform = mirror benchmark/gpu/rocm/ (a Project.toml + a 2-line runbenchmarks.jl); the suite needs no changes.

Two scales. The tracked SUITE (runbenchmarks.jl, grids 64³/128³) is the quick, regression-sensitive run used with save/judge above. The exhaustive characterization (benchmark/characterize.sh) runs the full matrix — every op-class (including FFT) over each backend's default grids (CPU 64³–512³, device 64³–256³, since a device cannot hold 512³ in Float64), on the CPU thread sweep 1/2/4/8 (powers of two up to the performance cores) and the GPU — building one (grid size, element type) at a time to bound memory (a 256³ Float64 tensor field is ~1.1 GB; holding all classes for both types at 256³ overflows the 12 GB GPU — gap 6), and assembles it into the committed report benchmark/RESULTS.md (the raw per-run JSON under benchmark/results/ is gitignored). Regenerate it on any platform with that one script; it stamps the date, commit, and host. The characterize.jl sweep additionally stamps each archive JSON with its own measurement vintage (commit=/measured= BenchmarkGroup tags), and report.jl prints the per-column vintages in the header — so a column measured at an older commit is visible as such instead of silently inheriting the report's HEAD (the 2026-07-22 decision-40 reductions skew, one host's archive swept hours before a threading feature landed, is the motivating incident).

7. Current coverage and known gaps

Covered: the public operation classes (FFT, algebra, operators, convolution, transfer, reductions; the device-only storage class of decision 63 is wired into the suite but has not yet been swept into the committed archive — see gap 7) parameterised by element type and grid size, runnable on CPU (-t1/-t4) and GPU (ROCm or CUDA) through one device-parameterised suite; the manual save→judge regression workflow; and the exhaustive characterization (characterize.sh → committed benchmark/RESULTS.md): every op-class (incl. FFT) at each backend's default grids (CPU 64³–512³, device 64³–256³), across two CPU 1/2/4/8 thread sweeps (i7-12700K, Ryzen 9800X3D) and two GPUs — RX 7900 XTX (gfx1100, ROCm) and RTX 5070 Ti (Blackwell sm_120, CUDA); the 7900 XTX is extended to a 512³ Float32 point for the bandwidth-bound classes, and the 9800X3D sweep covers 64³–512³, both element types, all classes — the first data in the CPU production band of docs/ARCHITECTURE.md decision 37 (a 512³ Float64 CPU sweep needs tens of GB of host RAM, which a 123 GB workstation clears with room to spare; it was these lanes that exposed finding (l)). The decision-27 additions (combine!, det!, symmetric_gradient!, weighted_inner) are wired into their classes and CPU-verified (0 allocations for combine!/det!/symmetric_gradient!; the small bounded guard for weighted_inner); they enter the committed RESULTS.md table on its next GPU-host refresh. Done (2026-07-21): both GPU archives are refreshed — the RX 7900 XTX (2026-07-20) and the RTX 5070 Ti — so every decision-27/32/33/34 row (combine!, det!, symmetric_gradient!, weighted_inner, the kernel-composed helmholtz_projection!/divergence!/combine! arities, exponential_convolve!, and the fused radial diagnostics) now carries both GPU columns at 64³–256³, both element types. The refresh also re-confirmed the §6 atomic-scatter contrast on the fused decision-34 kernels: radial_spectrum vector Float64 256³ is 54.973 ms on the 7900 XTX against 1.144 ms on the 5070 Ti (the figures §6 and §4(v) carry; this paragraph's earlier 65.95/1.371 pair predated the §4(s) per-row GC repair and is superseded) — a ~48× CUDA lead on what is now a pure scatter-add (its staging planes are gone, so the atomics are the whole story).

Gaps:

  1. CLOSED — the device rows no longer carry a blanket per-sample GC. This gap used to warn that the GPU reductions/convolution figures were latency rather than throughput, because every device row ran with gcsample = true. Finding (s) removed that: the collector is now decided per row from a measured device-pool probe, and only the documented materializers keep it. The committed archive is in the fixed regime on both cards, and the old warning's own symptom is gone — a $64^3$ Float64 convolve! scalar reads 33.1 µs on the RX 7900 XTX and 10.8 µs on the RTX 5070 Ti, against the $\approx 1.5$ ms floor this gap was written to describe.

  2. CUDA spans two NVIDIA generations, both on Enteropia (the office box; CPU Ryzen 9800X3D). characterize.jl now takes a cuda backend beside gpu/rocm (CuArray + CUDA.reclaim(), no comgr warm), so the memory-bounded one-class-at-a-time sweep runs on NVIDIA too. The RTX 5070 Ti (Blackwell sm_120, 16 GB) covers the full 64³–256³ matrix (both element types, all six classes; ~10.8 GB peak). 512³ exceeds 16 GB — the mul! tensor field alone is 4.5 GB and the build OOMs — but unlike AMD's HIP (gap 6), CUDA OOMs gracefully (a Julia OutOfGPUMemoryError, no context corruption), so probing the ceiling is safe. Enteropia now also contributes its 9800X3D CPU thread sweep beside the i7-12700K (host Aiporetne).

  3. Automated time-regression detection — BUILT (benchmark/regress.jl, 2026-07-22). One canary per execution mechanism (twelve: the broadcast route, each fused-kernel class, the tree reductions, FFT, transfer gather/scatter, the binning) at $128^3$ Float64, $\sim$1–2 minutes per backend, judged on minimum times against a committed per-host baseline (benchmark/baselines/<host>-<backend>[-tN].json) at a 25% tolerance with a hard exit code, plus the CPU serial-vs-threaded alarm $t_\mathrm{threaded} \le 1.1 t_\mathrm{serial}$ on every override-governed canary — the alarm that finding (l) lacked. Refreeze protocol: an intended slowdown reruns with --freeze in the same commit, with the reason. Calibration lesson from its first run, recorded so it is not relearned: 20 samples of a $\sim$250 µs canary let minima jitter $\sim 2\times$ at eight threads and false-alarm; the frozen calibration is 100 samples × 5 evals (batch-averaged minima), which held 12/12 invariant across repeated judges on both backends. Baselines for both hosts are committed — Enteropia (cpu-t1, cpu-t8, cuda) and Aiporetne (cpu-t1, cpu-t8, rocm; frozen 2026-07-22 with that host's post-rewrite re-sweep, its freeze-run inversion alarm 8/8 ok). Deliberately not push-triggered CI (cost policy; shared runners are noise): the BenchmarkGroup layout still keeps AirspeedVelocity.jl or PkgBenchmark.jl a drop-in if a CI story ever changes. First live catch (2026-07-24): the t1 helmholtz canary flagged at 1.27× baseline, which turned out not to be a slowdown but a dead-code bug — decision 42 had dropped the kernel's squared-wavenumber arguments while leaving the gated ::CPU loop's signature stale, so the loop fell out of dispatch and CPU helmholtz silently reverted to the KA-on-CPU launch decision 40 had escaped. Restoring the loop returned the canary to baseline without a refreeze — the check working exactly as designed, catching an achieved-time regression the allocation and pass audits cannot see (decision 47).

  4. The canary is a $128^3$ relative instrument, and on an X3D part it is largely cache-resident. Its grid is fixed at $128^3$ (benchmark/regress.jl, unchanged since the lane was built) so a lane costs 2–3 minutes and gets run. The consequence, measured on Enteropia 2026-08-05: add! moves 151 MB against a 96 MB L3, so repeated samples keep much of it resident and the single-thread figure reads 63.8 GB/s — well above the ~41 GB/s a Zen 5 core sustains from DRAM (§4(l)). The canary therefore does not probe the DRAM-bound regime, which is the one decision 37 names as the CPU path's tuning target; at $512^3$ the same working set is 9.66 GB and cannot cache. A regression that appears only once a field stops fitting would pass this net silently. That regime is covered instead by the characterization sweep (benchmark/characterize.jl, $64^3$–$512^3$), which is the instrument to reach for when a change plausibly alters memory traffic rather than arithmetic.

  5. Run-to-run variance — absolute numbers carry ~10% jitter, and the atomic-binning canary is the widest: radial_spectrum at -t8 on Enteropia measured 4.871, 4.793, 4.747 and 4.504 ms over four back-to-back repeats against a 4.384 ms baseline (2026-08-05) — an 8% spread with every draw above the frozen value, which sits low in its own distribution. Its scatter-add threads outside the with_threading override and its summation order is nondeterministic, so contention decides the figure. Read a single reading of that row against the baseline as noise unless it clears the 25% tolerance, and confirm any movement against the other backends before believing it. Cross-platform/-commit comparisons are only meaningful within a single session (hence the side-by-side discipline of §3); the tables here are indicative magnitudes, not contract values. The allocating kernel builders (spectral_cutoff / spectral_band / radial_kernel / assignment_window / translation_kernel) are the noisy extreme: their threaded $256^3$ cells swung ±50% between two same-day sweeps (GC timing on paid-once allocating passes) — read them as indicative only, never as regressions.

  6. GPU at 256³ — three traps, none a rocFFT bug (measured on a since-retired 12 GB AMD card; the $256^3$ ceiling below is specific to that capacity, while the cold-compile and allocator traps are not capacity-dependent. The wedge-instead-of-error behaviour itself still binds the current cards — it simply moves up a grid, as this gap's own 2026-06-26 update records for a 512³ Float64 sweep on the 24 GB card). Earlier notes blamed "rocFFT 256³ planning"; that was wrong. The facts, measured:

    • 256³ FFT works. Scalar and vector r2c/c2r at 256³ take ~1 s to plan and ~15–20 ms to run; the full fft class passes at 256³.
    • Cold kernel compilation looks like a hang. The first GPU use after a reboot compiles kernels host-side via AMD comgr → 0% GPU, 100% CPU, VRAM pool reserved, no output, for minutes. Never kill a cold first run — a killed compile never persists to ~/.cache/comgr, so the next run restarts cold. The characterize.jl sweep warms the cache with one trivial kernel up front. A further mitigation for the rocFFT share of the compile: setting the ROCFFT_RTC_CACHE_PATH environment variable to a writable file makes rocFFT persist its runtime-compiled FFT kernels there and reuse them across processes, turning that part of the cold start into a one-time cost (rocFFT runtime compilation).
    • The 256³ working set overflows 12 GB VRAM, and HIP segfaults instead of erroring — the crash is hipMallocFromPoolAsync in libamdhip64.so. Two compounding causes, two fixes: (i) holding all six classes' fields live for one (size, type) exceeds 12 GB at 256³ (a 4-class sweep fit; adding reductions + convolution did not) → characterize.jl builds one (op-class, size, element-type) at a time, bounding the working set to a single class (~few GB); (ii) GC returns freed device memory to the AMDGPU pool, not the OS, so the pool high-water mark accumulates across iterations and 256³ OOMs late (the first pairs fit, the last does not) → AMDGPU.reclaim() between iterations releases blocks back to the OS. Knock-on: a VRAM-OOM segfault can still degrade the HIP context until a reboot / rocm-smi --gpureset, after which even small ops segfault under load.
    • A GC-free benchmark loop wedges the allocating reductions — independent of grid size (seen at 64³), and the cause of a 4-hour hang. The lpnorm reduction materializes a pointwise-magnitude field per call; BenchmarkTools' tune!/run does almost no host allocation, so Julia's GC (host-pressure triggered) never fires, the dead GPU temps pile into the AMDGPU pool until it hits 12 GB, and the allocator spins — CPU pegged, GPU idle, VRAM maxed, for hours. It is GC-lag, not a leak (GC.gc() every ~50 calls holds the pool flat; a real solver fires GC every step, so the op is fine in use). Fixed by gcsample = true for GPU runs (characterize.jl and the ROCm runner): a GC before each sample bounds the pool — the reductions class then completes at ~0.5 GB peak. Distinct from the cold-compile hang above — there comgr is active (compiling, minutes); here it is idle (wedged, hours).

    With the per-(op-class, size, type) build the full 64³–256³ GPU column is in RESULTS.md. The standing limit on that card was the 12 GB ceiling itself: even one class's both-element-type 256³ fields strain it (hence the one-class-at-a-time build), and 512³ won't fit on that card. If a future OOM-segfault degrades the context, reset with rocm-smi --gpureset from a console (it can crash an active display session) or reboot.

    Update (2026-06-26, RX 7900 XTX, gfx1100, 24 GB). On RDNA3 256³ is indeed trivial for every class (both element types), and a 512³ Float32 point is now in RESULTS.md for the bandwidth-bound classes (fft, algebra, operators, convolution). But 512³ is not free even at 24 GB: transfer is omitted (its NUFFT oversamples ×2 to a 1024³ work grid) and reductions is omitted (the radial reductions hold a ≈24 GB live set at 512³ — vector fields in both representations + the inverse-rfft plans). A 512³ Float64 sweep of the heavy classes exceeds 24 GB, and a HIP OOM wedges the allocator (GPU 0 %, one host core spinning, VRAM full) rather than erroring — the same trap as the cold-compile / GC-free hangs above, and gcsample does not help when the live set (not GC lag) is what overflows. So the 512³ column is Float32 and skips those two.

  7. The storage class is swept on BOTH vendors — CLOSED 2026-08-23. Decision 63's device-only class carries 66 rows in each of the GPU 5070TI and GPU 7900XTX columns, and the four rows decisions 71 and 72 added are filled on all five Aiporetne lanes, so RESULTS.md has seven class sections with no half-filled table left. See finding (x) for the cross-vendor reading, which is the comparison this class exists to support. Method note, kept because it is what makes a partial sweep safe: characterize.jl overwrites the archive it is given, so a class-only sweep must be written to a separate file and merged. Both halves were done that way — the CUDA one verified 426 pre-existing rows bit-identical afterwards, the ROCm one 467 — and the merge is verified in both directions, re-merging the pre-merge backup into the merged archive to confirm it adds nothing and changes nothing, which catches a row silently dropped as well as a row silently altered.

  8. aarch64 is a production host architecture with zero coverage. The recorded production target (docs/ARCHITECTURE.md decision 37) is NAISS Arrhenius, and its GPU nodes are GH200 superchips: the CUDA device is hosted by a 72-core Grace CPU — ARM, aarch64 — while the CPU partition is x86-64 EPYC. The GPU path's host code will therefore eventually build and run on ARM, and nothing in this package has ever been compiled, tested, or benchmarked on that architecture. No blocker is known: the stack is pure Julia plus JLL artifacts published for aarch64-linux (FFTW, HDF5), and CUDA.jl runs on aarch64 hosts, Grace Hopper among them. But "no known blocker" is not "verified", and none of the x86-measured CPU findings transfer — finding (h)'s ESTIMATE mis-planning turns out to reach both x86 microarchitectures in the fleet rather than being the Zen 5 artifact it was first recorded as — which is a reason to carry MEASURE to ARM as a default expectation rather than a reason to assume it is absent — and NEON changes FFTW's codelet landscape entirely. Standing guard until access lands: never adopt an x86-only dependency or recommendation — the MKL FFTW provider, which has no aarch64 build, is the canonical tempting example — and when it does land, the first step on an Arrhenius node is the test matrix, then this benchmark suite.

  9. CUDA unified memory is unmeasured on Grace Hopper, the host it matters on. Finding (as) measured one x86 card, where pages migrate over PCIe. A GH200 reaches its Grace memory over NVLink-C2C, a far faster link, and also supports a mechanism the preference does not select: the GPU addressing ordinary system memory directly through its page tables, with no migration. CUDA.jl's "unified" is managed memory, which migrates, so which of the two suits a streaming pseudospectral pass is open.

    Three things make that measurement easy to get wrong. The preference is read at compile time, so device and unified memory cannot be compared in one Julia session; the comparison needs two environments run back to back. CUDA.jl prefetches a unified array before every launch only when the process sees exactly one GPU, so a job restricted to its own device and one seeing all four measure different regimes. And the benchmark harness refuses unified memory by design, so the measurement is a bespoke script, not a characterize.jl sweep.

    The design that separates the two costs: at a size that fits in GPU memory, device against unified, which prices the overhead alone; then a size exceeding GPU memory by a few percent, on unified memory, which adds the cost of oversubscription. Record the visible-device count with both.

(an) The traversal order's rebuild is allocation-free where it was 15 MiB a call (2026-09-03, decision 80). A point_traversal_order build allocates four arrays — the Int32 result, the counting sort's Int64 keys, the histogram with its prefix sum, and the Bool marks of the permutation check — and a consumer whose points move pays that on every rebuild. Measured on the host at $32^3$:

  • allocating point_traversal_order: 18.9 KB at $10^3$ points, 135.9 KB at $10^4$, 1.31 MB at $10^5$, 13.0 MB at $10^6$ — linear in the point count, as its four arrays are.
  • in-place point_traversal_order!: 1248 bytes at $10^3$ and 1312 at $10^6$ — constant, a ratio of roughly $10^4$ at the larger count.

The residue is not the package's: three KernelAbstractions launches plus the validation's own leave about 1.2 KiB of host-side launch bookkeeping, the same class as the FFTW callback of §4(t), and it is why test/allocations.jl guards this row with a bound rather than a zero. The bound is far below one point-sized array, so a regression that began allocating per point could not hide under it. What the device pool cares about is the part that scales, and that is now the caller's storage entirely.

A correction to (t), found 2026-09-04. The callback state is per PLAN EXECUTION, and decision 76 changed how many executions a transform makes: a rank-R field was one batched execution and is now one per contiguous component. Measured at $24^3$ on four threads, to_physical! allocates exactly 4032 B per component — 4032 scalar, 12096 vector, 36288 tensor — and 0 B at one thread, where the callback is absent. test/allocations.jl's field_threshold carries slack for ONE execution ($4096 \times$ the thread count), so the scalar and vector rows kept passing while the nine-component tensor rows failed at four threads and above; the threaded CI lane had been red on those three rows since decision 76, and the bound now scales with the component count too. The size-independence recorded above still holds: what multiplies is the number of executions, not the cost of one.

(ao) The traversal build's running total was the one unthreaded stage, and its share is set by the GRID (2026-09-04, decision 81). Three of the four stages of point_traversal_order are KernelAbstractions kernels and thread by KA's own partitioning; the running total over the block counts was cumsum!, serial on a host array. Because the block count follows the grid and tile_size rather than the point count, the serial stage does not shrink as the rest speeds up:

  • 9800X3D, $10^6$ points, default tile_size, $256^3$: build 9.24 ms at one thread and 1.87 at eight (4.9×), with the scan flat at 0.08 ms — 1% of the build serially, 4% at eight threads.
  • Same at $512^3$ (2.1M blocks): build 3.41 ms at four threads and 2.85 at eight, with the scan at 0.69–0.70 ms — 20% and 25% of the build. This is the default tile size at the grid decision 37 names for the CPU, not a corner.
  • At tile_size = 1 on $256^3$ (16.8M blocks) it reached 55% of the build at eight threads.

Threaded (_scan_offsets!), the scan runs $2.6$–$7.3\times$ faster and the build gains $1.17\times$ at four threads and $1.26\times$ at eight at $512^3$. The scan's own speedup peaks around 2.1M blocks and falls off at 16.8M, where the two-pass form's extra read of the counts saturates bandwidth.

Two other observations from the same sweep. The build is SLOWER at tile_size = 16 than at 4 on eight threads (4.79 against 1.89 ms), which is atomic contention on only 4096 counters — the same mechanism as the radial shell binning of the triage section. So the build has a sweet spot near the default, with contention above it and the scan below it, and that is the opposite of the gather's preference for coarser blocks; the two pull against each other and only the gather's direction was documented.
